# PRD v13 - 메인 화면 개선 (여행 소식·인기 여행지)

> 현재 메인 화면은 '내 여행' 리스트뿐이다. 여행자가 실제로 행동을 바꿔야 하는 정보(안전·혜택)와 다음 여행지 영감(인기 여행지)을 한 화면에 추가한다.

## 1. 목표와 원칙

- 메인을 '내 여행 목록'에서 '여행 전후에 매일 열어 볼 이유가 있는 홈'으로 바꾼다.
- 정보는 **길게 나열하지 않는다.** 안전 경보, 입국 규정 변경, 항공편 변경처럼 여행에 영향을 주는 것 2\~3개만 먼저 보여주고, 나머지는 더보기로 둔다.
- **내가 등록한 여행지가 있으면 그 여행지 소식을 항상 우선 노출한다.**
- 모든 소식은 출처를 표시하고 원문 링크로 연결한다. 원문을 복사해 싣지 않는다(저작권).

## 2. 화면 구성 (위 → 아래)

| 순서 | 영역 | 내용 |
| --- | --- | --- |
| 1 | 내 여행 (기존) | 등록한 여행 카드, D-day |
| 2 | 여행 소식 | 여행 안전 / 여행 혜택 탭. 탭당 카드 2\~3개 + '더보기' |
| 3 | 어디로 떠나볼까요? | 해외 / 국내 인기 여행지 카드(가로 스크롤) |

- 여행이 하나도 없을 때는 '내 여행' 영역이 빈 상태가 되지 않도록 '새 여행 만들기' 안내를 보여주고, 아래 영역이 화면을 채운다.
- 모바일(폭 360\~430px)을 기준으로 설계하고, 데스크톱에서는 카드를 2\~3열로 펼친다.

## 3. 여행 소식

### 3-1. 여행 안전 (여행 전 알아야 할 최신 안전 정보)

- 단순 여행 뉴스가 아니라 **행동이 바뀌는 정보**만 올린다: 여행경보·안전 공지, 입국 규정 변경(비자·전자입국신고 등), 항공편 운항 변경·결항, 자연재해·시위·감염병.
- 카드 표시 항목: 제목, 지역(나라/도시), 게시일, 중요도 배지, 출처 이름.
- 정렬 우선순위: (1) 내 여행지의 중요도 높음 → (2) 내 여행지의 그 외 → (3) 그 외 지역의 중요도 높음 → (4) 최신순.
- "내 여행지"는 지금 진행 중이거나 예정된 여행의 국가코드(`destinations.country_code`, PRD v12)로 판단한다. 지난 여행(D+)은 제외.
- 중요도 3단계: **높음**(여행 취소·변경까지 고려해야 함), **보통**(유의하면 되는 정보), **참고**.
- 정보가 없을 때는 '현재 등록된 주의 소식이 없어요'라는 빈 상태를 보여준다.
- 안전 정보는 틀리면 피해가 크므로 화면에 "정확한 내용은 출처 공식 사이트에서 확인하세요" 문구를 항상 표시한다.

### 3-2. 여행 혜택 (놓치면 아쉬운 할인·축제)

- 하위 구분: **국내 여행 이벤트·이슈**, **해외 여행 이벤트·이슈** (탭 안에서 필터 칩으로 전환).
- 카드 표시 항목: 제목, 지역, 기간(시작\~끝), 출처 이름. 지난 기간의 항목은 자동으로 숨긴다.
- 정렬: 내 여행지·여행 기간과 겹치는 이벤트 우선 → 종료가 가까운 순.
- 플랫폼 자체 광고·플랫폼 커미션이 있는 상품 판매 링크는 이번 범위에서 제외한다(정책·동의 문제가 따로 생긴다).

### 3-3. 상세 화면 (카드 클릭 시)

- 표시: 제목, 지역, 게시일, 중요도, **우리가 정리한 요약(200자 내외)**, 행동 안내(해당 시), **출처 이름 + 원문 보기 링크**, 최종 확인일.
- 원문 전체를 복사하지 않는다. 요약은 우리 문장으로 다시 쓰고, 자세한 내용은 출처 링크로 보낸다. 링크는 외부 브라우저(앱에서는 인앱 브라우저)로 열어 우리 화면과 구분된다.
- 한 카드에 출처가 여러 개일 때는 대표 출처 1개만 쓴다.

## 4. 어디로 떠나볌까요? (인기 여행지)

- 한국인이 가장 많이 간 해외 여행지 / 국내 여행지를 카드로 보여준다 (탭 2개: 해외, 국내, 가로 스크롤, 각 5\~10개).
- 카드: 도시명, 나라, 순위, **집계 기준월**(예: 2026년 9월 기준), 출처.
- 카드를 누르면 여행 만들기로 이어진다 (여행지가 미리 선택된 상태). 도시가 `destinations`(PRD v12)에 있으면 그 데이터를 쓰고, 없으면 선택 시점에 확정한다.
- **"한 달 내"의 실제성:** 출입국·관광 수치는 보통 다음 달에 확정·공개되므로(최신 수치는 1\~2개월 지연 가능), '지난달 기준'으로 표시하는 것이 현실적이다. 실시간 순위가 필요하면 별도 소스가 필요하다. (공식 통계의 공개 시점은 구현 전 확인 필요)
- 앱 자체 사용자 데이터(Routory에서 만든 여행 집계)는 사용자 수가 적어 대표성이 없고 개인정보 이슈가 있어 사용하지 않는다. 나중에 보조 지표로만 더할 수 있다.
- 카드 이미지는 라이선스가 불확실한 외부 사진 대신 우리가 만든 그라데이션·아이콘을 기본으로 한다. 공공 데이터의 이미지를 쓸 경우 이용 조건을 확인한다.

## 5. 데이터 출처 (사용자가 제시한 참고 사이트)

| 출처 | 쓰임 | 방식 제안 | 확인 필요 |
| --- | --- | --- | --- |
| 외교부 해외안전여행 (0404.go.kr) | 여행경보·안전 공지 | 공공데이터 API가 있는지 확인 후 연동, 없으면 수동 등록 + 링크 | API 존재 여부, 이용 조건(리터러시·표기 의무) |
| 한국관광공사 (visitkorea) | 국내 축제·행사, 국내 인기 여행지 통계 | 공공데이터(TourAPI·관광 데이터랩) 연동 가능성 확인 | 제공 항목, 이미지·텍스트 이용 조건, 호출 한도 |
| IATA Travel Centre | 입국 요건(비자·여권) | **링크아웃만** (본문 수집·크롤링 금지) | 링크 이용 방식(상업 서비스 성격의 데이터일 가능성) |

|  |  |  |  |

- 위 표의 "연동 가능/불가"는 이 문서 작성 시점에 공식 문서로 검증하지 못했다. 구현 첫 단계에서 공식 문서·이용약관을 확인해야 한다.
- 원칙: 약관이 허용하지 않는 사이트는 크롤링하지 않고 링크로만 연결한다. 공공 데이터라도 표기 의무(출처 밝히기)가 있으면 지킨다.

## 6. 업데이트 방식 — 결정이 필요한 사항

| 방식 | 장점 | 단점 |
| --- | --- | --- |
| A. 내가 직접 조사해 올림 (관리자 입력) | 품질·저작권 통제가 쉬움, 개발이 가벼움 | 정기적으로 내가 해야 함, 안전 정보의 실시간성이 떨어짐 |
| B. 자동 수집 (주기 실행) | 운영 부담이 적고 최신성 유지 | API 존재·약관에 따라 불가한 소스가 있음, 오류 시 잘못된 정보 노출 위험 |
| C. 혼합 (권장) | 자동 수집은 '후보'로 쌓고, 사람이 승인하면 노출 | 관리자 화면이 필요 |

**제안 (단계적으로):**

1. 1단계 — 관리자 수동 등록. 간단한 관리 화면(기존 공지사항 관리와 같은 권한 방식)에서 제목·요약·출처·링크·중요도를 입력한다. 내용이 맞는지 사람이 검수하는 출발점이라 가장 안전하다.
2. 2단계 — 연동 가능한 공공 API(여행경보, 국내 축제·행사)만 자동 수집해 '승인 대기' 후보로 쌓는다. 승인해야 노출된다.
3. 3단계 — 여행경보 단계 상향 같은 위험도 높은 항목은 내 여행지에 한해 자동 노출(+ 푸시 알림, PRD v11 연동)을 검토한다. 자동 노출은 정확성 검증 후에만 한다.

- 인기 여행지는 월 1회 갱신(관리자 입력 또는 통계 자료 기반)으로 시작한다.

## 7. 데이터 모델 (제안)

- `travel_feed_items`: id, kind('safety'|'benefit'), scope('domestic'|'overseas'), country\_code(nullable), region\_label, title, summary(우리 문장, 200자 내외), action\_tip(nullable), importance('high'|'medium'|'low'), published\_at, valid\_from(nullable), valid\_to(nullable), source\_name, source\_url, last\_checked\_at, status('draft'|'published'|'archived'), origin('manual'|'auto'), created\_by, created\_at
- `popular_destinations`: id, scope('overseas'|'domestic'), period('YYYY-MM'), rank, name\_ko, country\_code(nullable), destination\_id(nullable, `destinations` 참조), source\_name, source\_url, created\_at. (scope, period, rank) 유니크
- 읽기: 로그인한 사용자에게 status='published'만 허용. 쓰기: 관리자(기존 공지사항과 같은 권한 방식)만, RLS로 직접 쓰기 차단.
- 자동 수집을 넣을 때는 Edge Function(service role)이 status='draft', origin='auto'로 싸고 관리자가 승인해 published로 바꾼다.
- 만료: valid\_to가 지난 혜택 항목은 조회에서 제외하고, 안전 항목은 게시일이 오래되면(예: 90일) 자동으로 보관 처리한다.

## 8. 개인정보·정책

- "내 여행지 우선 노출"은 이미 저장된 여행 데이터로 앱 안에서만 판단하고, 외부로 전송하지 않는다.
- 외부 링크 클릭 시 우리가 개인식별 정보를 넣지 않는다.
- 출처 표기와 "공식 사이트에서 확인" 안내는 개인정보 처리방침(PRD v10)의 면책 문구와 일관되게 둔다.

## 9. 기존 기능과의 관계

- **여행 정보 브리핑(PRD v9)**: 여행 하나에 묶인 정보(환율·날씨·현지 뉴스 등). 이번 메인 소식은 전체 사용자용 피드다. 나중에 브리핑의 '현지 뉴스' 카드가 이 피드를 재사용할 수 있다.
- **여행지 확장(PRD v12)**: country\_code, destinations를 이 기능이 그대로 쓴다.
- **푸시 알림(PRD v11)**: 안전 경보 푸시는 초기 범위에서 제외, 3단계에서 검토.

## 10. 개발 단계 제안

1. 사전 확인: 출처별 API·이용 조건 공식 문서 확인, 현재 메인 화면 구조 파악
2. `travel_feed_items`, `popular_destinations` 테이블 + RLS
3. 관리자 등록 화면(여행 소식, 인기 여행지)
4. 메인 화면: 여행 소식 영역 + 상세 화면 + 출처 링크
5. 메인 화면: 어디로 떠나볌까요 영역
6. (선택) 공공 API 자동 수집 → 승인 대기 후보

## 11. 확인이 필요한 사항

- 업데이트 방식: 위 제안(수동 시작 → 공공 API 후보 자동화)으로 갈지, 계속 수동으로 운영할지
- 관리자 등록 화면을 앱 안에 둘지, 별도 관리 페이지로 둘지 (현재 공지사항 등록 방식 기준)
- 인기 여행지를 '지난달 기준'으로 해도 괜찮은지 (실시간 순위는 소스가 없음)
- 혜택 항목에서 플랫폼 할인(항공권·숙소 프로모션)까지 다룰지, 공식 축제·정부/지자체 이벤트로만 한정할지
- 항공사 공지는 어느 항공사까지 링크를 모을지 (내 여행의 항공권 항공사 기준 우선을 제안)
