# Common pages (알림 · 설정)

> CLAUDE.md에서 이동된 상세 내용. 이 영역을 작업하기 전에 먼저 읽을 것.

- **Common pages (알림 · 설정, `commonPages.js`, routes `#/notifications`/`#/settings`)**: the single shared destination for both MAIN-MENU's and the SHELL's MYTRIP-MENU's 🔔/⚙ buttons — one small module defines both routes rather than each menu getting its own copy. Both share a `←` back button that calls `history.back()` instead of navigating to a fixed route, because these two pages are reachable from very different places (main with no SHELL, or any of the five SHELL screens) and there's no single "correct" destination to hardcode — relying on browser history works because the only way in is clicking a menu button on some page, so there's always a real previous entry to pop back to. Both routes go through the same `requireLogin` guard as every other screen (`app.js#initRouting`). The module also owns `ICONS.bell`/`ICONS.gear` (plus its own `ICONS.back`) so `mainPage.js` and `tripShell.js` render pixel-identical icons rather than each keeping a separate copy — both read `window.TripLog.commonPages.ICONS` lazily (only when their own menu is first built), so load order just needs `commonPages.js` before those two, which it already is (loads right after `router.js`). `#/notifications` is still a bare `"준비 중이에요."` placeholder; `#/settings` now has one real section in it — "개인정보 및 약관" (`.simple-page-section`/`-title`, new CSS: just a small muted label above the list) holding a three-item list (reusing `.mytrip-menu`'s own CSS, not a new list style) — 이용약관 → `#/terms`, 개인정보처리방침 → `#/privacy`, and 개인정보 수집·이용 안내 → **also** `#/privacy` (same `data-action` handler matches both `"privacy"` and `"privacy-notice"`) — above its own `"다른 설정은 준비 중이에요."` note. The third item exists to mirror `consentPage.js`'s "개인정보 수집·이용 동의" checkbox by name (a user who remembers checking that during consent should find a matching menu label here), but there's no separate document for it, so it just reopens the privacy policy. All three links are plain navigation to the already-read-only `#/terms`/`#/privacy` screens — neither screen has ever had a checkbox or save button (only `#/consent` does), so "읽기 전용, 재동의 없음" required no special mode here, just pointing at what already existed. Below that, a second section, "계정", holds `로그아웃` (plain `auth.signOut()` then `#/login` — the same `logout()` shape `mainPage.js`/`tripShell.js` used to each have their own copy of before it was pulled out of both menus; this is the "다른 위치" those removals deferred to) and `회원 탈퇴` (navigates to `#/account-delete`, styled with the existing `.mytrip-menu-logout` class for the red/separated look — see **Account deletion (회원 탈퇴)**). Both pages also toggle `body.has-simple-page-bg` (`--surface-blue`, `#d6e4fb`) on enter/leave, the same `body.has-main-bg` pattern `mainPage.js` uses — **this background is specific to these two pages**, not shared by `#/terms`/`#/privacy`/`#/account-delete`, which stay on the plain `--page-bg` the generic `.page` class already gives them.
  - **`#/settings` since the 고객센터/여행 내보내기/버전정보 pass**: a new first section "고객센터" (same `.simple-page-section`/`.mytrip-menu` shape as "개인정보 및 약관") holds 공지사항/문의하기/도움말, each just a plain `router.navigate` to its own new route (`#/notice`/`#/contact`/`#/help`) — all three are bare `renderNotifications`-shaped `"준비 중이에요."` placeholders for now (`router.js`'s `ROUTES`/`PAGE_ALIASES`, `app.js`'s `CONSENT_GATED`, and `tripShell.js`'s `ALL_ROUTES` all got the three new route names alongside `notifications`/`settings`, same reasoning as those two — see this file's note on each). After "계정" sits "여행 내보내기", a single item with **no** `<h2>` section title above it (per spec: "섹션 메뉴는 아니지만") — clicking it calls `window.TripLog.tripExport.open()` — this file only knows that function exists (`tripExport.js` loads later in `index.html`'s order, but since the call happens inside a click handler rather than at load time, the order doesn't matter — see **Trip export (여행 내보내기)** below). Last, below the pre-existing `"다른 설정은 준비 중이에요."` line, a `<p class="simple-page-version">` shows a hardcoded `APP_VERSION` constant ("1.0.0") — kept in sync by hand with `triplog/package.json`'s `version` (that file is never fetched by the browser, so there's no way to read it from client code without adding a build step).
  - **Collapsible sections**: the three titled sections (고객센터/개인정보 및 약관/계정) now open and close on tap — "여행 내보내기" isn't one of them (no list under it to collapse), but was asked to sit and look exactly like one anyway (same position, font size, color). Each section's `<h2>` became a `<button data-toggle-section="<key>" aria-expanded aria-controls>` built by a small `collapsibleSection(key, title, itemsHtml)` helper, with a chevron (`ICONS.caret`, same 24×24 stroke-icon shape as `ICONS.back`/`bell`/`gear`) that rotates 180° via `.simple-page-section-title[aria-expanded="true"] .simple-page-section-caret` (same `[aria-expanded="true"]`-driven rotation `app.js`'s `.quick-transport-trigger-caret` already uses). `toggleSection` just flips `aria-expanded` and the list's `hidden` attribute — no animation, matching this app's existing plain `[hidden]` toggles rather than the custom height-animated collapse `dayMap.js`'s chevron handle does. Open/closed state lives in a module-level `sectionOpen` object (keys `"customer-service"`/`"legal"`/`"account"`), not re-initialized on every `render()` call, the same reason `consentPage.js`'s checkbox `state` isn't — stepping into 공지사항/이용약관/etc. and pressing back (a real `history.back()`, see this bullet's parent) should come back to the same open/closed sections, not reset them. All three sections start closed on a fresh visit. "여행 내보내기" reuses the bare `.simple-page-section-title` class (a small `actionTitle(action, label)` helper, parallel to `collapsibleSection`) so its position/font-size/color match the three toggle titles exactly, but without `data-toggle-section`/`aria-expanded`/a caret — it's wired to `data-action="trip-export"` instead, so `bindBack`'s click handler fires `tripExport.open()` directly rather than toggling a (nonexistent) list.
  - **"알림" 섹션** (PRD v11 "푸시 알림 시스템" 5번; `031_push_notifications.sql`의 `notification_settings` 테이블 필요; `sectionOpen`에 `notification` 키 추가 — 다른 세 섹션과 같은 `collapsibleSection` 모양으로 맨 위에 놓인다).
    - **토글 두 개**: 일정 알림(출발 임박·다음 일정)/초대·공유 알림(새 멤버 가입·초대 수락) — `notification_settings.schedule_enabled`/`share_enabled`와 1:1. 공지사항은 토글 없이 "공지사항은 항상 받아요" 고정 문구만(PRD가 명시적으로 끄는 설정을 두지 않음). 새 CSS 컴포넌트 `.toggle-switch`(체크박스를 숨기고 `.toggle-switch-track`이 배경/동그라미를 그리는 CSS-only 스위치) — `.consent-checkbox-row` 체크박스로는 on/off가 뚜렷하지 않아서 새로 만들었다(이 앱의 첫 토글 스위치).
    - **읽기/쓰기**: `notificationSectionHtml()`이 `storage.getNotificationSettings()`(동기, 기본값 `{scheduleEnabled:true, shareEnabled:true}` — 행이 없는 사용자도 이 기본값으로 먼저 뜬다)로 그리고, `renderSettings` 끝의 `hydrateNotificationSection(el)`이 `storage.loadNotificationSettings()`로 서버 값을 받아 체크박스를 다시 맞춘다. 토글 변경은 `change` 이벤트(`bindBack` 안)가 바로 `storage.saveNotificationSettings(...)`로 upsert하고, 실패하면 체크 상태를 되돌리고 `ui.showToast(err.message)`로 알린다(낙관적 업데이트 + 실패 시 롤백).
    - **알림 권한 배너** (`.settings-permission-row`, 토글 목록 맨 위 줄, `renderNotificationPermissionRow`): 매번 다시 계산해서 여섯 중 하나만 보여준다 — ① `navigator.standalone === false`(iOS Safari 일반 탭)면 "iPhone에서는 홈 화면에 추가한 뒤에 알림을 받을 수 있어요."(가장 먼저 검사돼서, 권한이 거부 상태여도 iOS 안내가 우선), ② 네이티브이고 `pushNotifications.getLastError()`가 있으면(FCM `registrationError`) "알림 등록에 실패했어요."(`.settings-permission-note--error`, `--text-danger`) — OS 권한은 허용됐는데(그래서 아래 `notificationPermissionState()`는 `"granted"`로 볼 것) FCM 등록 자체가 실패한 경우를 가로채 보여준다, ③ 웹(`!auth.isNativeApp()`)이고 `webPush.isSupported()`가 `false`면(Service Worker/Push API 자체가 없는 구형 브라우저 등) "이 브라우저에서는 알림을 지원하지 않아요." — 버튼을 아예 숨긴다, ④ `permissionPrompt.notificationPermissionState()`가 `"denied"`면 "설정에서 알림 권한을 허용해주세요.", ⑤ `"granted"`면 "알림이 켜져 있어요.", ⑥ 그 외(`"default"`/`"prompt"`/모름)면 "알림 켜기" 버튼(`data-action="notif-allow"`). ①·②·③·④는 버튼 자체가 없어서 권한 모달이 열릴 일이 없다 — "모달 대신 안내로 바꿔줘"를 버튼을 안 그리는 방식으로 만족시킨다.
    - **"알림 켜기" 클릭** → `permissionPrompt.askNotification(onAllow)`로 사전 안내 모달부터 연다(바로 OS/브라우저 권한을 묻지 않는다, `permission-prompts.md` 참고) → 모달의 '허용'을 눌러야 `requestNotificationPermission(el)`이 실제 권한을 요청한다. 네이티브는 `window.TripLog.pushNotifications.requestAndRegister()`로 이어져 `PushNotifications.requestPermissions()` → 허용되면 `"routory-default"` 채널 생성 + `register()`(FCM 토큰 요청) → `'registration'` 이벤트의 토큰을 `device_tokens`에 `upsert(platform:'android')`까지 간다(`pushNotifications.js`, **Permission prompts** 참고). 웹은 `window.TripLog.webPush.subscribe()`로 이어져 `Notification.requestPermission()` → 허용되면 `/sw.js`를 서비스 워커로 등록하고 `pushManager.subscribe({userVisibleOnly:true, applicationServerKey: <config.js의 vapidPublicKey>})` → 받은 `PushSubscription`을 JSON으로 `device_tokens`에 `upsert(platform:'web')`까지 간다(`webPush.js`, 아래 **Web Push** 참고). 요청 직후 배너를 한 번 다시 그리고, (네이티브) `registrationError`가 비동기로 늦게 와도 `pushNotifications.onError` 구독이 "지금 #/settings가 떠 있으면"(`settingsEl`) 배너를 다시 그린다.
    - **로그아웃/회원 탈퇴 직전**: `logout()`과 `accountDeletePage.js`의 `performDelete()` 둘 다 `pushNotifications.removeDeviceToken()`과 `webPush.unsubscribeAndRemove()`를 먼저 호출한다 — 네이티브는 FCM 토큰 행만, 웹은 실제 브라우저 구독(`subscription.unsubscribe()`)까지 끊고 `device_tokens` 행도 지운다(localStorage `triplog.pushToken`/`triplog.webPushToken`에 각각 기억해 둔 값으로 "이 기기/브라우저의" 행만 식별 — 다른 기기나 다른 사용자의 토큰은 건드리지 않는다). 둘 다 플랫폼이 다르면 `isSupported()`로 조용히 no-op이라 분기 없이 둘 다 불러도 안전하다. 다음에 같은 기기/브라우저로 로그인하는 사람에게 이전 사용자의 알림이 가지 않게 하려는 것 — 실패해도 로그아웃/탈퇴 자체는 막지 않는다.

- **Web Push** (PRD v11 "푸시 알림 시스템"; `triplog/sw.js` + `triplog/js/webPush.js`; `031_push_notifications.sql`의 `device_tokens` 필요; PC/안드로이드 크롬·엣지에서 동작, iOS는 16.4+에서 홈 화면에 추가한 PWA 상태일 때만 — 그 외 iOS Safari는 위 "알림" 섹션의 ① 안내로 걸러진다): FCM을 쓰는 네이티브(`pushNotifications.js`)와 달리 VAPID 키 쌍으로 서명하는 표준 Web Push다.
  - **서비스 워커 위치**: `triplog/sw.js` — 반드시 사이트 루트에 있어야 한다. 서비스 워커의 기본 scope는 "자신이 있는 경로 아래 전체"라서 `js/sw.js` 같은 하위 경로에 두면 `/#/...` 같은 앱의 다른 경로를 제어할 scope를 못 받는다. `vercel.json`의 `rewrites`는 손대지 않았다 — `triplog/`가 이미 Vercel 배포 루트라서(`vercel`/`vercel --prod`를 `triplog/` 안에서 실행, `docs/deploy.md`) `triplog/sw.js`가 그대로 `/sw.js`로 서빙된다. `vercel.json`에 `/sw.js` 전용 `Cache-Control: no-cache` 헤더를 추가했다(`docs/deploy.md`) — 서비스 워커 파일은 브라우저가 어차피 하루 간격으로 업데이트를 확인하지만, Vercel의 기본 정적 자산 캐싱에 걸려 그보다 오래 묵는 일을 막는다. `serve.py`는 모든 파일에 이미 `no-store`를 보내므로 로컬은 그대로도 안전하다.
  - **`sw.js`의 두 이벤트**: `push`는 `event.data.json()`으로 `{title, body, url, icon?}` payload를 읽어(파싱 실패 시 `event.data.text()`로 대체, 그래도 빈 알림보다 낫다는 원칙) `self.registration.showNotification`을 띄운다 — `icon`/`badge` 기본값은 전용 앱 아이콘 자산이 아직 없어서 로그인 화면이 이미 쓰는 `img/login-icon.png`(512×512)를 재사용한다. `notificationclick`은 `event.notification.data.url`(해당 여행 화면의 해시 경로, 예: `/#/my-trip/<id>`)로 열린 탭이 있으면 `client.focus()` + `client.navigate()`로 재사용하고, 없으면 `clients.openWindow()`로 새 창을 연다. 오프라인 캐싱(install/activate의 캐시 전략)은 다루지 않는다 — 이 서비스 워커의 유일한 목적은 푸시다. `push`/`notificationclick` payload 계약(서버가 어떤 JSON을 보내야 하는지)은 아직 실제로 보내는 쪽(Edge Function `send-notification`)이 없어서 이 파일의 기대 형태로만 존재한다 — 그 함수를 만들 때 이 형태를 맞춰야 한다.
  - **`webPush.js`** (`window.TripLog.webPush`): `auth.js`/`flight.js`와 같은 "네이티브 브리지가 올려 둔 `window.Capacitor.Plugins.*`를 그대로 쓴다"는 이 앱의 무번들러 패턴과 짝을 맞춰, 여긴 반대로 브라우저 표준 API(`navigator.serviceWorker`, `window.PushManager`, `Notification`)를 직접 쓴다 — 별도 라이브러리/번들 없이도 표준 API라 가능하다.
    - `isSupported()`가 `!auth.isNativeApp()`을 **가장 먼저** 검사한다(요청 4번) — Capacitor 네이티브 앱의 웹뷰 안에도 `ServiceWorker`/`PushManager`가 기술적으로 존재할 수 있지만, 이 앱은 네이티브에서 FCM(`pushNotifications.js`)만 쓰기로 했으므로 네이티브에서는 이 경로 전체가 항상 꺼져 있어야 한다. 그다음에야 `'serviceWorker' in navigator && 'PushManager' in window && typeof Notification !== 'undefined'`를 본다.
    - `subscribe()`: `Notification.requestPermission()` → `"granted"`가 아니면 그냥 끝(요청 2번 "사전 안내 모달 → 허용을 누른 뒤에만" 흐름과 맞물려, 이 함수 자체는 이미 모달의 '허용' 이후에만 불린다 — 거부해도 모달이 다시 뜨지 않게 하는 책임은 `commonPages.js`가 아니라 브라우저의 "한 번 거부하면 재요청 시 조용히 거부"라는 표준 동작에 있다). 허용되면 `navigator.serviceWorker.register("/sw.js")`(한 번 등록하면 `swRegistration`에 캐시) → 이미 구독이 있으면(`getSubscription()`) 재사용, 없으면 `pushManager.subscribe({userVisibleOnly:true, applicationServerKey: urlBase64ToUint8Array(config.js의 vapidPublicKey)})`로 새로 구독 — `userVisibleOnly:true`는 표준 요구사항(이 값 없이는 Chrome이 구독 자체를 거부한다: "보이지 않는 푸시로 남용하지 않겠다"는 약속). 구독에 성공하면 `JSON.stringify(subscription.toJSON())`을 `device_tokens.token`에 `upsert(platform:'web')`하고, 같은 문자열을 `localStorage.triplog.webPushToken`에도 남겨 둔다(로그아웃 시 "이 브라우저의" 행 식별용 — `pushNotifications.js`가 FCM 토큰을 같은 방식으로 캐시하는 것과 동일한 패턴).
    - `unsubscribeAndRemove()`: 저장해 둔 `localStorage` 토큰 문자열을 먼저 읽어 두고(구독을 끊고 나면 `getSubscription()`으로 다시 물어볼 수 없어서, 끊기 *전에* 값을 챙겨야 한다 — 끊는 것과 식별자를 구하는 것의 순서가 중요), 등록된 서비스 워커의 현재 구독을 `unsubscribe()`한 뒤, 그 토큰 문자열로 `device_tokens`에서 `user_id`+`token` 일치 행만 지운다. 구독 해제가 실패해도(네트워크 등) DB 행 삭제는 시도한다 — 어느 한쪽이 실패해도 로그아웃/탈퇴 자체를 막지 않는다(네이티브 쪽 `removeDeviceToken()`과 동일한 "실패해도 조용히" 원칙).
  - **VAPID 키**: `npx web-push generate-vapid-keys`(Node, `web-push` npm 패키지)로 한 쌍을 만든다 — Public Key는 `triplog/js/config.js`의 `vapidPublicKey`(이미 2026-10-17 대화에서 등록됨, 브라우저에 노출돼도 안전한 공개키), Private Key는 클라이언트 코드 어디에도 두지 않고 앞으로 만들 Edge Function `send-notification`의 Supabase Secrets(`VAPID_PRIVATE_KEY`, 사용자가 직접 `supabase secrets set`으로 등록)로만 쓴다. 한 번 발급한 키 쌍을 나중에 재발급하면 기존 구독이 전부 무효화된다 — 운영 중 교체는 주의.
  - **아직 하지 않은 것**: 실제로 웹 푸시를 발송하는 서버 쪽(Edge Function `send-notification`이 `web-push` 라이브러리로 `device_tokens`의 `platform='web'` 행에 발송)은 아직 없다 — 이번 작업은 구독까지만이다. 자동화 브라우저로는 `isSupported()`/"지원 안 함" 배너/`Capacitor.isNativePlatform()` 분기만 확인했고(실제 OS/브라우저 권한 팝업을 자동화가 띄우면 멈출 위험이 있어 피했다), 실제 `Notification.requestPermission()` → 구독 → `device_tokens` upsert → 로그아웃 시 unsubscribe까지 이어지는 전체 흐름은 사람이 실제 브라우저에서 "알림 켜기"를 눌러 확인해야 한다.
    - **앱 시작 시**: `app.js`가 네이티브+로그인 상태면 `pushNotifications.refreshIfAlreadyGranted()`를 기다리지 않고 부른다 — OS 알림 권한이 이미 허용돼 있으면(이전에 "알림 켜기"를 눌렀던 기기) `register()`를 다시 불러 토큰을 갱신한다(기기 재설치·FCM 토큰 로테이션 대응). 권한이 없는 상태에서는 아무것도 하지 않는다 — 새로 권한을 묻는 건 항상 설정 화면에서 사용자가 직접 눌러야 한다.
    - 실제 브라우저(로그인된 세션, 웹 경로)로 검증: 토글 on/off가 `notification_settings`에 즉시 반영되고 새로고침 후에도 유지됨, "알림 켜기" 클릭 시 모달 문구/버튼 라벨이 요청대로("나중에"/"허용") 뜸, `Notification.permission`을 `denied`/`granted`로 흉내 내 배너가 올바른 문구로 바뀜, `navigator.standalone`을 `false`로 흉내 내 iOS 안내가 denied보다 먼저 뜸, `pushNotifications` 모듈이 웹에서 `isSupported()===false`로 조용히 비활성화되고 `removeDeviceToken()`이 토큰 없이도 에러 없이 끝남 — 전부 확인. **네이티브(Android) 경로 자체는 실제 기기/에뮬레이터에서 아직 검증하지 못했다** — `npx cap sync android`(사용자 본인이 실행)로 플러그인을 네이티브 프로젝트에 반영한 뒤 빌드해서 채널 생성/토큰 upsert/registrationError 배너를 실기기로 확인해야 한다.
