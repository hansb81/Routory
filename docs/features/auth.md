# Auth and Supabase

> CLAUDE.md에서 이동된 상세 내용. 이 영역을 작업하기 전에 먼저 읽을 것.

### Auth and Supabase

- **Client** (`supabaseClient.js`): `index.html` loads supabase-js from the jsDelivr CDN (UMD, `window.supabase`, before all app scripts); `supabaseClient.js` creates the client with the project URL and anon key written in the file and exposes it as `window.TripLog.supabase` (not as a global `supabase`, which stays the library namespace).
  - The anon key is public, so data safety rests entirely on RLS on every table; never put the `service_role` key in the client.
  - The client uses `flowType: "pkce"` on purpose: the default implicit flow returns the OAuth result in the URL hash (`#access_token=...`), which collides with this hash router (`redirectTo` ends in `#/main`, tokens would be appended after it and not parsed, and supabase-js clears `location.hash`). PKCE returns `?code=...#/main`; supabase-js exchanges the code itself and only removes `code`.
  - Connectivity check: `await TripLog.supabase.auth.getSession()` returns `{ data: { session: null }, error: null }` with no network call when nobody is signed in, so it only proves the client exists. To check the URL/key, `GET <SUPABASE_URL>/auth/v1/settings` with the `apikey` header should return 200.
- **Login page** (`loginPage.js`, route `#/login`): three buttons of identical size/font (`.login-btn`, each with its service's logo as inline SVG on the left and its brand color from the `--brand-*` tokens). 구글로 / 카카오로 시작하기 call `supabase.auth.signInWithOAuth({ provider, options: { redirectTo: auth.oauthRedirectTo(), skipBrowserRedirect: auth.isNativeApp() } })`; on the web that's the same as before (this tab navigates to the provider's page, `skipBrowserRedirect` is falsy) and there is no callback page. On native, `skipBrowserRedirect: true` stops `signInWithOAuth` from navigating the app's own WebView — it only returns `{ data: { url } }` — and `signIn()` opens that URL itself with `window.Capacitor.Plugins.Browser.open({ url })` (`@capacitor/browser`, Custom Tabs on Android), a real external browser rather than the embedded WebView; Google specifically returns `disallowed_useragent` (403) for its OAuth page inside an embedded WebView (same restriction that already applied to KakaoTalk's in-app browser, below), so this was a required fix, not just a nice-to-have. The login buttons re-enable right after `Browser.open` resolves (the Custom Tab covers the screen while it's up, so there's no double-submit risk); `auth.js#handleDeepLink` closes that tab once the `routory://auth-callback` redirect comes back (see **Auth and Supabase**). 네이버로 시작하기 doesn't go through Supabase at all — Supabase's built-in provider list has no Naver — so `loginPage.js#naverSignIn` opens Naver's OAuth2.0 authorize URL directly (`https://nid.naver.com/oauth2.0/authorize?response_type=code&client_id=...&redirect_uri=...&state=...`). `client_id` is `TripLogConfig.naverClientId` (`js/config.js`; public by design, same treatment as the Google Maps/Kakao JS keys, but still a placeholder value until the real one from Naver Developers is filled in). `state` is a fresh `util.generateId()` value saved to `sessionStorage` (`triplog.naverOAuthState`) right before the redirect, for the callback page to check. `redirect_uri` is always `${location.origin}/auth/naver-callback` — a real path, not a `#/...` one, because Naver appends `?code=...&state=...` as a query string, and a hash router can't see query params placed before its own `#` fragment. That path is served by the static file `triplog/auth/naver-callback.html` (see the Vercel/`serve.py` rewrite note above), which reads `code`/`state`/`error` from `location.search`, checks `state` against the saved `sessionStorage` value (clearing it either way — one-time use regardless of outcome), and on a match calls the **Edge Function `naver-login`** (see **Server**) for a `hashedToken`, then `supabase.auth.verifyOtp({ type: "email", token_hash: hashedToken })` to actually create the session. This page is outside the SPA bundle (a real path, not a hash route — see above), so it can't use `window.TripLog.supabase`; it loads supabase-js from the same CDN as `index.html` and makes its own client with the same URL/anon key (`detectSessionInUrl: false`, since this page's own `?code=` is Naver's authorization code, not a Supabase PKCE code, and must not be consumed by supabase-js's own URL detection). Any failure (Naver returned `error`, no `code`, `state` mismatch, the Edge Function call failing, or `verifyOtp` failing) redirects to `/#/login?error=<code>&error_description=<msg>` — the same mechanism `auth.js#readCallbackError`/`takeCallbackError()` already use for Google/Kakao failures, so `loginPage.js` shows it with no new error-display code needed. Success redirects to `/#/main`; the session `verifyOtp` created is in `localStorage` by then, so the `TripLog.supabase` client `index.html` creates fresh on that load picks it up immediately (same cross-page-load session sharing the PKCE web flow already relies on), and `app.js`'s existing `auth.takePostLoginPath()` still carries the user on to wherever they were headed before login if that was set. Every origin the app is opened from (`http://localhost:8080`, a phone address, the deployed domain) must be registered as both a "서비스 URL" and a "Callback URL" (`.../auth/naver-callback`) in Naver Developers, same reasoning as the Google Maps referrer list. Naver login refuses to start from `file://` (no origin), same as Google/Kakao.
  - The Google and Kakao providers must be enabled in the Supabase dashboard (Authentication → Providers), and `http://localhost:8080/**` (plus any phone address and the deployed domain) added under Authentication → URL Configuration → Redirect URLs; otherwise the authorize URL returns a raw JSON 400 ("provider is not enabled") or falls back to the Site URL.
  - Kakao note: Supabase always requests the `account_email` scope for Kakao unless its "Allow users without an email" setting takes effect, and a Kakao app without the email consent item fails at Kakao with KOE205 ("설정하지 않은 동의 항목: account_email"). This only shows in a real browser.
- **`auth.js`**: caches the Supabase session (`init()` reads it once at startup, waiting for the `?code=` exchange after an OAuth return, with a 5 s timeout; `onAuthStateChange` keeps it current) so the synchronous router guards can use `isLoggedIn()`. It also provides:
  - `getUserId()`, `getProfile()` (`{ id, name, email, avatarUrl, provider }`, trying several `user_metadata` field names because Google and Kakao differ: `full_name`/`name`/`nickname`/`preferred_username` and `avatar_url`/`picture`/`profile_image`; only http(s) avatar URLs are kept — `mainPage.js`'s account row reads it directly).
  - `takeCallbackError()`: at load `auth.js` grabs any `error`/`error_code`/`error_description` from the return URL (query or hash) or a failed `?code=` exchange from `getSession()`; the login page shows it once, because the router rewrites the URL and the reason would otherwise be lost.
  - `signOut()` (scope `local`, so other devices stay signed in), `onChange`, `savePostLoginPath` / `takePostLoginPath`.
  - **Native app OAuth** (`isNativeApp()`, `oauthRedirectTo()`, `initDeepLinks()`): `isNativeApp()` is `Boolean(window.Capacitor?.isNativePlatform?.())` — `false` on the web build, since it never loads any Capacitor script (nothing to install there; `window.Capacitor` only exists when the native shell injects it). `oauthRedirectTo()` is what `loginPage.js` passes as `redirectTo`: the web's `origin + "/#/main"` unchanged, or `"routory://auth-callback"` on native, because a native OAuth round-trip leaves the app for the system browser and comes back via a URL scheme, not a page reload — `?code=...` in a normal https redirect has nowhere to land. `initDeepLinks()` (called once at module load, not inside `init()`) registers `window.Capacitor.Plugins.App.addListener("appUrlOpen", ...)` for that scheme — the generic per-plugin proxy every Capacitor native app exposes automatically, used directly instead of importing `@capacitor/app`'s JS package, since this project has no bundler (the npm dependency in `mobile/package.json` still matters: `cap sync` reads it to register the plugin's native Kotlin/Swift side). `handleDeepLink(url)` pulls `code` (or `error`/`error_description`) out of the callback URL's query string with `new URL(url).searchParams`, best-effort closes the external browser tab (`Capacitor.Plugins.Browser.close()` — see **Login page**), and calls `supabase.auth.exchangeCodeForSession(code)`; success flows through the same `onAuthStateChange` → `onChange` listeners as the web path (`app.js` then navigates off `#/login`), failure shows a toast (the login page isn't re-rendering to catch it the way `takeCallbackError()` does on the web, since the app never reloaded). This requires `routory://auth-callback` to be added under Supabase → Authentication → URL Configuration → Redirect URLs (same reason `http://localhost:8080/**` is there — Supabase rejects a `redirectTo` it doesn't recognize) — the user adds this by hand, it's not something any file here can express.
- Login is required only when `TripLogConfig.requireLogin` (in `config.js`) is not `false` and the page is served over http(s); set it to `false` if provider setup is broken and the app becomes unreachable (but then nothing can be saved, see **Data**). The main page shows the user's avatar/name and a 로그아웃 button; the SHELL's slide-in menu (`tripShell.js`, shown on my-trip/schedule/budget/wallet/lodging) has the same logout.
