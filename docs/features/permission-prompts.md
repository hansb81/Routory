# Permission prompts (카메라 · 위치)

> CLAUDE.md에서 이동된 상세 내용. 이 영역을 작업하기 전에 먼저 읽을 것.

- **Permission prompts (카메라 · 위치, `permissionPrompt.js`)**: a custom rationale screen shown *before* the real OS permission dialog, on the theory (also common app-store review guidance) that explaining why first raises the grant rate versus an unexplained native popup. Two independent gates:
  - **Camera** (`permissionPrompt.js`'s `askCamera(onAllow)`, a `.modal-overlay`/`.modal-confirm` dialog reusing the same markup as `tripShell.js`'s `MYTRIP-EXIT-CONFIRM`/`accountDeletePage.js`'s confirm dialog — no new CSS): both `flight.js`'s ticket-photo "직접 찍기" and `tripImport.js`'s 사진 tab "직접 찍기" call this before doing anything else; "사진에서 선택" (gallery) on either screen is untouched, since gallery access isn't a camera permission. On native, `askCamera` first calls `@capacitor/camera`'s `checkPermissions()` — if already `"denied"` (e.g. Android "don't ask again"), the dialog shows only "설정에서 권한을 허용해주세요." with the '허용' button hidden, and `onAllow` (the actual `getPhoto`/file-input trigger) is never called, since re-prompting a permanently-denied permission typically doesn't even show the OS dialog again. Otherwise (granted/prompt/unknown, and always on web — there's no standard way to pre-check an `<input capture>`'s permission state) it shows the literal required message ("항공권/여행 정보 촬영을 위해 카메라 권한이 필요합니다.") with '허용'; clicking it calls `onAllow()`, which is what actually triggers the OS prompt.
  - **Location** (`myTripPage.js`'s "공항 이동 교통상황" card — the one real `navigator.geolocation` call site in the app; there's no separate "지도" feature that requests location today): instead of a modal, the card's own body is reused as the prompt surface (`permissionBodyHtml`, new CSS `.mytrip-card-actions` wrapping existing `.btn-cancel`/`.btn-save`), since this card hydrates automatically on page load rather than from a click — popping a modal unprompted would be worse UX than a modal shown right after an explicit button press. `checkGeoPermission()` (`navigator.permissions.query({name:"geolocation"})`, `null` if unsupported e.g. older Safari) decides the branch: `"granted"` skips the rationale entirely and calls `getCurrentPosition()` directly (no OS prompt will appear, so there's nothing to explain); `"denied"` replaces the card body with "설정에서 권한을 허용해주세요." and stops, same reasoning as the camera case; anything else (`"prompt"` or unknown) shows the literal required message ("주변 장소 검색과 교통정보 안내를 위해 위치정보를 사용합니다.") with '허용'/'나중에' — '허용' calls `getCurrentPosition()` (now the real prompt appears), '나중에' removes the card for this render (same as the pre-existing "hide on failure" rule for this card, see **My-trip page**).
  - Both gates degrade to "just show the rationale" when permission state can't be determined, rather than guessing `"denied"` — treating "unknown" as "never asked" is the safer default (worst case: one unnecessary rationale screen) versus the alternative (silently skipping a prompt the user never actually got to answer).
  - **Notification** (PRD v11 "푸시 알림 시스템"; `permissionPrompt.js`'s `askNotification(onAllow)` + `notificationPermissionState()`; caller is `commonPages.js`'s 설정 화면 "알림" 섹션, see **Common pages**): same `.modal-overlay`/`.modal-confirm` structure as camera but its own overlay instance (`dataset.alias = "NOTIFICATION-PERMISSION-CONFIRM"`) and its own copy — title "알림을 받아보세요", body "출발 전날과 일정 시작 전, 여행 멤버 변화를 알려드리려면 알림 권한이 필요해요.", buttons **"나중에"/"허용"** (camera's equivalent buttons say "닫기"/"허용" — different label on request). `notificationPermissionState()` checks `@capacitor/push-notifications`' `checkPermissions()` first (native: `'granted'|'denied'|'prompt'`), falling back to the web `Notification.permission` (`'granted'|'denied'|'default'`), `null` if neither exists.
    - Unlike camera's denied path (which still opens the modal, just hides the 허용 button and shows the denial text inside it), **denied here never opens the modal at all** — the settings page checks `notificationPermissionState()` itself before deciding whether to render the "알림 켜기" button or an inline "설정에서 알림 권한을 허용해주세요." notice, so `askNotification` only ever gets called from the "아직 묻지 않음/모름" state. Same reasoning for iOS Safari non-standalone (`navigator.standalone === false`, a property that only exists in iOS Safari) — the settings page shows "iPhone에서는 홈 화면에 추가한 뒤에 알림을 받을 수 있어요." instead of a button, checked *before* the permission-state check so it wins even if the OS-level state happens to be `denied` too. A third no-button case exists on web only: if `webPush.isSupported()` is `false` (no `ServiceWorker`/`PushManager` at all — old browsers), the banner shows "이 브라우저에서는 알림을 지원하지 않아요." instead, checked before the permission-state query.
    - `askNotification`'s `onAllow` → `commonPages.js`'s `requestNotificationPermission(el)`, which branches on `auth.isNativeApp()`: native → `window.TripLog.pushNotifications.requestAndRegister()` (`triplog/js/pushNotifications.js`): `PushNotifications.requestPermissions()` first, and only if that comes back `"granted"` does it call `register()` (creates the `"routory-default"` notification channel, then asks FCM for a token). The `'registration'` event's token gets upserted into `device_tokens` (`platform:'android'`); `'registrationError'` is logged and surfaces as "알림 등록에 실패했어요." in the settings banner (see **Common pages**) — this can happen even though the OS permission was granted (no Google Play Services, bad `google-services.json`, network). Web → `window.TripLog.webPush.subscribe()` (`triplog/js/webPush.js`, see **Common pages**'s **Web Push** section for the full flow): `Notification.requestPermission()` first, and only if `"granted"` does it register `/sw.js` and call `pushManager.subscribe(...)`, upserting the resulting subscription into `device_tokens` (`platform:'web'`). `webPush.isSupported()` checks `!auth.isNativeApp()` *first* (요청 4번) so this entire path is a no-op inside the native app's webview even though `ServiceWorker`/`PushManager` may technically exist there — native always goes through FCM instead.
