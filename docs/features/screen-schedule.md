# Schedule page (일정 화면)

> CLAUDE.md에서 이동된 상세 내용. 이 영역을 작업하기 전에 먼저 읽을 것.

- **Schedule page**: reuses the header/menu/timeline in `index.html`; timeline rendering is in `app.js`, the add/edit/delete form in `schedule.js` (`openForm(item, { date, hideDate })` is the single entry to the plain-item form — see **Schedule item form (SCHEDULE-FORM)** below).
  - The header has no back button of its own anymore (removed once the SHELL's top bar added its own X) — `여행중`/닫기(X) on the SHELL are the only ways back to my-trip/main from here now.
  - **Header** (`#trip-title` + `#trip-dates`, `app.js#renderTripHeader`): the trip title, then its date range below at 12px (`"2026.11.14~2026.11.19"`, built by `app.js#tripDateRange` from `trip.startDate`/`endDate` with `-` swapped for `.` and no spaces around `~`, same `dotted()` trick as `mainPage.js#formatPeriod`). The title is plain text now — it used to be clickable and open the trip-setup wizard to edit the trip's city/dates (`app.js#openTripSetup`); that was removed, so it has no `cursor: pointer`/hover state and nothing happens on click (see **Trip setup wizard**'s note on the now-missing edit entry point).
  - **Quick menu** under the header now holds 교통편 and 숙소 (`QUICK-MENU` alias "빠른 메뉴 (교통편 · 숙소)"), right-aligned (`.quick-menu { justify-content: flex-end }`) — 가계부/여행지갑 moved up to the SHELL's bottom tab bar (`MYTRIP-BOTTOMTABS`, see **Trip shell (SHELL)**'s "Bottom tabs" note) and no longer have buttons here; 숙소 was briefly moved there too but came back to sit next to 교통편 (still navigates to `#/lodging/:id` for the current trip, same as before — see **Lodging**). Both buttons share `.quick-menu-btn` (a white `--surface` pill with `box-shadow: var(--shadow-sm)`, accent border/text on hover); 교통편 additionally carries `.quick-transport-trigger` for its `▼` caret (`.quick-transport-trigger-caret`, next to the label — no icon/emoji in the button itself) that rotates 180° and turns accent-colored while the dropdown is open (`[aria-expanded="true"]`, the same attribute `openTransportMenu`/`closeTransportMenu` already toggled).
  - **Transport dropdown (quick menu, `app.js#initQuickMenu`/`openTransportMenu`)**: clicking 교통편 no longer opens `flight.js`'s modal directly — it toggles a small dropdown (`.quick-transport-list`) anchored below the button itself, not a centered popup. Only two options now: 항공 calls `flight.openForm()`; 기타 calls `transportForm.openForm()`. The list is a `document.body`-appended `<ul>` positioned with `position: fixed` from `triggerBtn.getBoundingClientRect()` — deliberately not nested inside `.app-top` (a `position: sticky` ancestor, which would trap it inside that stacking context and stop it floating above the timeline below). It closes on an outside click, `Escape`, any `scroll` (a capture-phase `document` listener, since nested-container `scroll` events don't bubble), and via `app.js#closeAllOverlays` (already called on `router.onLeave("schedule", …)`) so it can't survive a route change. `flight.js` no longer has any transport-picking UI of its own — see **Flight**. Fixed-route, sub-categorized transport (기차/버스/선박) used to be separate 항목 in this dropdown, each showing `ui.showComingSoon`; they're gone from here now and live as a `카테고리` picker inside the 기타 form instead — see **Transport (기타 교통편)**.


- **Schedule item form (SCHEDULE-FORM, `schedule.js`)**: the old "장소 추가"/"메모 추가" pair of small popups (each opened by its own `.day-add-btn`) is gone — `app.js#renderDaySection` now renders a single full-width `.day-add-btn` labelled "일정 추가" per Day (`flex: 1` fills the space the two old buttons + gap used to take), and both `schedule.js#bindTimelineEvents`'s click on that button and a click on an existing plain/lodging timeline card open the **same** full-screen form via `openForm(item, { date, hideDate })` (item `null` = add). Unlike every other modal in the app (`expenseForm.js`, `walletForm.js`, …) this one is built once by `ensureForm()` and appended to `document.body` the same way, but is full-screen like `walletViewer.js`/`.wallet-viewer-overlay` (`.schedule-form-overlay` clears `.modal-overlay`'s padding/centering) instead of a capped 420px `.modal` — index.html no longer has any of this form's markup (`#modal-overlay`/`#field-*` are gone; only the small delete-confirm `#confirm-overlay` stays static, since `schedule.js` still references it directly). `.schedule-form-sheet` caps and centers itself with `max-width: var(--content-max); margin-inline: auto;`, the same rule every other "full screen" page uses (`.budget-shell`, `.wallet-shell`, `.lodging-shell`, `.wallet-viewer`) — so on a wide window this form is the same card width as the schedule screen it was opened from, not edge-to-edge (an earlier pass tried edge-to-edge, reasoning that the capped/centered look reads as "a popup with gray margins" on a wide window; that was superseded — matching the schedule screen's own width won out). `.schedule-form-header`/`.schedule-form-footer` (and `.app-top`, `.day-map-handle`) use `--surface-blue` (`#d6e4fb`, see **Color policy: pastel**), one step darker than the `--page-bg-blue` (`#e8f1ff`) body behind them, so the header/footer/quick-menu bar read as a distinct surface rather than blending into the page.
  - **Day + time, one row** (`.schedule-form-daytime`): no more `<input type="date">`/calendar — the date is a toggle dropdown exactly like `expenseForm.js`'s day picker (`.schedule-day-picker`/`-trigger`/`-list`, built from `util.getTripDays(trip)`), except the trigger shows the raw date (`"2026-11-14"`) instead of a "Day N" label (the list's options do say "Day N · M.D(요일)"); there's no separate "날짜" text label any more, since the trigger itself *is* the control. `시간` (a plain `<input type="time">`) sits to the right of the same row via `margin-left: auto` on `.schedule-time-group`. Lodging items lock the day (`state.hideDate`, from `item.lodging` truthy) by disabling the trigger (`els.dayTrigger.disabled`) — time stays editable either way.
  - **장소 is now a live search box, not free text + a separate "지도에서 선택" button** (that button/`mapPicker.js` flow is gone from this form — see the note below). Focusing it lazily creates a small inline Google map (`showPlaceMap`, `.schedule-place-map-wrap`, hidden until first focus) between the input and the memo field — DOM order alone pushes 메모 down, no layout math needed. Typing debounces (400ms) into `gmaps.searchText` biased to the map's current center and renders results in `.schedule-place-results` (search-only, **no** "주변 추천" list); picking a result or clicking a blank spot on the map (reverse-geocoded) sets the place text + hidden `lat`/`lng` fields and drops/moves a marker. Enter in the field is suppressed (`e.preventDefault()`) so it can't accidentally submit the form while searching.
  - **사진**: unchanged add/remove flow (`saveImage`/`deleteImage` via `images.js`), except tapping a thumbnail's image (not its ✕) now opens a small full-screen viewer (`ensurePhotoViewer`, `.schedule-photo-viewer-overlay`, a second `document.body`-appended overlay, `--z-alert` so it sits above the form) showing that one photo via `getImageUrl` — closed by its own ✕, clicking the dim background, or Escape.
  - **취소/삭제/저장 stay in a fixed `.schedule-form-footer`** (flex-shrink: 0 sibling of the scrolling `.schedule-form-body`, not `position: fixed`) so they never move even while the inline map is open and the body is scrolled.
  - **Validation**: place, memo and photos are all optional individually now — the rule is "at least one of the three" (`!place && !memo && images.length === 0`), not the old "place or memo".
  - `mapPicker.js` (the old separate full-screen "지도에서 장소 선택" picker, `#map-modal-overlay`) and its CSS (`[MAP-PICKER]` section, `--z-map` token) are **no longer called from anywhere** — `schedule.js` was its only caller. Left in place rather than deleted (small, self-contained, no other file references it), but it's dead code now; delete it (and `--z-map`) if nothing else ever needs a standalone map picker.


- **Timeline reorder & swipe-delete** (`timelineDrag.js`, wired up in `app.js#initTimelineDrag`): only on "일반" cards — a plain place/memo item, `!item.flight && !item.transport && !item.lodging` (`app.js#renderItemCard` marks these `data-plain="1"` and wraps them in `.timeline-item-wrap` + a `.item-delete-bg`; flights, 기타 교통편 and lodging render unwrapped, `data-plain="0"`, and keep their own existing ways to sort (departure time / always-last) and delete (flight's own detail screen; 기타 교통편 via its own form's 삭제 button, see **Transport (기타 교통편)**; lodging via the generic edit form's 삭제 button)). The two gestures start from different hit targets, so there's no ambiguity to resolve (no long-press, no timer):
  - **Drag handle to reorder, including across Days**: a dedicated `.item-drag-handle` (3-line/hamburger icon, same SVG path as `tripShell.js`'s ☰) sits at the card's right edge (plain cards get `padding-right: 40px` to leave room for it) — pointerdown *there* starts a drag immediately, no hold required. The card's `.timeline-item-wrap` switches to `position: fixed` (needs `z-index: var(--z-modal)` to paint above the sticky `.app-top`'s `z-index: 20`) and follows the pointer's Y only; a placeholder holds its slot. Each Day's `.date-items` is now **always rendered** even with zero items (`data-date="<dateKey>"`, `app.js#renderDaySection`/`renderDateItems`; `.date-items:empty { margin-top: 0 }` keeps this invisible when not dragging) so there's always a drop target — `findDayContainerAt(clientY)` (nearest-by-distance over all `.date-items` in the timeline) picks which Day the pointer is currently over, and moving into a different one re-parents both the placeholder and the floating wrap into it (`#timeline.is-reordering` shows every empty Day as a dashed box; the current one gets `.date-items--drop-target`'s accent outline). Within whichever Day is current, crossing a sibling's midpoint moves the placeholder past it with a lightweight FLIP animation (measure → inverse `translateY` → transition to none). Dropping puts the wrap back at the placeholder's spot, reads that Day's final `.timeline-item[data-plain="1"]` order off the DOM, and calls `onReorder(orderedIds, dateChange)` — `dateChange` is `{ id, date }` only when the Day actually changed, `null` for a same-Day reorder. `app.js` turns that into `storage.reorderItems(orderedIds, dateChange && { [dateChange.id]: { date: dateChange.date } })`, which `Promise.all`s one `updateItem` per id (`sortOrder = index`, plus `date` for the moved one) and always re-renders the timeline after, success or failure — cheap since a Day's item count is small, and it's what makes the map's numbering, the distance labels, and the (possibly new) Day grouping all recompute correctly. `.item-distance` labels are hidden (not removed) for the duration via `#timeline.is-reordering` since they'd be stale mid-drag.
  - **Swipe left to delete**: unchanged — pointerdown anywhere on the card *except* the handle, then >10px mostly-horizontal movement, commits to this. The card's own `transform: translateX()` tracks the pointer 1:1 (no CSS transition while live); the red `.item-delete-bg` need not be resized — it's simply revealed as the opaque card slides left off of it. Crossing 50% of the card's width auto-deletes *during the drag itself* (doesn't wait for release, matching the "스와이프 한 만큼" spec) — the card animates fully off-screen, then `onDelete(id)` → `app.js` → `schedule.js#deleteItemById` (extracted from the old delete-confirm flow so the modal's 삭제 button and this share one path: delete row → clean up its photos → re-render). Releasing before 50% snaps back (`transform` reset with a transition). Either way a `g.deleted`-style guard (see the file) stops a stray leftover pointermove from double-firing the delete.
  - **`.item-delete-bg` is inset 3px from `.timeline-item-wrap`, not `inset: 0`.** It used to be flush with the wrap, which is itself clipped to the card's exact box via `overflow: hidden` — geometrically an exact 0px gap (checked with `getBoundingClientRect`, confirmed identical on all four sides), but at rest this still showed a hairline red fringe along the card's rounded edges (a Chromium `overflow: hidden` + `border-radius` + `box-shadow` anti-aliasing artifact, not a layout bug — the shadow has nowhere valid to render since the clip is flush with the card's border box, so a sub-pixel sliver of it blends against the red instead of disappearing cleanly). The 3px inset (plus its own `border-radius: calc(var(--radius-md) - 3px)`) gives a real multi-pixel buffer so nothing red can ever touch that clip boundary; the reveal during an actual swipe starts imperceptibly later (3px) and isn't noticeable. If this card ever needs to sit flush edge-to-edge with `.item-delete-bg` again, re-derive the inset rather than reverting to 0.
  - **Mouse-specific gotcha this uncovered**: unlike touch, a mouse fires a normal `click` on mouseup as long as mousedown/mouseup share the same target — *regardless of how far the pointer moved in between* — so finishing either gesture with a mouse would otherwise immediately reopen the edit modal on the same card. Fixed by adding a one-shot, capture-phase `click` swallower on the card the moment either gesture commits (`suppressNextClick`); this is why a plain tap (no committed gesture) still opens the edit modal exactly as before.
  - **`schedule_items.sort_order`** (008_schedule_item_order.sql, additive/optional) is what makes a persisted reorder survive a reload or reach other members — without running it, dragging still *feels* like it works (the live DOM animation has no server dependency) but the drop always fails (`storage.reorderItems` → `updateItem` 42703/PGRST204 → the standard "서버 테이블 구조가 앱과 달라요" toast) and the subsequent re-render snaps back to server order — this now also blocks a cross-Day move's `date` change, since it rides in the same `updateItem` patch as `sortOrder` for the moved item (one PostgREST request, so a missing column fails the whole patch, not just the `sortOrder` half). Reading/adding/editing items is unaffected either way (see **Item types**'s `sortOrder` note) — this migration only gates the reorder *feature*, not the schedule screen in general. (This migration has since been run against the project's Supabase instance — cross-Day drags now persist for real, verified end to end.)
