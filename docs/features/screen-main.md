# Main page / Trip setup wizard

> CLAUDE.md에서 이동된 상세 내용. 이 영역을 작업하기 전에 먼저 읽을 것.

- **Main page** (`mainPage.js`): placeholders for flights/news, then the trip cards from `getAllTrips()` (upcoming first, past last, D-day via `util.ddayLabel`). Cards are plain links to `#/schedule/:id` (selecting a trip goes straight to its schedule, not the my-trip screen).
  - The list is refreshed from the server on every enter; it shows a loading line before the first load, a retry button if loading fails, and an empty state with no trips.
  - "새 여행 만들기" and "+ 새 여행" open the same 2-step wizard as the schedule page's trip settings (`tripSetup.open({ trip: null, canClose: true, onComplete })`). `onComplete` calls `storage.createTrip` with the title `"<city> 여행"`, the `cityId` (so the flight and lodging features recognize the city) and the dates (async; a failure only shows a toast), then re-renders the list and shows a toast (the user stays on the main page).
  - There is no free-text destination or title field: only cities listed in `destinations.js` can be chosen, so add new places there.
  - "가져오기"/"여행 가져오기" (next to "새 여행 만들기"/"+ 새 여행" in both the empty state and the trips list) open `tripImport.js`'s modal with `mode: "create"` — see **Trip import** below.
  - **MAIN-MENU** (the right slide-in menu opened from the account row's ☰ button): the panel head has no "메뉴" text any more — just three icons, right-aligned (`justify-content: flex-end`): 알림(🔔)/설정(⚙, both from `commonPages.js`'s shared `ICONS`, navigating to `#/notifications`/`#/settings` — see **Common pages (알림 · 설정)**) then 닫기(✕). Below that, the existing profile row (`menuProfileHtml`, name + avatar) is unchanged. The `<ul>` list has `여행 가져오기` then `지난 여행` (below it) — 설정 (the old coming-soon dummy) and 로그아웃 were removed from here (not deleted from the app, just no longer shown in this menu — they're slated to move elsewhere, not yet decided where); `mainPage.js` no longer has a `logout()` function since nothing calls it any more.
  - **지난 여행 (`#/past-trips`)**: "내 여행" now only lists trips that haven't ended (`sortUpcoming`, `isPastTrip` = `daysUntil(endDate||startDate) < 0`) — a trip whose schedule has finished no longer shows on the main page at all, it only shows here. Opened from MAIN-MENU's "지난 여행" item (`router.navigate(router.buildPath("past-trips"))`). It's a plain `.page` (no SHELL), styled like the 알림/설정 screens in `commonPages.js`: same `.simple-page-header`/`.simple-page-title` (back button + title, `history.back()`), same `body.has-simple-page-bg` background (`--surface-blue`, `#d6e4fb` — reused as-is, no new background class) toggled on `router.onEnter`/`onLeave`. The trip list reuses `tripCardHtml`/`.trip-cards` as-is (same card look, D-day badge already renders the "지난" `--past` variant) sorted most-recently-ended-first (`sortPast`); empty state is `<p class="simple-page-empty">지난 여행이 없습니다.</p>`. No swipe-to-delete here (not wired up — deleting a past trip isn't supported from this screen yet). `hydrateCardAvatars` was generalized to take an explicit root element (`hydrateCardAvatars(trips, el)`) so both this screen and the main page's card grid can hydrate member avatars independently; `storage.onChange` re-renders whichever of the two (`pageEl`/`pastPageEl`) is currently visible.

- **Trip setup wizard** (`tripSetup.js` + `destinations.js`): step 1 picks a city, step 2 picks dates on a custom calendar. `tripSetup.js` only collects data and calls back. `open()` takes `trip: null`, `onComplete` calling `storage.createTrip` — the schedule header's title used to open the same wizard with `trip: existing` to edit an already-created trip's city/dates (`app.js#openTripSetup`/`completeTripSetup`), but that entry point was removed (see **Schedule page**), so there is currently no way to change an existing trip's destination or dates from the app; re-add it (e.g. behind the SHELL's still-dummy `여행 설정` menu item) if that's needed again. The trip title is auto-generated as "<city> 여행" unless the user has a custom title.
  - `open()`'s third caller — besides `mainPage.js`'s "새 여행 만들기"/"+ 새 여행" — is now `travelFeed.js`'s "어디로 떠나볼까요" cards (see above), which pass an optional `preset: { destinationId }` (jump straight to step 2 via `resolveCity(city, { autoAdvance: true })`, a parameter this `resolveCity` didn't take before) or `preset: { query }` (prefill the search box and let `scheduleSearch` run, same as if the user had typed it — no auto-select, since the city name alone can be ambiguous). Both are additive; existing callers that don't pass `preset` are unaffected.
  - **Tabs (PRD v12 - 여행지 확장·도시 검색), 2단 구조로 되돌림**: 1차 탭(`#region-tabs`, 기존 `.tab-row`, 2개뿐이라 스크롤 없음) — 해외/국내, **해외가 먼저**(요청대로). 해외를 고르면 2차 탭(`#group-tabs`, `.tab-row--sub`의 `overflow-x:auto` 가로 스크롤 필 스타일)이 나타나 10개 지역(일본/동남아/중국/대만/유럽/북미/오세아니아/중동/중미·카리브/남미)을 보여준다 — 국내를 고르면 2차 탭은 숨겨지고 국내 8개 도시가 바로 보인다(기존 그대로, `destinations.js`의 하드코딩 `DOMESTIC_CITIES`). 2차 탭 선택 시 `scrollIntoView({inline:'center'})`로 보이는 곳까지 스크롤(터치·마우스 공통, 별 다른 처리 불필요). 기본 선택은 해외 + `japan`(가장 많이 쓰는 지역 - 임의 선택, 명시적 지시는 아니었음).
  - **Overseas presets come from the `destinations` table** (`source='preset'`, `014_destinations.sql`/`016_destinations_preset_coords.sql`), not a code constant any more — `destinations.js#loadPresets()` fetches once (`supabase.from('destinations')...`), caches in memory, and is kicked off as soon as the wizard opens (not lazily per-tab) so switching tabs rarely shows a loading state. Loading → 5 skeleton rows (`.pick-item--skeleton`, opacity-pulse like `flight-ticket-pulse`); load failure → `.pick-empty--error` with a "다시 불러오기" button (`destinations.js#retryLoadPresets`, same `empty-state`-with-retry shape as the main trips list).
  - **Picking an overseas city calls `search-destination`'s `action:'select'`** (`tripSetup.js#resolveCity`, `supabase.functions.invoke`) to confirm lat/lng/IANA timezone before the city can be chosen — 국내 cities never call this (unchanged toggle-select). Every one of the 70 preset cities already has `resolved_at` set (`016_...sql`), so in practice this call returns immediately with no external API round-trip; it only does real work for a city a user picks that was never resolved before. While resolving, that row's button shows "확인 중…" and is disabled (other rows are also inert until it settles — one resolution in flight at a time, tracked by a generation counter so a stale response from a since-abandoned pick can't clobber a newer selection); on failure the row switches to an inline "도시 정보를 불러오지 못했어요. 다시 시도해 주세요" + "다시 시도" button and the wizard does not advance (the footer only appears once a city is actually selected, so step 2/완료 is unreachable while unresolved or errored). A resolved pick's `destinations` row (`{name_ko, name_en, country_code, country_name_ko, lat, lng, timezone, ...}`) is kept in `state.resolvedCity` and is what `onComplete`'s payload (`destinationId`, `timezone`, plus the usual `cityId:null`/`destination` string) is built from — `cityId` stays `null` for these (same "unknown to `destinations.js`'s old constants" precedent `tripImportPreview.js` already set — only costs the flight/lodging airport-suggestion feature, not a hard failure).
  - `storage.js#createTrip`/`saveTrip` now also accept/persist `destinationId`/`timezone`/`lat`/`lng`/`currency` (`trips.destination_id` from `014_destinations.sql`, `timezone` from `017_trips_timezone.sql`, `lat`/`lng`/`currency` from `018_trips_destination_fields.sql`) alongside the existing `destination`/`cityId` string fields — all written together so nothing that still reads the old string fields breaks. 국내 trips and anything made before this change keep all five columns `null`. These five feed `myTripPage.js`'s 환율/날씨 카드와 `expenseForm.js`'s currency picker directly once `destinationId` is set — see **My-trip page** and **Budget page** for the `destinationId`-present-vs-absent branching each of those does (an audit found they'd otherwise keep re-deriving currency/coordinates from the `destination` string even when the real values were already known).
  - **City images**: fetched at runtime from Wikipedia's summary API (free/open-licensed images only — Wikipedia/Commons doesn't host non-free photos for this kind of content) using a `wiki` title. 국내: fixed titles set by hand. 해외 프리셋(이번에 추가): `destinations.js#presetCityFromRow`가 `name_en`(공백→밑줄)을 위키 제목으로 그대로 추정해서 쓴다 — DB에 위키 제목 컬럼을 새로 안 두려고 고른 방법이라, 동명이인 도시(예: 영문명이 흔한 도시)는 틀린 사진이 붙거나 못 찾을 수 있다; 실패하면 조용히 기본 핀 아이콘(📍)으로 남는다(`fetchCityImage`의 기존 실패 처리 그대로, 에러로 다루지 않음).
  - **Free-text search** (PRD v12 3번): typing in `#city-search` hides the tabs and shows search results instead (clearing it goes back to tabs — same `isSearching()` gate the tab-only list already used). Two layers, merged: (1) **local** — a synchronous, no-network substring match over 국내's `DOMESTIC_CITIES` and whatever overseas preset regions are already loaded (`tripSetup.js#localSearchEntries`) — this is what makes 국내 cities (서울/부산/제주/...) show up in search at all, since `destinations` has no domestic rows; it's also *why* 국내 never duplicates with a remote hit — local results always win and `mergeSearchEntries` drops any remote result with the same (`name_ko`,`country_name_ko`). (2) **remote** — `search-destination`'s `action:'search'`, called 300ms after typing stops (`scheduleSearch`/`runSearch`), skipped entirely while an IME composition is in progress (`compositionstart`/`compositionend` tracking — a plain `input` listener alone isn't enough because `compositionend` can fire without a trailing `input` event in some browsers) and for queries shorter than the server's own minimum (한글 1자/그 외 2자 — checked client-side too, so under-length queries never even reach the function). Per-query results are cached in a module-level `Map` for the rest of the page session (never cleared on wizard re-open) so retyping the same thing doesn't re-call the function.
  - **No real request cancellation** — `supabase-js`'s `functions.invoke` doesn't expose an abort signal, so a stale in-flight search isn't literally killed when a newer one starts. Instead `runSearch` always writes its result into the cache (so that query is cached correctly even if the user has since moved on) but only calls `render()` if `state.query` still equals the query that request was for — so an old response can never clobber what's on screen, which is the actual behavior the "cancel the old request" instruction was after.
  - Clicking a result dispatches by `entry.kind`: `"domestic"` toggles `state.cityId` directly (no network call, identical to the tab flow); `"local-preset"` (an already-loaded overseas preset matched locally) and `"remote"` (straight from the Edge Function's response) both go through `resolveSearchResult`, which builds the `select` payload as `destinationId` (if the result already carries `destinations.id` — preset/previously-saved-user rows) → `placeId` (Google-sourced fresh hits) → `nameEn`+`countryCode` (Open-Meteo-sourced fresh hits) in that priority order. `resolveSearchResult` shares `cityResolveState`/`resolveGen` with the tab flow's `resolveCity` (one shared "확인 중…"/error-with-retry state, keyed by a stable `resultKeyFor(entry)` so the right row keeps showing it even after the list re-renders) and a shared `state.resolvedKey` so a row stays "선택됨" after success even though its pre-resolution key (e.g. a `place_id`) and post-resolution key (now has a real `destinations.id`) differ.
  - States per instruction 6: under the server's minimum length → inline guidance text; nothing cached yet for that query → "검색하는 중이에요…" (pulsing text, `.pick-empty--loading`/`.pick-skeleton-pulse` keyframe reused); zero merged results after the remote call finished → "다른 이름으로 검색해 보세요"; `degraded:true` → a toast ("검색 연결이 불안정해요. 추천 도시만 보여드려요"), shown once per completed fetch (naturally not per-render, since fetches are cache-gated to once per distinct query). Preset-tier rows (local or `is_preset:true` remote) get a small "추천" badge (`.pick-badge`); everything else doesn't.
  - Mobile/keyboard (instruction 8): `#city-search` is `position: sticky; top: 0` inside `.wizard-body` (not the shared `.search-input` class, to avoid affecting the flight/invite screens that reuse it) so it stays visible above the scrolling result list; result reachability under an on-screen keyboard relies on the wizard's existing `dvh`-sized modal + `.wizard-body`'s `overflow-y: auto` (same mechanism `mobile-capacitor.md`'s safe-area notes describe elsewhere) rather than any new Capacitor keyboard-resize config — **not verified on a real device/Capacitor build**, only in a desktop browser.
  - **Two CSS bugfixes found after the tab rework**: (1) `.tab-row--sub`'s horizontal scrollbar (visible on desktop Chrome/Windows) sat flush against the pill buttons' bottom edge, visually overlapping them — fixed with `padding-bottom: var(--space-2)` inside the scroll container so the scrollbar renders with a gap below the buttons instead. (2) The 도시 선택 "선택됨" button text was invisible — `#trip-modal-overlay .pick-btn` (the wizard's pastel-color override, `color: var(--dday-pastel-bg)`) out-specificities the base `.pick-btn--selected { color: #fff }` rule since it's ID-scoped, and the wizard's own `#trip-modal-overlay .pick-btn--selected` only overrode `background` (not `color`) — so a selected button ended up with pastel-blue text on a pastel-blue background. Fixed by adding `color: #ffffff` to that scoped `--selected` rule.
