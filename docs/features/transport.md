# Transport (기타 교통편: 기차 · 버스 · 선박)

> CLAUDE.md에서 이동된 상세 내용. 이 영역을 작업하기 전에 먼저 읽을 것.

- **`transportForm.js`**: 일정 화면의 빠른 메뉴(교통편) 드롭다운에서 "기타"를 고르면 열리는 작은 모달(`.modal`, 420px 캡 — `flight.js`의 전체화면 단계형 창과 다르다). 기차/버스/선박은 더 이상 그 드롭다운의 개별 항목이 아니다 — 이 창의 `카테고리` 칩(기차/버스/선박/기타) 중 하나로 들어갔다. **사진 인식(OCR) 과정이 전혀 없다** — `flight.js`의 항공권 사진 분석과 다르게, 전부 직접 입력이다.
- **흐름 (한 화면, 위에서부터 순서대로)**: 날짜(Day) 드롭다운 → 카테고리(기차/버스/선박/기타) 칩 → 출발지(글자 입력) + 출발 시간 → 도착지(글자 입력) + 도착 시간 → 좌석(선택 입력, 비워도 된다) → 등록. 날짜/카테고리/출발지/출발시간/도착지/도착시간은 모두 필수고, 좌석만 선택이다 (`handleSubmit`의 검증 순서가 이 순서와 같다).
  - 날짜 드롭다운은 `expenseForm.js`의 `.expense-day-*` 토글형 목록과 똑같은 모양(`.transport-day-*`로 클래스만 새로 뗐다) — `util.getTripDays(trip)`에서 Day 목록을 만든다. 여행 기간이 없으면(Day가 0개) `openForm`이 그냥 열리지 않는다(`flight.openForm`과 같은 가드).
  - 카테고리 칩도 `expenseForm.js`의 `.expense-category-*`(원형 아이콘 + 아래 라벨, 가로 스크롤)와 같은 모양을 `.transport-category-*`로 옮겼다. 네 가지: 🚆 기차 / 🚌 버스 / 🚢 선박 / 📌 기타 (`TRANSPORT_META`).
  - 출발지/도착지는 `schedule.js`의 장소 칸과 같은 방식으로 지도에서 찾을 수 있다 — 입력칸에 포커스하면 그 바로 아래에 작은 지도가 나타나고(`createPlaceField`, 두 칸 각각 독립된 지도·검색 상태를 가진다), 입력하면 디바운스 후 `gmaps.searchText`로 검색해 결과 목록을 보여주거나, 지도를 직접 눌러 역지오코딩(`gmaps.reverseGeocode`)으로 이름을 채울 수 있다. 다만 **좌표(lat/lng)는 저장하지 않는다** — `item.transport`은 이름만 쓴다(역/터미널 이름 같은 글자만 저장). 지도는 어디까지나 이름을 "찾는" 보조 수단이라, 검색 결과가 없으면(`"...에 맞는 장소를 찾지 못했어요. 직접 입력해도 돼요."`) 그냥 입력칸에 직접 타이핑하면 그 글자 그대로 저장된다 — 선택을 강제하지 않는다. 지도 중심은 여행지(`trip.destination`)를 지오코딩한 좌표, 실패하면 서울 기본값.
- **데이터 모델**: `item.transport = { category, depPlace, depTime, arrPlace, arrTime, seat }` — `item.flight`/`item.lodging`과 같은 자리(서버 컬럼 `schedule_items.transport`, jsonb, `013_transport_items.sql`). `category`는 `"train"|"bus"|"ship"|"etc"` 중 하나, `seat`는 비워두면 빈 문자열(값이 있으면 요약문에 ` · <seat>`로 붙는다).
  - `storage.js#addItem`은 `transport` 값이 있을 때만 `row.transport` 키를 넣는다 (`flight`/`lodging`과 달리 처음부터 있던 컬럼이 아니라서, 마이그레이션을 아직 안 돌린 서버에서 일반 일정 추가가 깨지지 않게 하려고 — 008의 `sort_order`와 같은 이유, 다만 여기는 "값이 없으면 키 자체를 안 보낸다"는 더 단순한 방식이다. `sort_order`처럼 빠진 컬럼에 대해 한 번 더 재시도하지는 않는다 - 기타 교통편은 재시도해도 저장할 데이터(transport 자체)가 없으면 의미가 없기 때문). 마이그레이션 전에 "기타" 교통편을 추가/수정하려 하면 다른 신규 컬럼 기능과 같은 표준 실패 메시지("서버 테이블 구조가 앱과 달라요…")가 뜬다 — 일반 일정·항공편 추가는 전혀 영향받지 않는다.
- **추가/수정 겸용**: `openForm(item)` — `item`을 넘기면 그 값으로 채워진 수정 폼(`schedule.js`의 일반 일정 폼과 같은 패턴), 안 넘기면 새 등록 폼. `schedule.js#bindTimelineEvents`가 타임라인 카드 클릭을 라우팅한다: `item.flight` → `flight.openDetail`, `item.transport` → `transportForm.openForm(item)`, 나머지 → 일반 폼.
- **삭제**: 별도 확인 팝업이 없다 — `flight.js`의 상세 창과 같은 "두 번 눌러야 삭제"(처음 누르면 버튼이 "정말 삭제"로 바뀌고 `.btn-danger`가 붙는다, 두 번째에 실제로 지운다) 방식.
- **타임라인 표시** (`app.js#renderItemCard`): 아이콘은 카테고리별(`transportForm.iconFor`), 한 줄 요약은 `transportForm.summary` — `"<출발지> <출발시간> ~ <도착지> <도착시간>[ · <좌석>]"`. 항공편과 같은 취급: 요약문에 시간이 이미 들어 있어서 `item.time`은 따로 안 보여주고(`timeLabel`), 드래그 재정렬·스와이프 삭제 대상도 아니다(`isPlain = !item.flight && !item.transport && !item.lodging`), 좌표가 없어서 다음/이전 일정과의 거리 표시도 건너뛴다(`itemDistanceKm`). 정렬(`app.js#renderTimeline`의 `sortKey`)도 항공편과 같은 버킷 — 그날 안에서 `item.transport.depTime` 기준으로 맨 위쪽에 온다(일반 일정의 `sortOrder`나 숙소의 "항상 맨 아래"보다 앞).
- **스크립트 로드 순서**: `index.html`에서 `flight.js` 바로 다음, `destinations.js` 앞 (storage.js/util.js 이후면 어디든 괜찮지만 관련 기능끼리 묶어 뒀다). `app.js`가 `transportForm.init(renderTimeline)`을 `flight.init(renderTimeline)` 바로 다음에서 부른다. 지도 검색(위 출발지/도착지 항목)이 `googleMaps.js`(`window.TripLog.googleMaps`)를 쓰므로, `index.html`에서 `transportForm.js`보다 먼저 로드돼야 한다 — 이미 그렇게 되어 있다(`googleMaps.js`가 훨씬 앞쪽).
- **색상**: 이 모달(`.transport-modal`)만 배경이 다른 창의 기본 흰 배경(`.modal` → `--surface`)이 아니라 파스텔 블루(`--surface-blue`)이고, 등록 버튼(`.btn-save`)도 다른 화면의 진한 `--accent` 대신 파스텔 블루(`--dday-pastel-bg`)다 — `.lodging-map-search .btn-save`/`.wallet-form-modal .btn-save` 등과 같은 스코프 오버라이드 방식(`css/style.css` 7-1 섹션).
