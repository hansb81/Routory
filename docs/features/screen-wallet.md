# Wallet page / Visibility / Upload form / Viewer (여행지갑)

> CLAUDE.md에서 이동된 상세 내용. 이 영역을 작업하기 전에 먼저 읽을 것.

- **Wallet page** (`walletPage.js`, route `#/wallet/:id`, PRD v7 "여행지갑 기능"; entered from the SHELL's bottom tab 여행지갑 (moved there from the schedule page's own quick menu), same `requireTrip` route guard (`app.js`) as `my-trip`/`schedule`/`budget`/`lodging` — missing/foreign trip id bounces to `main` before this page ever renders): a 개인지갑/공유지갑 tab row (`walletCategoryData.WALLET_VISIBILITY`, `DEFAULT_VISIBILITY = "personal"`; styled like `tripImport.js`'s `.trip-import-tab` — see **Wallet visibility (개인지갑/공유지갑)** below for what the split means) above a category filter row (`walletCategoryData.WALLET_CATEGORIES`, 5 keys matching `wallet_items.category`'s check constraint, plus a screen-only `전체`) styled like the expense form's category picker (circular icon, small label below), then a 2-column `.wallet-grid` of cards (category badge, preview, title). A PDF card shows a 📄 icon + the file's basename (from `fileUrl`, the part after the last `/`); an image card starts as "불러오는 중..." and `hydrateImages` resolves it via `storage.js#getWalletFileUrl(path, 60)` (a thin `createSignedUrl` wrapper, not `getPublicUrl`, since the bucket is private) — falling back to "불러올 수 없어요" on error (a `hydrateId` counter drops stale results if the filter changes first, same pattern as `app.js#hydrateImageThumbnails`). Filtering (both the visibility tab and the category chip) re-renders client-side from `storage.getWalletItems()`; an empty (filtered) list shows "공유된 문서가 없어요."(공유지갑 tab) or "아직 등록된 문서가 없어요."(개인지갑 tab).
  - **Per-trip since `019_wallet_trip_required.sql`** (user feedback: items were showing mixed across every trip's wallet instead of staying with the trip they were uploaded under): `walletPage.js#render(el, trip, loading)` filters `storage.getWalletItems()` (the *entire* cross-trip cache, same shape as `budgetPage.js#getExpenses()`) down to `item.tripId === trip.id` before splitting by visibility — mirroring how `budgetPage.js` filters `getExpenses()` by `trip.id` itself rather than storage pre-filtering it. `storage.js#loadWalletItems(tripId)`/`isWalletItemsLoaded(tripId)` load and track "loaded" per trip (`walletItemsLoadedTrips` Set, `walletItemsRequestIds` Map — the exact `expensesLoadedTrips`/`expensesRequestIds` pattern, not the old single-flag "loaded everything the user can see" shape) — `enter(el, { params })` resolves `trip = getTripById(params.id)` the same way `budgetPage.js#render` does. Before this migration, `walletForm.js` always saved personal uploads with `trip_id = null` (a "common storage" bucket, e.g. for a passport reused across trips), which is why every trip's 개인지갑 looked identical — the common-storage concept was removed outright (user confirmed: 개인지갑 is for sensitive personal documents and should be split per trip just like 공유지갑, not kept as a shared bucket).
  - The list starts from `storage.js#getWalletItems()`, a mutable cache that `walletPage.js`'s route `render` fills for real on first visit via `storage.js#loadWalletItems(trip.id)` — `select * from wallet_items where trip_id = :tripId`, RLS (007_wallet_shared.sql) still narrows further to "내 것 + 내가 멤버인 여행에 공유된 것", personal and shared items together; the page splits them client-side by `item.visibility`. Loading follows the same pattern as `budgetPage.js` (`storage.isWalletItemsLoaded(trip.id)` picks the loading text vs. the cached grid, refreshed behind it, a toast on failure). `walletForm.js`'s `addWalletItem` also pushes each successful upload onto this cache directly, so it appears in the grid immediately without a re-fetch (`clearCache()` resets the cache and every trip's "loaded" entry together, so a different signed-in user starts from an empty, unloaded state — never a previous account's items). There is no `←` back button any more (the `일정` tab on the SHELL is now how you get back to the trip's `#/schedule/:id` — `walletForm.js`/`walletViewer.js` still read `storage.getTrip()` for "which trip is this upload going into", same as before). The fixed bottom-right `+` opens `walletForm.js`; a card click opens `walletViewer.js` (see below) with that item.


- **Wallet visibility (개인지갑/공유지갑)**: every `wallet_items` row has a `visibility` (`personal` | `shared`, default `personal`; 007_wallet_shared.sql) picked once at upload time in `walletForm.js` and never changed afterward (no "move to the other wallet" action). `personal` means only the uploader can ever see or read the row/file (unchanged from before this split); `shared` additionally means every member of the item's `trip_id` can see the row and read the file. Since `019_wallet_trip_required.sql`, `trip_id` is `not null` for every row regardless of visibility (not just `shared` — the check constraint `wallet_items_shared_needs_trip` from 007 is now redundant but left in place, see **Wallet page**'s per-trip bullet above for why). RLS (007) splits the old single "본인만 조회/수정" `for all` policy into a `select` policy that's `user_id = me OR (visibility = 'shared' AND is_trip_member(trip_id))` plus separate insert/update/delete policies that stay owner-only — so a member seeing someone else's shared item can never edit or delete it (`walletViewer.js` also hides the 삭제 button client-side when `item.userId` isn't mine, to avoid a dead click that RLS would 42501 anyway). Storage RLS gets one more policy alongside 006's "own folder" one: `storage.objects` rows are also selectable (not upload/update/delete) when their `name` matches a `shared` `wallet_items.file_url` whose trip the requester belongs to — this is what actually lets another member's browser turn that path into a signed URL via `getWalletFileUrl`, since the file itself still physically lives under the uploader's `<uid>/…` folder. `walletViewer.js` shows "· 공유중" next to the category label when `item.visibility === "shared"` so the viewer knows it's visible to others.


- **Wallet upload form** (`walletForm.js`, a modal opened from the wallet page's `+`, not a route; add-only, no edit/delete yet): the first field is the 개인지갑/공유지갑 tab pair from **Wallet visibility** above (`state.visibility`, reset to `DEFAULT_VISIBILITY` = 개인지갑 every time the modal opens) — 공유지갑 is left out of the tab list entirely (not just disabled) when `storage.getTrip()` is null, which in practice no longer happens since the wallet page now requires a trip via its route guard (kept as a defensive filter anyway). Three buttons below it build three hidden `<input type="file">`s with different attributes — 사진에서 선택 (`accept="image/*"`), 직접 찍기 (`accept="image/*" capture="environment"`), PDF·파일 선택 (`accept="image/*,application/pdf"`) — all funnel into one `handleFileChosen(file)`. It rejects anything over 10 MB or outside image/PDF immediately (before any upload attempt, not just at save), showing `.form-error`; an image gets a local `URL.createObjectURL` preview, a PDF shows its `file.name` only (per PRD, no in-browser PDF rendering), and a ✕ clears the selection (revoking the object URL). Category is a single-select chip row (`walletCategoryData.WALLET_CATEGORIES`, no `전체` — this is a picker, not a filter, visually identical to `.expense-category-item` but under its own `.wallet-form-category-*` classes, matching the project's per-screen-namespace convention). Required at submit: file, category, title (description is optional; a missing current trip is also blocked here as a second guard — `showError` if `storage.getTrip()` is null, regardless of visibility); same open/close/saving-disables-close pattern as `expenseForm.js`. On submit it calls `storage.addExpense`-style `storage.js#addWalletItem({ file, category, title, description, visibility, tripId })` — **since `019_wallet_trip_required.sql`, `tripId` is always `storage.getTrip()?.id` regardless of visibility** (previously personal uploads always forced `tripId = null`, the "common storage" bucket that caused the per-trip bug — see **Wallet page**'s per-trip bullet), which uploads to `supabase.storage.from('wallet')` at path `"<uid>/<Date.now()>_<sanitized filename>"` (matching 006's `(storage.foldername(name))[1] = auth.uid()` policy — the physical path never depends on visibility or trip, only the `wallet_items` row does) and then inserts the `wallet_items` row; if the DB insert fails after a successful upload it tries to remove the now-orphaned Storage object before surfacing the original error. `storage.js#fail()` gained two more error-code branches for this: Storage's `NoSuchBucket` (the `wallet` bucket hasn't been created yet — see 006) and `Unauthorized`/`invalid_jwt`. `walletForm.js` is add-only (no edit).


- **Wallet viewer** (`walletViewer.js`, opened by clicking a wallet card, not a route): unlike every other modal in the app it is full-screen, not the capped-420px `.modal` (`.wallet-viewer-overlay` clears `.modal-overlay`'s `padding`/centering the same way `.map-modal-overlay` does). Header shows title + category icon/label together (plus "· 공유중" for a shared item — see **Wallet visibility**), then the description (if any) as a separate line, then a 삭제 button — hidden when `item.userId !== auth.getUserId()` (a shared item opened by a member other than its uploader), since RLS would reject the delete anyway. Body: a PDF gets an `<iframe>` plus a "새 탭에서 열기" link (belt-and-braces, since iframe PDF rendering is inconsistent on mobile); an image gets pinch-to-zoom and drag-to-pan built on raw Pointer Events (no library) — one `pointerdown/move/up` set handles both one-finger pan and two-finger pinch (distance-ratio scaling), `wheel` + `ctrlKey` covers trackpad pinch gestures, and double-click/tap toggles 1×/2× for mouse-only use; scale is clamped 1–4 and snaps back to 1 when it drops below ~1. `img.setPointerCapture` is wrapped in try/catch (it throws `NotFoundError` for a pointer the browser doesn't consider "active" — harmless in practice but cheap to guard). Both the grid thumbnail and the viewer's image/PDF resolve through the same `storage.js#getWalletFileUrl(path, ttlSeconds)` (thin wrapper over `createSignedUrl`, returns `null` instead of throwing so callers just show a fallback; the viewer asks for 300 s, the grid for 60 s) — for a shared item this signed URL now also works from another member's session (see **Wallet visibility**'s Storage policy note). 삭제 opens its own small confirm dialog (`.modal-confirm`, a separate DOM instance — not the schedule page's `#confirm-overlay`, which is wired to that module only) and calls `storage.js#deleteWalletItem(item)`: deletes the `wallet_items` row first (that's what "deleted" means to the user), then best-effort removes the Storage object (a failure there is only `console.warn`ed, not surfaced, mirroring `addWalletItem`'s asymmetric cleanup priority). Success closes the viewer, toasts, and calls the same `onChange` callback (`walletPage.js`'s grid refresh) that `walletForm.js` uses.
