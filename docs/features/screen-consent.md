# Consent gate (약관 동의)

> CLAUDE.md에서 이동된 상세 내용. 이 영역을 작업하기 전에 먼저 읽을 것.

- **Consent gate (약관 동의, `consentPage.js`, route `#/consent`)**: shown once, right after a user's first successful login, if they have no `user_consents` row yet (`storage.hasConsent()` — see `storage.js`'s note on that function and `010_user_consents.sql`). One 전체동의 checkbox plus three items — 이용약관 동의/개인정보 수집·이용 동의 (both required, each with a "보기" link to `#/terms`/`#/privacy`) and 광고성 정보 수신 동의 (optional, no "보기" — there's no separate document for it) — reusing the login screen's centered-360px-column look (`.consent`, new CSS) and the expense form's checkbox pattern (`accent-color`, not a custom widget). "동의하고 시작하기" stays `disabled` until both required boxes are checked; 전체동의 reflects (and can set) all three at once. Checkbox state lives in a module-level `state` object, not re-initialized on every `render()` call, specifically so that clicking "보기", reading the policy, and clicking its own `←` (which is a plain `history.back()`, landing back on `#/consent` because that's genuinely the previous history entry) doesn't reset what the user already checked. On submit, `storage.saveConsent({ termsVersion, privacyVersion, marketingAgreed })` (reading the versions from `window.TripLog.legalPages`) `upsert`s the one `user_consents` row and navigates to `#/main` — always main, never back to wherever the user originally intended to go, even from an invite link, per spec. A save failure (e.g. migration 010 not run yet) shows the mapped error inline (`.form-error`, same pattern as every other form) and re-enables the button without losing the checked state.
  - **Routing**: `app.js#initRouting` adds a `requireConsent` guard (`!auth.isRequired() || !auth.isLoggedIn() || storage.hasConsent() ? true : router.buildPath("consent")`) to the same route list `requireLogin` already covers (`CONSENT_GATED`), registered *after* `requireLogin` so login is checked first. `#/consent` itself only gets `requireLogin` plus one extra guard that bounces an already-consented visitor straight to `#/main` (covers typing the URL directly — spec's "skip and go to main" requirement). Because `requireConsent` is a synchronous guard but consent status comes from an async query, `storage.refreshConsent()` must resolve *before* the guard can run with the right answer: `initRouting`'s `auth.init().then(...)` now awaits it (when logged in) right before `router.start()`'s first `render()`, and a new `enterApp()` helper does the same (`await refreshConsent()` then `router.navigate(...)`) for the other place a login completes while the SPA is already running — `auth.onChange`'s "was on `#/login`, just became logged in" branch (native-app deep-link return). Calling `router.navigate` before the await would resolve were the bug class to avoid here — the guard would still see the stale default (`hasConsent() → true` until `consentLoaded` flips) and let an unconsented user straight into the app.
  - **Graceful degradation**: `storage.hasConsent()` defaults to `true` whenever `consentLoaded` is still `false` (never successfully checked, including because migration 010 hasn't been run — a `select` against a missing table fails and `refreshConsent()` just logs a warning rather than throwing) — so the entire consent feature is a no-op until the table exists, the same philosophy as 003/008's optional migrations. Verified by hand: with 010 not yet run on the live project, `#/consent` redirects straight to `#/main` (can't prove "no row" without a working table to query), and forcing the screen open (`storage.hasConsent = () => false` from the console) and submitting shows the expected "서버에 데이터 테이블이 아직 없어요…" `fail()` message.
  - **`consent` is in `tripShell.js`'s `ALL_ROUTES`** (not `SHELL_ROUTES`) for the same reason `terms`/`notifications`/etc. are — so the SHELL correctly hides itself if this route is ever reached while it was showing, even though in practice a user hits `#/consent` immediately after login, before any trip context exists.
