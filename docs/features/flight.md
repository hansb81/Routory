# Flight (항공)

> CLAUDE.md에서 이동된 상세 내용. 이 영역을 작업하기 전에 먼저 읽을 것.

- **Flight** (`flightData.js` data/lookup + `flight.js` UI): the schedule page's quick-menu button that opens this is labelled 교통편, but picking a transport type (항공/기차/버스/선박) happens **before** this module is ever involved, in a dropdown under that button (see **Transport dropdown (quick menu)** above) — `flight.openForm()` is only called once 항공 has already been chosen, so `flight.js` itself has no transport-type screen or state any more (an earlier pass added one directly inside this modal; it was pulled back out into the quick-menu dropdown instead, since a transport-type *picker* reads better as a lightweight dropdown than as a whole first screen of a modal). Adding a new flight therefore still opens the same **choice screen** first (`flight-step-choice`, mode `"choice"` in `flight.js#stepsFor`) — "항공권 사진으로 등록" (ticket-photo card, on top) or "직접 등록할게요" (manual, at the bottom), exactly as before this whole feature existed. Editing an existing flight skips the choice screen entirely (see below). A detail modal opens when a flight card is clicked (`schedule.js` routes flight cards to `flight.openDetail`).
  - **직접 등록 (manual path)**: same order as before — Day → airline + flight number (one screen) → confirm times/airports (`flight-step-day` → `flight-step-airline` → `flight-step-confirm`). The footer button on the airline screen stays disabled and says what is missing until both are filled. `←` on the Day screen (the path's first screen) returns to the choice screen; `←` on later screens just steps back one screen, same as before.
  - **항공권 사진으로 등록 (photo path)**: the same ticket-photo card as before (two buttons, 사진에서 선택 / 직접 찍기) now lives on the choice screen instead of the airline screen. How the photo is actually picked branches on `auth.isNativeApp()`: the web keeps the original two hidden `<input type="file">`s (gallery `accept="image/*"`, camera `capture="environment"`) read with `FileReader` (`readTicketFile`); the native app instead calls `@capacitor/camera`'s (deprecated-but-still-functional) `getPhoto({ resultType: "dataUrl", source, quality: 85, correctOrientation: true })` (`captureTicketPhoto`, `source` is `"PHOTOS"` or `"CAMERA"` depending which button was pressed) via the generic `window.Capacitor.Plugins.Camera` proxy — no bundler, so the npm package's JS is never imported, same pattern as `auth.js`'s `@capacitor/app` usage; a cancel (`"User cancelled photos app"`) is swallowed silently, other failures show a toast. Both paths converge on one function, `applyTicketDataUrl(dataUrl, readId)`, which takes the resulting `"data:mime;base64,..."` string from either source, size-checks it (`MAX_TICKET_BYTES`, computed from the base64 length so it works without a `File` object), fills the preview `<img>`, and hands it to `analyzeTicket`. The photo becomes a base64 string either way and is sent to the Edge Function via `supabase.functions.invoke("analyze-ticket", { body: { imageBase64, mimeType } })` (`analyzeTicket()`; status "항공권 분석 중...").
    - On success, `applyScanAndAdvance` (replaces the old `applyScan`) fills the airline chip and flight-number input (a recognized airline outside the 8 known ones, or a null value, is left blank) and decides how many screens are still needed, then jumps straight there — `flight.js#stepsFor` composes `["day"?, "airline"?, "confirm"]` for the photo path from two flags: `dayRequired` (true when the ticket's departure date doesn't match any Day of the trip, or wasn't read at all) and `airlineRequired` (true when the airline or flight number wasn't read). If neither is required (full read, date matches a Day), it skips straight to the confirm screen and immediately runs the same route lookup the manual path's "조회하기" does (`startLookup`).
    - **Day auto-match** (only case with no server round-trip involved): if the scanned departure date equals a trip Day's date, that Day is silently selected and a toast confirms it ("항공권 출발일에 맞춰 Day N으로 등록했어요."); no Day-picking screen is shown. If it doesn't match (outside the trip or unreadable), a Day screen (`flight-step-day`) is inserted before confirm and a toast asks the user to pick one — this is the fallback the user explicitly asked for when the date can't be resolved automatically.
    - If the airline or flight number wasn't read, an airline screen (`flight-step-airline`, no ticket card — that only lives on the choice screen now) is inserted with a notice above the fields ("항공권에서 자동으로 입력되었어요. 확인해주세요" + missing items), enforcing the same "can't proceed without airline+flight number" rule the footer button already enforces for the manual path.
    - It keeps the text-only `state.scan` (airports/times) so confirm is pre-filled without another lookup when all four were read, or overlaid on the lookup result when partial (only if the flight number still matches, `scanForCurrentFlight`).
    - On any error / `data.error` it shows the toast "자동 인식에 실패했어요. 직접 입력해주세요" and leaves the user on the choice screen. The base64 is dropped as soon as the call finishes (the preview `<img>` stays until ✕/close, or until the screen navigates away); nothing about the photo is ever stored.
  - `flight.js#stepsFor()` is the single source of truth for "what screen is this" (an ordered array of `"choice"|"day"|"airline"|"confirm"`; `state.step` is just an index into it) — editing always resolves to `["day","airline","confirm"]` starting at the last index (confirm), so `←` can still revisit Day/airline exactly like before, just without a photo-rescan option.
  - **Lookup order** in `fetchFlightInfo` (used by both the manual path's "조회하기" and the photo path's auto-continue): (1) AviationStack `/flights?flight_iata=` if the user saved a key (localStorage `triplog.aviationstack.key`); it returns recent operating records, so times are approximate for the trip date, and timestamps are labelled `+00:00` but are airport-local; do not use `flightsFuture` (the free plan can't filter by flight number and allows 1 request per 60 s). (2) adsbdb callsign lookup (no key) for origin/destination airports only. (3) Manual entry. Duration is computed from local times and the fixed UTC offsets in the `AIRPORTS` table, which assumes no DST. City → airport defaults live in `CITY_AIRPORTS`, keyed by the ids in `destinations.js`.
