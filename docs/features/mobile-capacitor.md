## Mobile wrapper (Capacitor)

- `mobile/` (sibling of `triplog/`, at the repo root) is a **separate** npm project that wraps the site for Android/iOS with Capacitor — PRD v5 "앱스토어/플레이스토어 출시" first step (Android only so far; iOS needs a Mac and hasn't been added).
  - **Why a separate folder, not inside `triplog/`**: `capacitor.config.json`'s `webDir` must be a real subfolder — Capacitor's CLI hard-rejects `webDir: "."` ("is not a valid value for webDir") because `cap sync` copies the entire webDir tree into the native app's assets, and copying the project root would recursively pull in `node_modules/`, the `android/` project itself, etc. So `mobile/capacitor.config.json` has `"webDir": "../triplog"`, reaching into the site folder from outside it — `triplog/index.html` and friends were never moved, and nothing about the deployed site (`vercel.json`, `serve.py`, paths in `index.html`) changed.
  - `mobile/package.json` (its own, unrelated to `triplog/package.json` or the repo-root one) has `@capacitor/core`, `@capacitor/android`, `@capacitor/ios`, `@capacitor/app`, `@capacitor/camera`, `@capacitor/browser`, `@capacitor/push-notifications`, `@capacitor/splash-screen` as dependencies and `@capacitor/cli`, `@capacitor/assets` as devDependencies; `mobile/node_modules` is gitignored (`mobile/.gitignore`). No `<uses-permission>` was added to `AndroidManifest.xml` for the camera plugin on purpose: its native side only requests `android.permission.CAMERA` at runtime if that permission is declared in the manifest (`CameraPlugin.kt#isPermissionDeclared`); left undeclared, it falls back to launching the system Camera/Gallery app via implicit intents (`<queries>` for `IMAGE_CAPTURE`/`GET_CONTENT`/`PICK`, already in the plugin's own manifest, auto-merged by Gradle) — no permission dialog, no manifest change needed. Revisit only if in-app camera preview (not just "open the Camera app") is ever wanted.
  - **Push notifications** (PRD v11; `@capacitor/push-notifications`, Android only so far): unlike camera, `AndroidManifest.xml` *does* need a hand-added `<uses-permission android:name="android.permission.POST_NOTIFICATIONS" />` — Android 13+(API 33) blocks runtime notification permission entirely without this manifest declaration (no silent-fallback path like camera's implicit-intent trick), and `targetSdkVersion` is 36 so this applies. `android/app/build.gradle` already conditionally `apply plugin: 'com.google.gms.google-services'` when `google-services.json` exists (generated by the original `npx cap add android`, not something this feature had to add) and the top-level `build.gradle` already has the `com.google.gms:google-services` classpath — both were already wired before this feature; only the manifest permission and the plugin's npm dependency were new. `android/app/google-services.json` (Firebase config, `applicationId: com.teamsdb.routory` must match the Firebase Android app) is committed (not gitignored — the commented-out `# google-services.json` line in `android/.gitignore` is intentionally left commented).
    - `triplog/js/pushNotifications.js` (`window.TripLog.pushNotifications`) is the client module — same "no bundler, read the native bridge's `window.Capacitor.Plugins.PushNotifications` proxy directly" pattern as every other Capacitor plugin here (`auth.js`/`flight.js`). See **Common pages**'s "알림" section and **Permission prompts**'s Notification gate for the full request → register → upsert flow and the registrationError UI. Not yet wired into `mobile/android`'s generated Gradle files (`capacitor.settings.gradle`/`capacitor.build.gradle` are both `// DO NOT EDIT — regenerated by "capacitor update"/"cap sync"`) — running `npx cap sync android` from `mobile/` (the user's own step, see root `CLAUDE.md`) is required before a native build picks up the new plugin.
    - **Tapping a notification** (`bindListeners()`'s `pushNotificationActionPerformed` listener): reads `action.notification.data.url` — the same hash-path string (`"/#/my-trip/<id>"` etc.) that `send-notification`'s FCM payload embeds in `data.url` (see `supabase/functions/send-notification`) and that `sw.js`'s web `notificationclick` handler already consumes, so native and web follow one shared URL convention end to end. `navigateToNotificationUrl()` strips everything up to and including the `#` (since `router.navigate()` expects a bare path, not a `"#/..."` string — see `router.js`) and calls `router.navigate(path)`. The listener is bound inside `register()`, so it's attached whenever `register()` first runs in that app session — for a user who already granted permission earlier, that's `app.js`'s startup call to `refreshIfAlreadyGranted()`, which (per Capacitor's documented behavior for this plugin) should still receive the tap event even for a cold start the notification itself launched, because the native layer buffers it until a listener is attached. **Not verified on a real device/emulator** — this environment has neither, so the cold-start delivery claim rests on Capacitor's own docs, not an observed test; confirm the first real on-device test actually opens the right screen from a killed-app state.
  - `mobile/capacitor.config.json`: `appId: "com.teamsdb.routory"`, `appName: "Routory"` (the native app's display name — originally `"TripLog"`, changed to `"Routory"` 2026-10-18 during Google Play prep to match the rebrand, see Overview). `mobile/android/app/src/main/res/values/strings.xml`'s `app_name`/`title_activity_main` (hand-maintained, not touched by `cap sync`) were updated to `"Routory"` at the same time — this is the string Android actually shows under the home-screen icon and in the Play Store listing, so it had to match even though `capacitor.config.json`'s `appName` is also used as the initial value when `npx cap add android` first generates the project.
  - `mobile/android/` is the generated native Android Studio project (`npx cap add android`); its own `.gitignore` (auto-created) excludes build output and the copied web assets (`app/src/main/assets/public`, regenerated by `cap sync`/`cap copy`, not hand-edited).
    - `AndroidManifest.xml`'s `MainActivity` carries a second `<intent-filter>` (`action.VIEW` + `BROWSABLE`, `<data android:scheme="routory" android:host="auth-callback">`) so Android routes `routory://auth-callback...` links to the running app (`launchMode="singleTask"`, already the Capacitor default, keeps it the same Activity instance instead of a new one) — this is what makes `triplog/js/auth.js`'s native OAuth redirect (see **Auth and Supabase**) actually reach the app. Hand-edited; `cap sync` doesn't touch `AndroidManifest.xml`, so this survives every sync.
  - `npx cap sync` (run from inside `mobile/`) copies `triplog/`'s current files into `android/app/src/main/assets/public` and updates native plugins — run it after any change to the site that should reach the native build. It also copies `triplog/package.json` and `vercel.json` into the assets folder as an inert side effect (webDir has no include/exclude filter); harmless, just unused dead weight in the APK.
  - **Safe-area (notch / home indicator)**: `index.html`'s viewport meta has `viewport-fit=cover` — without it `env(safe-area-inset-*)` always evaluates to `0`, even on native, because the page never opts into drawing under the system bars/cutout. `css/style.css`'s `:root` gets a blanket `padding-top`/`padding-bottom: env(safe-area-inset-*)`, which only actually helps screens that scroll as plain `body` content (main, login) — it does **not** reach anything `position: fixed` or `sticky` (their containing block is the viewport itself, unaffected by an ancestor's padding), so every full-bleed bar patches itself individually: the SHELL's own two bars (`--shell-top-h: calc(60px + env(safe-area-inset-top))`, `--shell-bottom-h: calc(57px + env(safe-area-inset-bottom))`, both `:root` tokens — see **Trip shell** under **Screens**) size and pad themselves with these; the five screens the SHELL floats over then leave room for it using the *same* tokens (`.page[data-page="my-trip"/"budget"/"wallet"/"lodging"]`'s `top`/`bottom`, `.wallet-fab`'s `bottom`) or, for the schedule screen which still scrolls as plain `body` content and so already gets `:root`'s own safe-area push, just the extra 60px/57px of *non*-safe-area chrome height (`.app-top`'s `margin-top`/sticky `top`, `.timeline`'s bottom padding) so the safe-area inset isn't added twice. `budget`/`wallet`/`lodging`'s own header (and `.budget-total-bar`/`.lodging-footer`) no longer need their own extra safe-area padding (removed) now that the page box itself starts below the notch; `.wallet-viewer-header` is the one exception that still adds its own `env(safe-area-inset-top)` — it's a true full-screen modal overlay (`.wallet-viewer-overlay`), not one of the five SHELL screens. On the web (or when `env()` isn't supported) every one of these resolves to `0`, so nothing looks different there. **Not verified on a real notched device** — only in a desktop browser, where `env()` is always `0` — so double-check the schedule screen's top spacing on-device after this change (see **Trip shell**'s note on the 60px/`--shell-top-h` split).
  - **App icon / splash** (`@capacitor/assets`, devDependency): generates the native icon/splash images from a source file the user supplies — Claude sets up the tooling but does not run `generate` itself (the user prepares the source image and runs the command by hand).
    - `mobile/assets/` (its own README explains the convention) is where the tool looks by default: `logo.png` (+ optional `logo-dark.png`) for the app icon, and — since the two rarely look good as the same image — a separate `logo.png`-independent `splash.png` (+ optional `splash-dark.png`, Custom Mode source, recommended ≥2732×2732px or it gets upscaled on the largest targets) for the splash screen; if `splash.png` is absent the tool falls back to generating a splash from `logo.png` instead. Background colors are passed as flags, e.g. `npx capacitor-assets generate --android --iconBackgroundColor "#007aff" --splashBackgroundColor "#ffffff"` (ignored for the splash when a dedicated `splash.png` exists — it only affects the icon then) — `--android` matters because there's no `ios/` project yet, and without a platform flag the tool would otherwise also look for one.
    - `sharp` (the image-resizing engine `@capacitor/assets` depends on) has a native install script that recent npm blocks by default ("install-scripts" allowlist); it's pre-approved in `mobile/package.json`'s `allowScripts` so a plain `npm install` in `mobile/` (e.g. on a fresh clone) sets it up without the user hitting a cryptic sharp error — verified with `node -e "require('sharp')"`.
    - Output goes straight into `mobile/android/app/src/main/res/` (native resources, not web assets) — `npx cap sync` does not touch it and isn't needed after running `generate`; only a rebuild in Android Studio is.
    - **On real Android 12+ (API 31+) devices/emulators, the generated `drawable/splash` full image never actually shows as the native splash — verified by reading `@capacitor/splash-screen` 8.0.2's own source (`SplashScreen.java`), not assumed.** `compileSdkVersion`/`targetSdkVersion` are 36, so the OS's own SplashScreen API always applies, and it hard-limits the splash surface to an icon + a solid background color, full stop — no arbitrary bitmap. `SplashScreen.java#showOnLaunch` always tries `showWithAndroid12API()` (androidx `core-splashscreen`'s `installSplashScreen()`) first on 31+, and it practically never throws on a real device, so it `return`s right after — the *other* code path (`show()`/`showDialog()`, the one that actually inflates `@drawable/splash` into a full-bleed `ImageView`) only runs as the pre-31 fallback when `showWithAndroid12API()` throws, so it's dead code on every current device. The plugin (already in `mobile/package.json`, wired into the native project by `npx cap sync android`, no `MainActivity.java` edit needed) is only good for extending how long the OS's own icon-on-background splash stays up (`plugins.SplashScreen.launchShowDuration` in `mobile/capacitor.config.json`); its `backgroundColor`/`androidScaleType`/`showSpinner` keys are dead on 31+ too (only read by the unreachable fallback).
    - **The icon screen's background color** is controlled by `values/styles.xml`'s `AppTheme.NoActionBarLaunch` (`parent="Theme.SplashScreen"`) via the `core-splashscreen` library's own `windowSplashScreenBackground` attr (unprefixed — confirmed from the library's `values-v31.xml`, which forwards it into the framework's `android:windowSplashScreenBackground` on 31+). Left unset it falls back to `?android:colorBackground` (a light lavender-gray on stock AOSP light theme) — set explicitly to `#007AFF` (RGB 0,122,255, matching `css/style.css`'s `--accent`) to brand the icon screen instead. `mobile/capacitor.config.json`'s `backgroundColor` was updated to the same hex only for consistency/documentation (it has no effect on 31+, see above). Hand-edited; `npx cap sync` doesn't touch `res/values/styles.xml`.
  - **Not yet done**: an iOS platform (`npx cap add ios`, Mac + Xcode required), running `capacitor-assets generate` itself (tooling is ready, source icon + the actual run are the user's), and AdMob. Kakao/Google console platform registration turned out to be **unnecessary** for this app's login: it goes through Supabase's `signInWithOAuth` (a plain web OAuth redirect), never the native Kakao/Google SDKs, so there's no package-name/key-hash pairing for either console to check — the two things that actually mattered were the `routory://auth-callback` Supabase redirect URL (above) and opening the OAuth page in a real external browser, both done now.
