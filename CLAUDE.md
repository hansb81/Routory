# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

`triplog/` is a Korean-language travel planner: a static site in plain HTML/CSS/vanilla JS, backed by Supabase (login, Postgres, one Edge Function). All UI text and code comments are Korean; match that.

- **Display name vs. internal name**: the app is branded **Routory** to users (`<title>`, the login screen heading, page-title `document.title`, the invite-share fallback place name), but nothing else was renamed — the folder (`triplog/`), the `window.TripLog` JS namespace every file reads/writes, `TripLogConfig`, and every `triplog.*` localStorage/IndexedDB key stay as `TripLog`/`triplog` (deliberately, to avoid a large low-value refactor and to not lose users' existing local data like saved photos or the AviationStack key). Don't "fix" this mismatch by renaming the internal code without being asked — it's intentional.

- No bundler, linter or test suite, and the directory is not a git repository.
- `triplog/package.json` (name/version only) exists just for Vercel. The repo-root `package.json` only lists the Supabase CLI as a devDependency (`node_modules` there is not part of the site).
- Things the user runs by hand, never Claude: `vercel` / `vercel --prod`, `supabase functions deploy`, `supabase secrets set`, every SQL file in `supabase/migrations/` (Supabase dashboard → SQL Editor), and `npx cap sync android` (see **Mobile wrapper (Capacitor)**).

## Commands

- **Run**: `python serve.py [port] [--local]` from the repo root (default 8080, serves `triplog/`), then open http://localhost:8080/. Opening `triplog/index.html` via `file://` also works, but nothing can be loaded or saved there (no login).
- **Phone testing**: without `--local`, `serve.py` listens on all network interfaces and prints the PC's addresses; a phone opens `http://<PC address>:8080/`.
  - Trips and items live in Supabase, so signing in with the same account shows the same trips (only photos stay per browser).
  - Over plain HTTP on a non-localhost address the page is not a secure context, so `crypto.randomUUID` is missing; keep the `generateId` fallback (`images.js` uses it).
  - This PC has a public IPv4 address (the Ethernet adapter gets it by DHCP, so it can change): stop the server when done or use `--local`. A `--local` server listens on 127.0.0.1 only and is unreachable from a phone.
- **Cache**: `serve.py` sends `Cache-Control: no-store` (unlike `python -m http.server`). A tab loaded before that may hold stale files: hard-reload (Ctrl+Shift+R), or from automation run `await fetch(url, {cache: 'reload'})` for each changed file and then `location.reload()`.
- **Static check**: only `node --check js/<file>.js`.
- **Deploy (Vercel)**: the site is plain static files published from the `triplog/` folder.
  - Run `vercel` / `vercel --prod` from inside `triplog/`, not the repo root (or `serve.py`, `CLAUDE.md`, `supabase/` and everything else would be published).
  - `triplog/vercel.json`: `framework`/`buildCommand`/`installCommand` are `null` (no install, no build); it also sets `X-Content-Type-Options: nosniff` on everything and `Cache-Control: public, max-age=86400` on `/img/*`. There is no `api/` folder. Almost every route is a `#/...` hash route, so `/` → `index.html` is enough — the exceptions are the Naver login callback and the account-deletion request page, which both need a real (non-hash) path; see **Login page** and **Account deletion request page (계정 삭제 요청)**. `vercel.json`'s `rewrites` maps the extensionless `/auth/naver-callback` to `triplog/auth/naver-callback.html`, and `/account-deletion` to `triplog/account-deletion.html` (Vercel doesn't resolve a directory-style clean URL to `index.html` on its own here); `serve.py` does the same extensionless → `.html` fallback itself for local/phone testing, generically for *any* matching path (`NoCacheHandler._rewrite_clean_url` — not hardcoded per-route), so both environments serve the same file at the same path.
  - File names are case-sensitive on Vercel: keep the paths in `index.html` exactly equal to the real file names.
  - Do not add a `Referrer-Policy: no-referrer` header: the Google Maps key is restricted by HTTP referrer.
  - For a new domain: add `https://<domain>/*` to the Google Maps key's website restrictions, `https://<domain>/**` to Supabase → Authentication → URL Configuration → Redirect URLs (ideally also Site URL), and the domain to the Kakao app (see **Invite**). Otherwise the map is blocked and login returns to the Site URL. Avoid wildcard `*.vercel.app` for the Maps key: any site on vercel.app could use it.

## Mobile wrapper (Capacitor)

- `mobile/` (sibling of `triplog/`, at the repo root) is a **separate** npm project that wraps the site for Android/iOS with Capacitor — PRD v5 "앱스토어/플레이스토어 출시" first step (Android only so far; iOS needs a Mac and hasn't been added).
  - **Why a separate folder, not inside `triplog/`**: `capacitor.config.json`'s `webDir` must be a real subfolder — Capacitor's CLI hard-rejects `webDir: "."` ("is not a valid value for webDir") because `cap sync` copies the entire webDir tree into the native app's assets, and copying the project root would recursively pull in `node_modules/`, the `android/` project itself, etc. So `mobile/capacitor.config.json` has `"webDir": "../triplog"`, reaching into the site folder from outside it — `triplog/index.html` and friends were never moved, and nothing about the deployed site (`vercel.json`, `serve.py`, paths in `index.html`) changed.
  - `mobile/package.json` (its own, unrelated to `triplog/package.json` or the repo-root one) has `@capacitor/core`, `@capacitor/android`, `@capacitor/ios`, `@capacitor/app`, `@capacitor/camera`, `@capacitor/browser`, `@capacitor/splash-screen` as dependencies and `@capacitor/cli`, `@capacitor/assets` as devDependencies; `mobile/node_modules` is gitignored (`mobile/.gitignore`). No `<uses-permission>` was added to `AndroidManifest.xml` for the camera plugin on purpose: its native side only requests `android.permission.CAMERA` at runtime if that permission is declared in the manifest (`CameraPlugin.kt#isPermissionDeclared`); left undeclared, it falls back to launching the system Camera/Gallery app via implicit intents (`<queries>` for `IMAGE_CAPTURE`/`GET_CONTENT`/`PICK`, already in the plugin's own manifest, auto-merged by Gradle) — no permission dialog, no manifest change needed. Revisit only if in-app camera preview (not just "open the Camera app") is ever wanted.
  - `mobile/capacitor.config.json`: `appId: "com.teamsdb.routory"`, `appName: "TripLog"` (the native app's display name — chosen literally when this was set up; may want to revisit against the **Routory** rebrand, see Overview).
  - `mobile/android/` is the generated native Android Studio project (`npx cap add android`); its own `.gitignore` (auto-created) excludes build output and the copied web assets (`app/src/main/assets/public`, regenerated by `cap sync`/`cap copy`, not hand-edited).
    - `AndroidManifest.xml`'s `MainActivity` carries a second `<intent-filter>` (`action.VIEW` + `BROWSABLE`, `<data android:scheme="routory" android:host="auth-callback">`) so Android routes `routory://auth-callback...` links to the running app (`launchMode="singleTask"`, already the Capacitor default, keeps it the same Activity instance instead of a new one) — this is what makes `triplog/js/auth.js`'s native OAuth redirect (see **Auth and Supabase**) actually reach the app. Hand-edited; `cap sync` doesn't touch `AndroidManifest.xml`, so this survives every sync.
  - `npx cap sync` (run from inside `mobile/`) copies `triplog/`'s current files into `android/app/src/main/assets/public` and updates native plugins — run it after any change to the site that should reach the native build. It also copies `triplog/package.json` and `vercel.json` into the assets folder as an inert side effect (webDir has no include/exclude filter); harmless, just unused dead weight in the APK.
  - **Safe-area (notch / home indicator)**: `index.html`'s viewport meta has `viewport-fit=cover` — without it `env(safe-area-inset-*)` always evaluates to `0`, even on native, because the page never opts into drawing under the system bars/cutout. `css/style.css`'s `:root` gets a blanket `padding-top`/`padding-bottom: env(safe-area-inset-*)`, which only actually helps screens that scroll as plain `body` content (main, login) — it does **not** reach anything `position: fixed` or `sticky` (their containing block is the viewport itself, unaffected by an ancestor's padding), so every full-bleed bar patches itself individually: the SHELL's own two bars (`--shell-top-h: calc(60px + env(safe-area-inset-top))`, `--shell-bottom-h: calc(57px + env(safe-area-inset-bottom))`, both `:root` tokens — see **Trip shell** under **Screens**) size and pad themselves with these; the five screens the SHELL floats over then leave room for it using the *same* tokens (`.page[data-page="my-trip"/"budget"/"wallet"/"lodging"]`'s `top`/`bottom`, `.wallet-fab`'s `bottom`) or, for the schedule screen which still scrolls as plain `body` content and so already gets `:root`'s own safe-area push, just the extra 60px/57px of *non*-safe-area chrome height (`.app-top`'s `margin-top`/sticky `top`, `.timeline`'s bottom padding) so the safe-area inset isn't added twice. `budget`/`wallet`/`lodging`'s own header (and `.budget-total-bar`/`.lodging-footer`) no longer need their own extra safe-area padding (removed) now that the page box itself starts below the notch; `.wallet-viewer-header` is the one exception that still adds its own `env(safe-area-inset-top)` — it's a true full-screen modal overlay (`.wallet-viewer-overlay`), not one of the five SHELL screens. On the web (or when `env()` isn't supported) every one of these resolves to `0`, so nothing looks different there. **Not verified on a real notched device** — only in a desktop browser, where `env()` is always `0` — so double-check the schedule screen's top spacing on-device after this change (see **Trip shell**'s note on the 60px/`--shell-top-h` split).
  - **App icon / splash** (`@capacitor/assets`, devDependency): generates the native icon/splash images from a source file the user supplies — Claude sets up the tooling but does not run `generate` itself (the user prepares the source image and runs the command by hand).
    - `mobile/assets/` (its own README explains the convention) is where the tool looks by default: `logo.png` (+ optional `logo-dark.png`) for the app icon, and — since the two rarely look good as the same image — a separate `logo.png`-independent `splash.png` (+ optional `splash-dark.png`, Custom Mode source, recommended ≥2732×2732px or it gets upscaled on the largest targets) for the splash screen; if `splash.png` is absent the tool falls back to generating a splash from `logo.png` instead. Background colors are passed as flags, e.g. `npx capacitor-assets generate --android --iconBackgroundColor "#007aff" --splashBackgroundColor "#ffffff"` (ignored for the splash when a dedicated `splash.png` exists — it only affects the icon then) — `--android` matters because there's no `ios/` project yet, and without a platform flag the tool would otherwise also look for one.
    - `sharp` (the image-resizing engine `@capacitor/assets` depends on) has a native install script that recent npm blocks by default ("install-scripts" allowlist); it's pre-approved in `mobile/package.json`'s `allowScripts` so a plain `npm install` in `mobile/` (e.g. on a fresh clone) sets it up without the user hitting a cryptic sharp error — verified with `node -e "require('sharp')"`.
    - Output goes straight into `mobile/android/app/src/main/res/` (native resources, not web assets) — `npx cap sync` does not touch it and isn't needed after running `generate`; only a rebuild in Android Studio is.
    - **On real Android 12+ (API 31+) devices/emulators, the generated `drawable/splash` full image never actually shows as the native splash — verified by reading `@capacitor/splash-screen` 8.0.2's own source (`SplashScreen.java`), not assumed.** `compileSdkVersion`/`targetSdkVersion` are 36, so the OS's own SplashScreen API always applies, and it hard-limits the splash surface to an icon + a solid background color, full stop — no arbitrary bitmap. `SplashScreen.java#showOnLaunch` always tries `showWithAndroid12API()` (androidx `core-splashscreen`'s `installSplashScreen()`) first on 31+, and it practically never throws on a real device, so it `return`s right after — the *other* code path (`show()`/`showDialog()`, the one that actually inflates `@drawable/splash` into a full-bleed `ImageView`) only runs as the pre-31 fallback when `showWithAndroid12API()` throws, so it's dead code on every current device. The plugin (already in `mobile/package.json`, wired into the native project by `npx cap sync android`, no `MainActivity.java` edit needed) is only good for extending how long the OS's own icon-on-background splash stays up (`plugins.SplashScreen.launchShowDuration` in `mobile/capacitor.config.json`); its `backgroundColor`/`androidScaleType`/`showSpinner` keys are dead on 31+ too (only read by the unreachable fallback).
    - **The icon screen's background color** is controlled by `values/styles.xml`'s `AppTheme.NoActionBarLaunch` (`parent="Theme.SplashScreen"`) via the `core-splashscreen` library's own `windowSplashScreenBackground` attr (unprefixed — confirmed from the library's `values-v31.xml`, which forwards it into the framework's `android:windowSplashScreenBackground` on 31+). Left unset it falls back to `?android:colorBackground` (a light lavender-gray on stock AOSP light theme) — set explicitly to `#007AFF` (RGB 0,122,255, matching `css/style.css`'s `--accent`) to brand the icon screen instead. `mobile/capacitor.config.json`'s `backgroundColor` was updated to the same hex only for consistency/documentation (it has no effect on 31+, see above). Hand-edited; `npx cap sync` doesn't touch `res/values/styles.xml`.
  - **Not yet done**: an iOS platform (`npx cap add ios`, Mac + Xcode required), running `capacitor-assets generate` itself (tooling is ready, source icon + the actual run are the user's), and AdMob. Kakao/Google console platform registration turned out to be **unnecessary** for this app's login: it goes through Supabase's `signInWithOAuth` (a plain web OAuth redirect), never the native Kakao/Google SDKs, so there's no package-name/key-hash pairing for either console to check — the two things that actually mattered were the `routory://auth-callback` Supabase redirect URL (above) and opening the OAuth page in a real external browser, both done now.

Every screen/part has an alias key (e.g. `MAIN`, `MYTRIP-BOTTOMTABS`, `FLIGHT`, `INVITE-MODAL`).

- The full list (visible menu names, files, CSS markers, edit guides, server SQL, flows) is **`comments.html`** in the repo root: searchable, click an alias to copy it. When adding or renaming a screen, modal or file, update its `SCREENS` / `FILES` / `EDITS` / `SERVER` arrays.

## Architecture

### Structure and routing

- **No ES modules.** Every file is an IIFE that reads from and writes to `window.TripLog.<name>` (`file://` blocks module imports). Load order in `index.html` matters: `util` → `ui` → `calendar` → `config` → `googleMaps` → `supabaseClient` → `auth` → `permissionPrompt` → `aiNotice` → `tripImport` → `storage` → `images` → `mapPicker` → `schedule` → `dday` → `flightData` → `flight` → `destinations` → `tripSetup` → `invite` → `dayMap` → `router` → `commonPages` → `legalPages` → `lodgingData` → `lodging` → `mainPage` → `loginPage` → `consentPage` → `accountDeletePage` → `myTripData` → `tripMembers` → `myTripPage` → `tripShell` → `invitePage` → `currencyData` → `expenseCategoryData` → `walletCategoryData` → `expenseForm` → `budgetPage` → `walletForm` → `walletViewer` → `walletPage` → `tripImportPreview` → `tripExport` → `timelineDrag` → `app`. `app.js` is the entry point and wires everything last. `aliasView.js` is not in the list (lazy-loaded). `lodgingData`/`lodging` moved after `router` (unlike most other feature pairs) because `lodging.js` calls `router.definePage` at load time, same reason `budgetPage.js`/`walletPage.js` load near the end.
- **Router** (`router.js`): hash router with routes `#/main`, `#/my-trip/:id`, `#/schedule/:id`, `#/login`, `#/invite/:code`, `#/budget/:id`, `#/wallet` (not tied to a trip, so no `:id`; see **Wallet page**), `#/lodging/:id` (see **Lodging**), `#/notifications`, `#/settings` (the last two have no `:id` either — they're a shared pair opened from both MAIN-MENU and the SHELL's MYTRIP-MENU, see **Common pages (알림 · 설정)**), `#/terms`, `#/privacy` (no `:id`, no login guard — see **Legal pages (이용약관 · 개인정보처리방침)**), `#/notice`, `#/contact`, `#/help` (no `:id`, bare "준비 중" placeholders reached from 설정's 고객센터 section — see **Common pages (알림 · 설정)**).
  - Unknown or empty hashes are replaced with `#/main`. A route is one page: the router only toggles `hidden` on that page's elements.
  - `schedule` reuses the original header/menu/timeline already in `index.html` (`.app-top` + `#timeline`); the other pages are `<main class="page">` sections the router creates.
  - A page's content is registered with `router.definePage(name, render)` (called on every visit; a route without one gets a generic "내용 준비 중" placeholder).
  - `router.beforeEnter(name, guard)` guards a route (return a path string to redirect); `onEnter` / `onLeave` hooks run around navigation.
  - `app.js` uses them so that `my-trip`, `schedule`, `budget` and `lodging` require an existing trip (unknown `:id` → `#/main`, the same `requireTrip` guard) and to close open modals when leaving the schedule page.
  - `router.query()` reads the hash's query string; `router.safeRedirect(value)` only lets known app routes through (not login, no `//`, no absolute URLs).
- **Login gate**:
  - `main`, `my-trip`, `schedule`, `invite`, `budget`, `wallet`, `lodging`, `notifications`, `settings`, `account-delete` and `consent` have a guard that sends a signed-out user to `#/login` (registered before `requireTrip`; from any route but main it adds `?redirect=<encoded path>`). `login` sends a signed-in user to the `redirect` path (or `#/main`). The same list minus `consent` also goes through a second, `requireConsent` guard — see **Consent gate (약관 동의)**.
  - Social login leaves the page and returns to `#/main`, so `loginPage.js` stores the redirect via `auth.savePostLoginPath` (localStorage `triplog.postLoginPath`, 15 min expiry) before `signInWithOAuth`; `app.js` after `auth.init()` takes it (`auth.takePostLoginPath`) and `replaceState`s to it when the landing hash is `#/main` / `#/login`.
  - `auth.onChange` re-checks the current screen when the session changes while it is open (logout button, another tab, expiry).
  - `router.start()` runs only after `auth.init()` has read the session, so `.app-top` and `#timeline` in `index.html` start `hidden` (the router shows them) to avoid a flash of the schedule screen.
- **Alerts and toasts** (`ui.js`): `ui.showAlert(message)` / `ui.showComingSoon(name)` show an in-app alert dialog instead of `window.alert()`; `ui.showToast(message)` shows the short-lived bottom toast.
- **Shared helpers**: `util.js` (`escapeHtml`, `generateId`, date helpers, `getTripDays`) and `calendar.js` (month grid markup, range-pick rule, month shifting; used by the trip-setup and lodging calendars). Use these instead of local copies. Always run externally sourced text through `escapeHtml` before putting it in `innerHTML`.
- **Render loop**: modules mutate storage, then call the `onChange` callback that `app.js` passed in (`renderTimeline`). `renderTimeline` rebuilds the whole timeline from the trip's date range, one Day section per date.

### Data (`storage.js`)

Trips and schedule items live in **Supabase** (`supabase/migrations/001`, `002`; `003` and `004` are optional/feature-specific, see **Server**). Without the tables every call fails with the Korean message "서버에 데이터 테이블이 아직 없어요…".

- **Reads** are synchronous from an in-memory cache: `getAllTrips`, `getTripById`, `getTrip`, `getItems`, `getItemById`. The cache is filled from the server:
  - `refreshTrips({ maxAgeMs })` selects `trips` with `trip_members!inner(role)` filtered by `trip_members.user_id = me`, i.e. every trip I belong to, invited ones included (`Trip.role` is `owner | editor`, `Trip.userId` is `owner_id`). With `maxAgeMs` it skips the request if the list was fetched that recently (the app start plus the main page's enter would otherwise fetch twice).
  - `loadItems(tripId)` selects that trip's `schedule_items`. `isTripsLoaded()` / `isItemsLoaded(id)` tell whether a first load happened.
- **Writes** are async and must be awaited: `createTrip` (inserts with `owner_id = session user`; a DB trigger adds the owner to `trip_members`), `saveTrip` (update; owner only, RLS returns 0 rows for an editor), `deleteTrip` (owner only, children cascade), `leaveTrip` (deletes my own `trip_members` row; needs 004), `addItem` / `updateItem` (patch fields only) / `deleteItem`, `loadMembers`, `removeMember`.
  - They update the cache from the server's response and throw an `Error` with a Korean message (`fail()` maps PGRST205 / 42501 / etc.) that callers show (form error line or `ui.showToast`). Modals stay open on failure so input isn't lost.
  - Ids are server-generated uuids.
- **Current trip**: pages set it with `setCurrentTrip(id)` (the router guard does this from the `:id`, looking only in the cache, so `app.js` calls `storage.refreshTrips()` after `auth.init()` and before `router.start()` so a direct `#/my-trip/:id` URL resolves); `getTrip()` returns it.
- **Cache safety**: `storage.onChange(fn)` fires whenever the trip cache is replaced or cleared (`mainPage.js` re-renders on it). `syncUser()` (called from `auth.onChange`) drops the cache and reloads when the signed-in user changed; `clearCache()` runs on sign-out, so one account never sees another's cached data.
- **Schedule loading**: `app.js#enterSchedule` (schedule route `onEnter`) shows "일정을 불러오는 중이에요..." for a trip whose items were never loaded, otherwise draws the cache and refreshes behind it. `mainPage.js` refreshes the list on every enter.
- **Not signed in** (`file://` or `requireLogin: false`): nothing can be loaded or saved; writes throw "로그인이 필요해요".
- **Photos**: still IndexedDB (`images.js`); only the item-id → image-ids map lives in localStorage `triplog.itemImages` (no photo column on `schedule_items`), so photos are not visible on other devices or to invited members.
- **Old data**: the old localStorage keys (`triplog.trips`, `triplog.items`, `triplog.trip`) are deliberately left untouched and never read or migrated (personal test data). `storage.js` only deletes the ancient `triplog.user` key at load; the old fixed mock user (`storage.getUser()/isLoggedIn()`) and `adoptUnownedTrips` are gone. The signed-in user comes from `auth.js`; without a name the UI falls back to "여행자".
- **Item types**: a plain item has `date/time/place/lat/lng/memo/images/sortOrder`.
  - `time` (optional, `field-time` in the add/edit form, an `<input type="time">`) writes straight to `schedule_items.time` — that column predates the current item shape (see the `title`/`time`/`category` note below) but was never written to until this; `rowToItem` already read it as a legacy fallback, so no migration was needed to start using it for real. Displayed as `.item-time` under the title (`app.js#renderItemCard`, `HH:MM`, skipped for flights since their time is already in the summary line).
  - `sortOrder` (integer, only meaningful among items sharing the same `trip_id`+`date` — see **Timeline reorder & swipe-delete**) is read from `schedule_items.sort_order` (008_schedule_item_order.sql) with a `0` fallback when that column doesn't exist yet, so reading/adding/editing items never breaks on a server that hasn't run 008 — only persisting a *new* order (`storage.reorderItems`) needs it and fails gracefully (toast + revert) until then.
  - A flight item is the same record with an extra `item.flight` object plus `category: "flight"`, `airline` (= `flight.airlineName`) and `flightNo`, copies written to the server columns `category`, `airline`, `flight_no` (002 must have been run, or saving a flight fails with "테이블 구조가 앱과 달라요"). No ticket-photo data is ever stored on an item.
  - Items are mapped from `schedule_items` rows in `storage.js#rowToItem`. The server column `title` may still carry a value from the old PRD-era schema; `renderItemCard` and the sort key in `app.js` fall back to it, so keep that fallback when changing the item shape.

### Screens

- **Main page** (`mainPage.js`): placeholders for flights/news, then the trip cards from `getAllTrips()` (upcoming first, past last, D-day via `util.ddayLabel`). Cards are plain links to `#/schedule/:id` (selecting a trip goes straight to its schedule, not the my-trip screen).
  - The list is refreshed from the server on every enter; it shows a loading line before the first load, a retry button if loading fails, and an empty state with no trips.
  - "새 여행 만들기" and "+ 새 여행" open the same 2-step wizard as the schedule page's trip settings (`tripSetup.open({ trip: null, canClose: true, onComplete })`). `onComplete` calls `storage.createTrip` with the title `"<city> 여행"`, the `cityId` (so the flight and lodging features recognize the city) and the dates (async; a failure only shows a toast), then re-renders the list and shows a toast (the user stays on the main page).
  - There is no free-text destination or title field: only cities listed in `destinations.js` can be chosen, so add new places there.

    - **Duplicate badges** (`mode: "append"` only, `markDuplicates()`): fetches the trip's current items fresh (`storage.loadItems`/`loadExpenses`, not the possibly-stale cache) right after the cards first render, then for each card looks for an existing row with the same `date`/`dayKey` and the same name ignoring whitespace/case (`normalize()`) — a `"기존 일정/비용 교체됨"` badge appears and `matchedId` is set to that row's id (read by `handleSubmit()` below to `update` instead of `insert`). For schedule items the name comparison is `place || title` on **both** sides, not `title` alone: real `schedule_items` almost never have `title` set (per **Data**, plain items use `place`; `title` is a legacy fallback column), and the AI's own extraction likewise splits a location into `place` with a separate, differently-worded `title` description — comparing `title` to `title` (or the existing row's `place` to the incoming `title`) would almost never fire since the wording rarely matches verbatim even for a true duplicate; matching `place || title` against `place || title` on both sides is what actually lines up with `saveScheduleItem`'s own `place = item.place || item.title` fallback used when saving.
    - **`등록하기` (`handleSubmit`) actually saves.** `mode: "create"` first calls `storage.createTrip` (with `cityId: null` — free-text AI destinations rarely match a `destinations.js` city, so the new trip loses the flight/lodging city-default lookups that a normally-created trip gets); the instant that succeeds, `state.mode` flips to `"append"` and `state.tripId`/`state.createdTitle` are set — so if anything after this point fails and the user hits `등록하기` again, it never tries to create a second trip, it just keeps saving into the one that already exists. Each schedule/expense item is then awaited **one at a time, in order** (`saveSequentially`, not `Promise.all` — a literal requirement, and it's also what makes "how far did it get" meaningful): a card with `matchedId` calls `storage.updateItem`/`updateExpense` on that id, one without calls `addItem`/`addExpense`.
      - `saveScheduleItem` maps `{date, place, time, memo}` onto `addItem`/`updateItem`'s actual shape (`date`, `place`, `memo` — see **Data**): `place` falls back to `title` when the AI didn't read a place (same priority order the app's own display fallback already uses), and `time` gets prepended into `memo` as `"09:00 · <memo>"` since plain schedule items have nowhere else to put a time. `category` is dropped silently — `addItem` has no such parameter for a plain item (only a structured `item.flight` object gets a `category` column, and the AI's guess isn't that structure) — this matches every other "장소 추가" entry in the app, which also has no category.
      - `saveExpense` maps directly (the AI's shape already matches `addExpense`'s), computing `krwAmount: currencyData.toKrw(amount, currency)` (`null` if the currency isn't in `RATES_TO_KRW`, same as `expenseForm.js`) — and substitutes `"etc"`/`"가져온 비용"` when `category`/`title` are empty, since both are `not null` (`title text not null`, `category text not null check (...)` in `005_budget.sql`) and the preview screen doesn't force the user to fill them before allowing `등록하기` in append mode.
      - **Partial failure**: each item is try/caught individually and sorted into `succeeded`/`failed`; if anything failed, the succeeded items are removed from `state.scheduleItems`/`state.expenses` (so a retry can't insert them twice) and `.form-error` shows counts plus up to 3 `'<title>': <reason>` lines (`summarizeFailures`) — the modal stays open, same "don't lose input" convention as every other form. `storage.createTrip` itself failing is a separate, earlier `.form-error` path (nothing else runs).
      - **On full success**: closes, toasts (names the new trip if `state.createdTitle` is set — a trip was created on the very first successful attempt, since it's cleared to null on `open()` and never set again once already in append mode), and `router.navigate`s to `#/schedule/:id` either way (a new trip or one already existing).

### Auth and Supabase

- **Client** (`supabaseClient.js`): `index.html` loads supabase-js from the jsDelivr CDN (UMD, `window.supabase`, before all app scripts); `supabaseClient.js` creates the client with the project URL and anon key written in the file and exposes it as `window.TripLog.supabase` (not as a global `supabase`, which stays the library namespace).
  - The anon key is public, so data safety rests entirely on RLS on every table; never put the `service_role` key in the client.
  - The client uses `flowType: "pkce"` on purpose: the default implicit flow returns the OAuth result in the URL hash (`#access_token=...`), which collides with this hash router (`redirectTo` ends in `#/main`, tokens would be appended after it and not parsed, and supabase-js clears `location.hash`). PKCE returns `?code=...#/main`; supabase-js exchanges the code itself and only removes `code`.
  - Connectivity check: `await TripLog.supabase.auth.getSession()` returns `{ data: { session: null }, error: null }` with no network call when nobody is signed in, so it only proves the client exists. To check the URL/key, `GET <SUPABASE_URL>/auth/v1/settings` with the `apikey` header should return 200.
- **Login page** (`loginPage.js`, route `#/login`): three buttons of identical size/font (`.login-btn`, each with its service's logo as inline SVG on the left and its brand color from the `--brand-*` tokens). 구글로 / 카카오로 시작하기 call `supabase.auth.signInWithOAuth({ provider, options: { redirectTo: auth.oauthRedirectTo(), skipBrowserRedirect: auth.isNativeApp() } })`; on the web that's the same as before (this tab navigates to the provider's page, `skipBrowserRedirect` is falsy) and there is no callback page. On native, `skipBrowserRedirect: true` stops `signInWithOAuth` from navigating the app's own WebView — it only returns `{ data: { url } }` — and `signIn()` opens that URL itself with `window.Capacitor.Plugins.Browser.open({ url })` (`@capacitor/browser`, Custom Tabs on Android), a real external browser rather than the embedded WebView; Google specifically returns `disallowed_useragent` (403) for its OAuth page inside an embedded WebView (same restriction that already applied to KakaoTalk's in-app browser, below), so this was a required fix, not just a nice-to-have. The login buttons re-enable right after `Browser.open` resolves (the Custom Tab covers the screen while it's up, so there's no double-submit risk); `auth.js#handleDeepLink` closes that tab once the `routory://auth-callback` redirect comes back (see **Auth and Supabase**). 네이버로 시작하기 doesn't go through Supabase at all — Supabase's built-in provider list has no Naver — so `loginPage.js#naverSignIn` opens Naver's OAuth2.0 authorize URL directly (`https://nid.naver.com/oauth2.0/authorize?response_type=code&client_id=...&redirect_uri=...&state=...`). `client_id` is `TripLogConfig.naverClientId` (`js/config.js`; public by design, same treatment as the Google Maps/Kakao JS keys, but still a placeholder value until the real one from Naver Developers is filled in). `state` is a fresh `util.generateId()` value saved to `sessionStorage` (`triplog.naverOAuthState`) right before the redirect, for the callback page to check. `redirect_uri` is always `${location.origin}/auth/naver-callback` — a real path, not a `#/...` one, because Naver appends `?code=...&state=...` as a query string, and a hash router can't see query params placed before its own `#` fragment. That path is served by the static file `triplog/auth/naver-callback.html` (see the Vercel/`serve.py` rewrite note above), which reads `code`/`state`/`error` from `location.search`, checks `state` against the saved `sessionStorage` value (clearing it either way — one-time use regardless of outcome), and on a match calls the **Edge Function `naver-login`** (see **Server**) for a `hashedToken`, then `supabase.auth.verifyOtp({ type: "email", token_hash: hashedToken })` to actually create the session. This page is outside the SPA bundle (a real path, not a hash route — see above), so it can't use `window.TripLog.supabase`; it loads supabase-js from the same CDN as `index.html` and makes its own client with the same URL/anon key (`detectSessionInUrl: false`, since this page's own `?code=` is Naver's authorization code, not a Supabase PKCE code, and must not be consumed by supabase-js's own URL detection). Any failure (Naver returned `error`, no `code`, `state` mismatch, the Edge Function call failing, or `verifyOtp` failing) redirects to `/#/login?error=<code>&error_description=<msg>` — the same mechanism `auth.js#readCallbackError`/`takeCallbackError()` already use for Google/Kakao failures, so `loginPage.js` shows it with no new error-display code needed. Success redirects to `/#/main`; the session `verifyOtp` created is in `localStorage` by then, so the `TripLog.supabase` client `index.html` creates fresh on that load picks it up immediately (same cross-page-load session sharing the PKCE web flow already relies on), and `app.js`'s existing `auth.takePostLoginPath()` still carries the user on to wherever they were headed before login if that was set. Every origin the app is opened from (`http://localhost:8080`, a phone address, the deployed domain) must be registered as both a "서비스 URL" and a "Callback URL" (`.../auth/naver-callback`) in Naver Developers, same reasoning as the Google Maps referrer list. Naver login refuses to start from `file://` (no origin), same as Google/Kakao.
  - The Google and Kakao providers must be enabled in the Supabase dashboard (Authentication → Providers), and `http://localhost:8080/**` (plus any phone address and the deployed domain) added under Authentication → URL Configuration → Redirect URLs; otherwise the authorize URL returns a raw JSON 400 ("provider is not enabled") or falls back to the Site URL.
  - Kakao note: Supabase always requests the `account_email` scope for Kakao unless its "Allow users without an email" setting takes effect, and a Kakao app without the email consent item fails at Kakao with KOE205 ("설정하지 않은 동의 항목: account_email"). This only shows in a real browser.
- **`auth.js`**: caches the Supabase session (`init()` reads it once at startup, waiting for the `?code=` exchange after an OAuth return, with a 5 s timeout; `onAuthStateChange` keeps it current) so the synchronous router guards can use `isLoggedIn()`. It also provides:
  - `getUserId()`, `getProfile()` (`{ id, name, email, avatarUrl, provider }`, trying several `user_metadata` field names because Google and Kakao differ: `full_name`/`name`/`nickname`/`preferred_username` and `avatar_url`/`picture`/`profile_image`; only http(s) avatar URLs are kept — `mainPage.js`'s account row reads it directly).
  - `takeCallbackError()`: at load `auth.js` grabs any `error`/`error_code`/`error_description` from the return URL (query or hash) or a failed `?code=` exchange from `getSession()`; the login page shows it once, because the router rewrites the URL and the reason would otherwise be lost.
  - `signOut()` (scope `local`, so other devices stay signed in), `onChange`, `savePostLoginPath` / `takePostLoginPath`.
  - **Native app OAuth** (`isNativeApp()`, `oauthRedirectTo()`, `initDeepLinks()`): `isNativeApp()` is `Boolean(window.Capacitor?.isNativePlatform?.())` — `false` on the web build, since it never loads any Capacitor script (nothing to install there; `window.Capacitor` only exists when the native shell injects it). `oauthRedirectTo()` is what `loginPage.js` passes as `redirectTo`: the web's `origin + "/#/main"` unchanged, or `"routory://auth-callback"` on native, because a native OAuth round-trip leaves the app for the system browser and comes back via a URL scheme, not a page reload — `?code=...` in a normal https redirect has nowhere to land. `initDeepLinks()` (called once at module load, not inside `init()`) registers `window.Capacitor.Plugins.App.addListener("appUrlOpen", ...)` for that scheme — the generic per-plugin proxy every Capacitor native app exposes automatically, used directly instead of importing `@capacitor/app`'s JS package, since this project has no bundler (the npm dependency in `mobile/package.json` still matters: `cap sync` reads it to register the plugin's native Kotlin/Swift side). `handleDeepLink(url)` pulls `code` (or `error`/`error_description`) out of the callback URL's query string with `new URL(url).searchParams`, best-effort closes the external browser tab (`Capacitor.Plugins.Browser.close()` — see **Login page**), and calls `supabase.auth.exchangeCodeForSession(code)`; success flows through the same `onAuthStateChange` → `onChange` listeners as the web path (`app.js` then navigates off `#/login`), failure shows a toast (the login page isn't re-rendering to catch it the way `takeCallbackError()` does on the web, since the app never reloaded). This requires `routory://auth-callback` to be added under Supabase → Authentication → URL Configuration → Redirect URLs (same reason `http://localhost:8080/**` is there — Supabase rejects a `redirectTo` it doesn't recognize) — the user adds this by hand, it's not something any file here can express.
- Login is required only when `TripLogConfig.requireLogin` (in `config.js`) is not `false` and the page is served over http(s); set it to `false` if provider setup is broken and the app becomes unreachable (but then nothing can be saved, see **Data**). The main page shows the user's avatar/name and a 로그아웃 button; the SHELL's slide-in menu (`tripShell.js`, shown on my-trip/schedule/budget/wallet/lodging) has the same logout.

- **Edge Function `analyze-ticket`** (`supabase/functions/analyze-ticket/index.ts` + README with deploy/curl steps; deployed with `supabase functions deploy analyze-ticket`; called from `flight.js#analyzeTicket`): Deno, no imports.

- **Edge Function `naver-login`** (`supabase/functions/naver-login/index.ts` + README with deploy/curl steps; deployed with `supabase functions deploy naver-login`; not yet called from the client — see **Login page**'s Naver note and `triplog/auth/naver-callback.html`'s `TODO`): unlike the two functions above, **this one does import** `@supabase/supabase-js` (pinned version, e.g. `@2.45.4`) — user lookup/creation/login-token issuance goes through the Auth Admin API, which the SDK does more safely/concisely than a hand-rolled REST call would; the "no imports" rule is specific to the Gemini-calling functions, not a blanket policy.
  - Takes `POST { code, state }` (the values `auth/naver-callback.html` received back from Naver's redirect) and needs no `Authorization` beyond the anon key — unlike `analyze-ticket`/`analyze-trip-import` it does not gate on a signed-in user, since this call *is* how a user signs in.
  - Exchanges `code` for a Naver access token (`POST https://nid.naver.com/oauth2.0/token`, `client_secret` from the secret `NAVER_CLIENT_SECRET`, never in code or in the response), fetches the profile (`GET https://openapi.naver.com/v1/nid/me`), then builds a synthetic identifier email `naver_<naver id>@users.triplog.app` — the actual Naver email is untrusted (consent-only, not verified) and only kept as `user_metadata.naver_email` — and finds-or-creates that Supabase user (`admin.createUser({ email_confirm: true, user_metadata: { provider: "naver", naver_id, nickname, avatar_url, naver_email } })`; a "already registered" error from `createUser` is treated as found, not fatal, since the existence pre-check is best-effort — see the file's own comments on `admin.auth.admin.listUsers`'s undocumented `filter` param).
  - Returns only `{ hashedToken }` (`admin.generateLink({ type: "magiclink", email }).data.properties.hashed_token`) — never the synthetic email, the Naver tokens, or the `service_role` key. The client is expected to finish with `supabase.auth.verifyOtp({ token_hash: hashedToken, type: "magiclink" })`, which needs no email either. That client-side wiring (and the redirect back into the hash-routed app afterward) is not built yet; this function only covers turning `code` into `hashedToken`.
  - Failures use real HTTP status codes instead of the analyze-* functions' "always 200" convention (this is a login endpoint, not a best-effort AI feature): `400` bad request, `401` Naver rejected the code, `405` not POST, `500` this function's own config or Supabase Admin API failure, `502` couldn't reach Naver.
  - Type-checked with `deno check` (not the Node-shim technique the other two use, since this one has a real remote import `deno check` can resolve) and smoke-tested end to end with `deno run` locally, including one real round-trip to Naver's token endpoint with a deliberately-invalid code to confirm the 401 path.
- **Edge Function `travel-briefing`** (`supabase/functions/travel-briefing/index.ts` + README with deploy/curl steps; deployed with `supabase functions deploy travel-briefing`; called from `myTripPage.js#hydrateBriefingCards`, see **My-trip page**): Deno, no imports — same Gemini-fallback/login-gate pattern as `analyze-ticket`, reusing the same `GEMINI_API_KEY`/`GEMINI_MODEL` secrets, but text-only (no image) and backed by a cache table instead of being fully stateless.
  - Takes `POST { destination, startDate, endDate }` (`YYYY-MM-DD`, `startDate <= endDate`). Builds a cache key `date_range = "<startDate>~<endDate>"` and looks up `briefing_cache` (009_travel_briefing.sql) for that `(destination, date_range)` pair via **plain `fetch` calls to PostgREST** (`SUPABASE_URL`/`SUPABASE_SERVICE_ROLE_KEY`, both auto-injected) rather than importing `@supabase/supabase-js` — unlike `naver-login`, there's no Admin-API-only operation here (just one `select` and one `upsert`), so raw REST keeps the "no imports" property the Gemini functions otherwise have.
  - **Caching (요청 2번: "같은 목적지+기간은 하루 한 번만")**: a cache row younger than `CACHE_FRESH_MS` (24h) is returned as-is (`cached: true, stale: false`) without calling Gemini at all. Otherwise it calls Gemini and, on success, `upsert`s the row (`on_conflict=destination,date_range`, i.e. at most one row per key — the REST call explicitly sends `created_at` on every upsert, since the column's `default now()` only applies to a fresh `insert`, not the `update` half of an upsert). On a Gemini failure it falls back to serving that same stale row if one exists at all (`cached: true, stale: true`) instead of a hard error — only a destination+range with *no* cache row at all (fresh or stale) gets the `{ error: "최신 정보를 가져오지 못했어요" }` (HTTP 200) failure shape the other two functions use.
  - **Prompt/model call**: builds a single Korean text prompt (no image) asking for `{ news: [...], deals: [...] }`, each item `{title, summary, sourceUrl, sourceName}`, and turns on Gemini's built-in `google_search` tool (`tools: [{ google_search: {} }]`) so the model grounds its answer in an actual web search instead of training-data recall — this is also why the request does **not** set `response_mime_type`/`response_schema` like the other two functions do: the Gemini API doesn't support combining structured-output mode with `tools`, so this function leans on prompt instructions + the same fence-stripping/`JSON.parse` fallback `analyze-ticket` already uses, then validates the shape itself server-side (`toResult`/`toItems`) — an item without a syntactically valid `http(s)` `sourceUrl` is dropped outright rather than shown without attribution (요청 1·3번: every surfaced item must carry a source link), and both arrays are capped at 5.
  - Verified with the same Node + `globalThis.Deno`-shim technique as `analyze-ticket`/`analyze-trip-import`, extended to also mock the PostgREST `fetch` calls (a small in-memory `Map` keyed by `destination|date_range` standing in for the real unique-constrained table) — covers the login/400 guards, cache-hit-skips-Gemini, cache-miss-per-distinct-key, the stale-cache-on-failure fallback, the true-failure (no cache at all) path, and the non-retryable JSON-parse-failure path, rather than a real deploy (the user's own step, same as the other two).
  - Client side (`triplog/js/myTripPage.js`): `hydrateBriefingCards` is one function that calls this once and fills **both** the 현지 뉴스 and 할인 정보 cards from the one response's `news`/`deals` arrays (rather than two separate calls) — see **My-trip page**'s "Real API cards, graceful-degradation group" bullet above for the rendering/failure-state details.
- **Edge Function `airport-congestion`** (`supabase/functions/airport-congestion/index.ts` + README; deployed with `supabase functions deploy airport-congestion`; called from `myTripPage.js#hydrateAirportCongestionCard`, see **My-trip page**): Deno, no imports, no DB (real-time data — caching it like `travel-briefing` would defeat the point). Same login gate/CORS/HTTP-200-on-failure shape as the other functions, but simpler: no Gemini involved, just a proxy.
  - Takes `POST { airportCode }` (IATA 3 letters). Only `SUPPORTED_AIRPORTS = Set(["ICN"])` is attempted at all; anything else returns `{ available: false }` immediately with no network call — this is what makes "해외 공항은 항상 숨김" true by construction rather than by a runtime check.
  - **The data.go.kr call is explicitly unverified** — read the file's own top-of-file comment and the README before touching it. Incheon Airport Corporation's "출국장 혼잡도 조회" API's real endpoint URL and response field names are gated behind data.go.kr's own approval flow (a downloadable `.docx` guide only visible after applying for that specific dataset with a real account), which isn't something crawlable/verifiable from here — confirmed by deliberately searching for it and also finding a developer's own write-up of getting this exact class of API's operation name wrong on a first guess. Given that, the function is built so an unverified guess is *safe* to ship: `fetchIncheonCongestion`/`parseIncheonResponse` follow data.go.kr's platform-wide conventions with confidence (`serviceKey`/`type=json` query params, `response.body.items.item[]` envelope) but guess at the inner field names (candidate lists in `pickNumber`), and — the actual safety net — the function does **not attempt the network call at all** unless both `DATA_GO_KR_SERVICE_KEY` and `INCHEON_CONGESTION_API_URL` secrets are set, defaulting to `available:false` (card stays hidden) otherwise. So it's safe to deploy right now; it just won't show real data until someone applies for the API, captures a real response, and fixes the field-name guesses accordingly (the README spells out those exact steps).
  - Verified (to the extent that's possible without the real endpoint) with the same Node + `globalThis.Deno`-shim technique as the other functions: auth/400 guards, the unsupported-airport short-circuit (no `fetch` call happens), the missing-secrets short-circuit (ditto), a successful parse picking the busiest of several mocked items, and `available:false` on a malformed response shape / HTTP error / thrown network error.
- **Edge Function `delete-account`** (`supabase/functions/delete-account/index.ts` + README; deployed with `supabase functions deploy delete-account`; called from `accountDeletePage.js`'s final confirm dialog — see **Account deletion (회원 탈퇴)**): takes `POST` with no body — the only input is the caller's own `Authorization` JWT, decoded the same way `analyze-ticket#isSignedIn` does (`role`/`sub` claims, trusting the gateway already verified the signature) to get the id of the account to delete. **Deliberately ignores any user id a request body might contain** — a client can only ever delete itself, never be tricked or abused into deleting someone else. `service_role` is used only for the deletion work below, never for identifying the caller. Like `naver-login`, this one imports `@supabase/supabase-js` (same pinned version) because it needs the Auth Admin API (`admin.auth.admin.deleteUser`) and Storage admin calls, not just Postgres rows.
  - **Eight explicit, ordered steps**, each wrapped so a failure names exactly which one broke (a shared `step(label, run)` helper turns any `{ error }` into `Error("<label> 실패: <message>")`): (1) `wallet_items` — reads each row's `file_url` (the path inside the private `'wallet'` bucket) first, removes those Storage objects, *then* deletes the rows, because Storage objects aren't Postgres rows and no FK `cascade` ever reaches them. (2) `expenses` where `created_by` = caller. (3) `schedule_items` where `created_by` = caller. (4) `trip_members` where `user_id` = caller — every membership, owned trips and shared ones alike ("본인이 속한"). (5) `trips` where `owner_id` = caller only — a shared trip the caller merely belongs to was already handled by step 4 (membership gone, trip itself untouched); deleting an *owned* trip here cascades via its own `trip_id` FKs to any remaining `schedule_items`/`expenses`/`trip_members`/`trip_invites` other members left in it — the same blast radius as `storage.js#deleteTrip`. (6) `trip_invites` where `created_by` = caller — RLS only lets owners create invites, so step 5's cascade has usually already cleared these; this is a (harmless, idempotent) mop-up. (7) `user_consents` where `user_id` = caller. (8) `admin.auth.admin.deleteUser(caller)` — by now nothing should still reference this user, so this should always succeed cleanly.
  - **Steps 2, 3 and 6 deliberately aren't scoped to "only trips I own"** — they delete by `created_by` regardless of who owns the trip, on purpose: this is a genuine policy difference from "여행 나가기" (`storage.js#leaveTrip`, which only removes the `trip_members` row and leaves your contributions anonymized in place) — *deleting the account* is a stronger ask ("erase my data") than *leaving a trip* ("I'm done with this one"), so it reaches into other people's trips to remove what this user specifically contributed, not just what they owned.
  - **Not a single transaction.** Running eight separate REST/Admin-API calls instead of one Postgres transaction means a mid-sequence failure can leave the earlier steps already applied. This is accepted, not accidental: every step's `WHERE` clause is scoped to the caller, so **re-running the whole function is always safe** — already-deleted rows just match zero and move on — making "retry" the actual recovery mechanism, which is also why the client's fixed failure message doesn't need to explain anything more specific than "try again / contact support." A single all-or-nothing version would need a dedicated Postgres function (RPC) wrapping all eight steps in one transaction, which wasn't asked for and wasn't built.
  - `011_delete_account_cascades.sql` is a schema-level safety net for this function, not a dependency of it — see that migration's own CLAUDE.md entry above. The function remains correct even on a database that hasn't run it (steps 1–7 already clear everything step 8 needs gone).
  - The client (`accountDeletePage.js`) never shows this function's specific error text to the end user — see **Account deletion (회원 탈퇴)** — only `console.warn`s it; the specific "`<단계> 실패: ...`" message exists for Edge Function logs, not for display.
  - Not yet deployed or run against a real account (deploying Edge Functions, and running `011_delete_account_cascades.sql`, are both the user's own steps, per this file's **Commands** section). Verified instead by exercising the client-side failure path for real: with the function undeployed, `accountDeletePage.js`'s confirm dialog genuinely received a failed `functions.invoke` call end to end (checkbox → button → confirm dialog → the fixed "고객센터로 문의해주세요" message shown inline, dialog left open, account/trips confirmed untouched afterward) — this is the actual current-state failure path, not a simulated one.

## Conventions

- The multi-step modals (trip setup, flight, lodging) share the `.wizard*` CSS classes (`.wizard-header/-heading/-body/-footer`, `.wizard-back`, `.wizard-close`, `.wizard-step-label`). Selectable lists share `.pick-list/.pick-item/.pick-info/.pick-name/.pick-sub/.pick-btn`, and search boxes use `.search-input`. Reuse these rather than adding new layouts. Element ids (e.g. `trip-back`, `city-list`) are separate from class names and stay module-specific.
- `[hidden]` is forced to `display: none !important` in CSS, so toggle visibility with the `hidden` attribute.
- `css/style.css` is one file split into numbered sections (the table of contents is at the top). Put new rules in the matching section instead of appending to the end. All colors, spacing, radii, shadows and z-indexes come from the `:root` tokens; do not hard-code hex colors or z-index numbers (use `--z-modal`, `--z-alert`, ...).
- **Category colors/icons**: the `--color-all/flight/lodging/meal/sightseeing/shopping/etc` tokens are kept in `:root`, and `[data-category="..."]` maps them to `--cat-color`. Give an element `data-category` and use `var(--cat-color)`. Icons and labels for the same keys live in `myTripData.CATEGORY_META`. (Schedule items themselves have no category.)
- The my-trip mint header uses `--mint`, `--mint-dark` (date pill) and `--mint-deep` (mint text on white).
- Responsive: the base styles are the 360px phone layout, with tweaks in the `max-width: 400px` block and wider layouts from 600/720/1024px (`--content-max` grows to 640/720/860). `word-break: keep-all` on `body` keeps Korean words together.
- **Color policy: pastel (going forward).** New color values for images/icons/badges and any new decorative or identity-carrying text (i.e. color that stands in for "which category/day/series/status" rather than plain body copy) should default to a pastel tone — soft, desaturated hues, not saturated primaries — rather than the older vivid/primary palette (`--accent` blue, the `--color-*` category colors, `--danger` red, the original `--route-*` blue/teal/orange/purple/red/green) that predates this policy. The policy started warm-only (coral/peach/berry/mustard/terracotta/ochre/cocoa, for `--route-1..6`/`--text-warm-muted`) but has since been used across the hue wheel on request — pastel blue (`--dday-pastel-bg`, `--page-bg-blue`), pastel gray (`--dday-pastel-gray-bg/-ink`), pastel coral/red (`--avatar-pastel-bg/-ink`, `--danger-pastel`) — so treat **pastel** (light, soft, not saturated) as the actual constraint, not warmth specifically. The one place hue is still narrowed to warm is a genuine **multi-color set shown together**, like `--route-1..6`, where that narrowing exists to keep N slots mutually distinguishable (see the validation note below) — it's not a sign that every other pastel must also stay warm. This does **not** mean recoloring existing neutral UI chrome (`--text`, `--text-soft`, `--text-muted`, `--border`, `--surface`, etc.) retroactively — only new colors going forward, unless asked to also redo the old ones. `--route-1..6` and `--text-warm-muted` (see **Day map** / **Inter-item distance**) were the first tokens under this policy; `--dday-pastel-bg/-ink`, `--dday-pastel-gray-bg/-ink`, `--avatar-pastel-bg/-ink`, `--danger-pastel` and `--page-bg-blue` (see **Main page**'s trip cards and MAIN-MENU) followed. Pastel-on-pastel pairings picked this way have repeatedly landed below WCAG AA contrast (e.g. the D-day badge, ~2:1) when the user asked for a specific pairing by name/hex — note the ratio in a code comment rather than silently swapping in a higher-contrast color, since the aesthetic call was deliberate and explicit.
  - **Don't eyeball a multi-color set — validate it, and validate the full "all pairs visible at once" case if that's realistically how it's seen.** `--route-1..6` is worn by every Day at the same time in one scrolling timeline, not shown one at a time like a paginated chart, so it's held to the dataviz skill's strict `--pairs all` gate (every one of the 15 pairs among 6 colors, not just neighbors) — run `scripts/validate_palette.js "<hex,...>" --mode light --pairs all` and don't settle for the default adjacent-only check just because it passes first. A hue-only warm palette (no blue/green/purple) doesn't have enough room to also pass **all-pairs under CVD simulation** at 6 slots — even the skill's own full-hue-wheel default palette only clears that for its first 3 slots — so treat CVD there as a documented, accepted gap (mitigated by the number always being shown too) and instead hold the line on the **normal-vision** floor for all pairs, which a warm-only set *can* clear with enough work. Getting there took more than picking 6 hex values by feel: hand-picked attempts kept failing because two colors that look different in isolation (e.g. two different "shades of orange", or two colors that are merely far apart in raw hue-degrees) can still collapse in OKLab once you account for how lightness and chroma compress hue differences — the fix that actually worked was a small script that hill-climbs 6 points in OKLCH (L, C, hue) to maximize the *worst* pairwise OKLab distance, constrained to a hue window that stays clear of blue/green/purple (see `--route-1..6`'s code comment in `style.css` for the resulting numbers: worst pair ΔE 18.6 against a 15 target). Reach for that kind of search — don't hand-tune hex values pair by pair — whenever a "just pick N different colors" request has more than ~4 slots or a "no cool hues" type constraint that narrows the usable range, since both make manual tuning this failure-prone.
  - **Pastel fills need a matching ink color, not one hardcoded text color.** A light pastel needs dark text and a darker pastel needs light text — check contrast per swatch (e.g. via that same script's exported `contrast(a, b)`) and store both together (`--route-N` + `--route-N-ink`, applied together as `--pin-color`/`--pin-ink`), instead of assuming white (or black) works on every color in the set.
  - **`--page-bg-blue` reached the SHELL and the schedule screen** (`body.has-trip-shell { background: var(--page-bg-blue); }`, `css/style.css`'s BASE section, next to the pre-existing `body.has-main-bg` rule). `body.has-trip-shell` is toggled by `tripShell.js#updateShell` for exactly the five SHELL routes (my-trip/schedule/budget/wallet/lodging), so in principle this rule applies to all five, but it's only actually *visible* on the schedule screen — the other four are `position: fixed` pages that already paint their own opaque `-shell`/`-empty` background over it (`.budget-shell`, `.wallet-shell`, `.mytrip-empty` still on `--page-bg` unless a later pass touches them; `.lodging-shell` was switched away from `--page-bg` in the same pass that reworked that screen, see **Lodging** — it's since moved on to `--surface-blue`, one step darker, see the next bullet). The SHELL's own bars (`.mytrip-bar`/`.mytrip-tabs`/`.mytrip-panel`) were switched to `--page-bg-blue` too, in the same pass — see **Trip shell (SHELL)**'s "Colors" bullet above. When a future pass touches `budgetPage.js`/`walletPage.js`/`myTripPage.js`, switch their `-shell`/`-empty` background to `--page-bg-blue` too, to keep moving toward the TOKENS section's "apply everywhere eventually" comment on `--page-bg-blue`.
  - **`--surface-blue` (`#d6e4fb`) is one step darker than `--page-bg-blue` (`#e8f1ff`)** — a surface color (header/footer bars, buttons) meant to sit *on top of* a `--page-bg-blue` background and read as distinct from it, the same relationship `--surface`/`--surface-muted` already have to `--page-bg`. Used by `.app-top`, `.day-map-handle`, `.schedule-form-header`, `.schedule-form-footer`, `.lodging-shell` and now `.budget-header`/`.budget-total-bar` (see **Schedule item form** / **Lodging** / **Budget page**) — `.budget-shell` itself is still `--page-bg`, same as `.lodging-shell` was before it got its own pass, so only the header/footer bars read as a distinct surface for now. `--dday-pastel-bg` (`#8cb4ff`, defined earlier for the main page's D-day badge/accent buttons) is reused the same way for `.dday-badge` on the schedule screen and for the lodging map's 검색 button (`.lodging-map-search .btn-save`) — both times paired with the existing `--dday-pastel-ink` (white) for text, not a new ink token.
- **Font color policy (2026-09-29 rule, separate from the pastel policy above — this one is about plain text, not decorative/identity color).** Six roles, each backed by a `:root` token:
  | 역할 | 토큰 | 값 |
  |---|---|---|
  | 기본 글자 (검정 대신) | `--text` | `#26364a` |

## Testing notes

- In the browser tool, resizing the window does not change the page viewport (it stays 1920px wide). To test 360px or 1440px layouts, open a same-origin page and put the app in an `<iframe style="width:360px">`; media queries follow the iframe width.
- UI changes are verified by driving the app in a real browser. In the user's own Chrome profile the app is signed in and holds real trips: create and delete only your own test data (delete a test trip by its id, e.g. `TripLog.supabase.from('trips').delete().eq('id', id)`, which also removes its items, invites and members); never bulk-filter, bulk-delete or leave the user's real trips (a real leave/kick cannot be undone without a new invite).
- `storage.js` caches trips and items in memory. If a test changes data behind the app's back (direct Supabase calls or `localStorage`), call `TripLog.storage.refreshTrips()` / reload; otherwise the cache is stale.
- Google-dependent tests (day map, map picker, lodging search) fail on `http://localhost:8080` with "키 인증 실패" unless that origin is in the Maps key's referrer list; the deployed domain works. In a background tab timers are throttled and scroll events / `OverlayView.onAdd` do not run until a frame is rendered, so map tests need `window.dispatchEvent(new Event("scroll"))` and a screenshot to force frames.
- When testing the clipboard from automation the page may have no focus, so `navigator.clipboard` calls can hang or reject ("Document is not focused"); that is not an app bug.
- Two-account flows (invite acceptance, kicking, leaving) cannot be driven from one browser session. RLS and the SQL functions were tested against a real Postgres (PGlite in Node with a stubbed `auth` schema and roles); do the same for new policies before asking the user to run them.
