# Server (supabase/)

> CLAUDE.md에서 이동된 상세 내용. 이 영역을 작업하기 전에 먼저 읽을 것. 스키마 원본은 supabase/migrations/ 참고.

- **Migrations** (`supabase/migrations/`, run by the user in the Supabase SQL Editor, in order; PRD: `PRD v3 — 여행 공유 · 초대 기능` in the repo root):
  - `001_invite_feature.sql`: tables `trips` (`owner_id`), `schedule_items`, `trip_members` (roles `owner`/`editor`, `unique(trip_id,user_id)`), `trip_invites` (`invite_code`, 7-day expiry); RLS on all four; trigger `trips_add_owner` inserts the creator as `owner`; `security definer` helpers `is_trip_member` / `is_trip_owner` (the PRD's own policies recurse on `trip_members`); invitees join only through `rpc('accept_trip_invite', { p_invite_code })`; `trip_members` has no client INSERT/UPDATE policy; the owner can delete other members. It makes `category`/`title` nullable (the app's item shape `place/lat/lng/flight/lodging` differs from the PRD's `time/category/title`) and adds `lat/lng/flight/lodging/city_id`.
  - `002_flight_ocr.sql`: `airline` / `flight_no` on `schedule_items` (after 001).
  - `003_member_profiles.sql`: `get_trip_members` (optional; without it the member list shows counts only).
  - `004_leave_trip.sql`: policy "참여자는 스스로 나가기" so a participant can delete their own non-owner membership (needed by 여행 나가기).
  - `005_budget.sql` (PRD v6 "가계부 기능", file `PRD v6 — 가계부 기능` in the repo root; named 005 not 004 to avoid colliding with `004_leave_trip.sql`): table `expenses` (`trip_id` not null, `day_key` — `"prep"` or `"YYYY-MM-DD"`, `amount` check `> 0`, `currency`, `krw_amount` — approximate, computed client-side at save time, `payment_method` check `cash|card`, `category` check against the 7 keys in `expenseCategoryData.js`, `payer_ids`/`split_ids` uuid[] with no per-element FK, `created_by` default `auth.uid()`), RLS enabled, one "멤버만 조회/수정" policy (`for all` using `is_trip_member(trip_id)`, so any member can edit any expense, matching the shared "결제/나누기" model — not restricted to the creator), and the `set_updated_at` trigger reused from 001. **No screen consumes this yet**: `js/currencyData.js` (`FIXED_CURRENCIES` KRW/USD, `DESTINATION_CURRENCIES` ~13 more, `RATES_TO_KRW` — approximate, needs periodic updates, `getCurrencyOptions`/`toKrw`/`findByCountry`) and `js/expenseCategoryData.js` (`EXPENSE_CATEGORIES`, 7 keys matching the SQL check) back the `#/budget/:id` page (see **Budget page**); `storage.js#loadExpenses`/`getExpenses` read `expenses`; `addExpense`/`updateExpense`/`deleteExpense` write (thin — the caller, `expenseForm.js`, computes/passes `krwAmount`, `paymentMethod`, `category`, `payerIds`/`splitIds`, `memo`; `deleteExpense` is called by the budget page's swipe-delete, see **Budget page**).
  - `006_wallet.sql` (PRD v7 "여행지갑 기능", file `PRD v7 — 여행지갑 기능` in the repo root): table `wallet_items` (`user_id` not null, FK `on delete cascade`; `trip_id` nullable, FK `on delete set null` — deliberately not `cascade`, so deleting a trip never destroys a personal document, it only unlinks it and the item falls back to the "공통 보관함"; `category` check against 5 keys `passport|flight|qr|lodging|etc`; `file_type` check `image|pdf`; `file_url` is documented to hold the Storage **path**, not a public URL, since the bucket is private) plus one RLS policy "본인만 조회/수정" (`user_id = (select auth.uid())`, no member sharing at this point — that came later, see 007). The same file also creates a policy on `storage.objects` scoped to `bucket_id = 'wallet'` requiring `(storage.foldername(name))[1] = auth.uid()::text`, i.e. every object path must start with `<uid>/…`. **The `wallet` Storage bucket itself is not created by SQL** — it must be made by hand in the dashboard first (Storage → New bucket → Public bucket OFF; the file's trailing comment block has the exact steps, plus the 10 MB / png·jpeg·pdf limits from the PRD).
  - `007_wallet_shared.sql` (개인지갑/공유지갑 구분; requires 006): adds `wallet_items.visibility` (`personal|shared`, default `personal`) plus a check that a `shared` row must have a `trip_id`; replaces 006's single "본인만 조회/수정" `for all` policy with 4 narrower ones — `select` widens to `user_id = me OR (visibility = 'shared' AND is_trip_member(trip_id))` (reusing 001's `is_trip_member` helper), while insert/update/delete stay owner-only. Also adds a second `storage.objects` policy (alongside 006's "own folder" one, combined by `OR` since both are permissive) letting a trip member `select` (not upload/modify/delete) an object whose path matches a `shared` `wallet_items.file_url` for a trip they belong to — this is what lets `getWalletFileUrl`'s `createSignedUrl` work from another member's session for a shared item, even though the file physically still lives under the uploader's own `<uid>/…` folder. See **Wallet visibility (개인지갑/공유지갑)** for the client-side behavior this backs.
  - `js/walletPage.js` (`storage.js#loadWalletItems`/`getWalletItems`), `js/walletForm.js` (`addWalletItem`) and `js/walletViewer.js` (`getWalletFileUrl`, `deleteWalletItem`) are the consumers (see **Wallet page** / **Wallet visibility (개인지갑/공유지갑)** / **Wallet upload form** / **Wallet viewer**).
  - `008_schedule_item_order.sql`: adds `schedule_items.sort_order` (integer, only meaningful within the same `trip_id`+`date` — the app never compares it across dates) and backfills existing rows to their current `created_at` order via a `row_number() over (partition by trip_id, date order by created_at)` so nothing visually reorders just from running it. Backs **Timeline reorder & swipe-delete**'s drag-to-reorder; see that section for why the client (`storage.js#addItem`/`updateItem`/`reorderItems`) is written to degrade gracefully instead of erroring outright when this hasn't been run yet (a bare `select("*")` never errors on a missing column, only an explicit `.order("sort_order", …)` or writing to it would, so the read path and `addItem`'s base insert never name that column directly — `addItem` tries the insert once with `sort_order`, and only on a 42703/PGRST204 failure retries without it).
  - `009_travel_briefing.sql`: adds `briefing_cache` (`destination text`, `date_range text` — `"YYYY-MM-DD~YYYY-MM-DD"` — , `content jsonb`, `created_at timestamptz`, `unique(destination, date_range)`), backing the Edge Function `travel-briefing`'s "same destination+date range → at most one fresh Gemini call per day" cache. RLS is enabled with **no policies at all** on purpose — this table isn't per-user/per-trip data, it's a public cross-user cache the client never reads directly, so the only thing that can touch it is the function's `SUPABASE_SERVICE_ROLE_KEY` (which bypasses RLS regardless of policies).
  - `010_user_consents.sql`: adds `user_consents` — one row per user (`user_id unique`, defaulting to `auth.uid()`), holding `terms_version`/`privacy_version` + `terms_agreed_at`/`privacy_agreed_at` (the version string and timestamp of the terms/privacy policy the user last agreed to — free-form text, no version scheme enforced at the DB level, but `legalPages.js`'s `TERMS_VERSION`/`PRIVACY_VERSION` constants — currently `"1.0"` — are the single source of truth `consentPage.js` writes here) and `marketing_agreed boolean not null default false` + `marketing_agreed_at`. RLS: a single "본인만 조회/수정" `for all` policy (`user_id = (select auth.uid())`), same shape as `wallet_items` (006) since this is purely personal data never shared with anyone else. `updated_at` is kept current by the same `set_updated_at()` trigger function 001 defines. This table only records *that* (and which version) a user consented — it's not a consent-event log (re-agreeing `upsert`s the one row in place, keyed on the `user_id` unique constraint) — see **Consent gate (약관 동의)** for the screen and routing that now actually reads/writes it.
  - `011_delete_account_cascades.sql`: changes four foreign keys' `on delete` rule so account deletion can't be blocked by them — `trips.owner_id` (`001`, previously no action at all — the one that would otherwise always fail `auth.admin.deleteUser` for anyone who owns a trip) to `cascade`, and `schedule_items.created_by`/`expenses.created_by`/`trip_invites.created_by` (`001`/`005`, previously `set null` — the "leave a trip, keep an anonymized record" behavior `storage.js#leaveTrip` relies on) also to `cascade`. This is a deliberate policy split: *leaving* one trip (`leaveTrip`, only deletes the `trip_members` row) still anonymizes your contributions to that trip, but *deleting your account* now erases them everywhere, including trips you don't own — a different, stricter expectation than leaving, and the right one for "delete all my data." Not required for the **Edge Function `delete-account`** below to work (it deletes all of this explicitly, in order, before ever calling `deleteUser`) — this migration is a schema-level safety net so the same outcome holds even if that function's logic changes or something calls `deleteUser` directly. Constraint names assumed to be the Postgres-default `<table>_<column>_fkey` (true for an inline, unnamed `references` clause, which is how `001`/`005` declared all four) — the migration's own comment flags this as the one way it could fail to apply cleanly.
  - `012_account_deletion_requests.sql`: adds `account_deletion_requests` (`email` + a `check (char_length(...) <= 320)` cap, `login_provider` nullable `check (... in ('google','kakao','naver','other'))`, `message` + a 2000-char cap, `status` defaulting to `'pending'` with a `check` against `'pending'|'done'|'rejected'`, `created_at`, `processed_at`). RLS is **insert-only** — `for insert to anon, authenticated with check (true)`, no `select`/`update`/`delete` policy at all — on purpose: this table exists specifically to take submissions from people who aren't logged in (see **Account deletion request page**), so there's no `auth.uid()` to scope a "read your own" policy against, and opening read access to everyone would leak every submitter's email to every other anon/authenticated caller. The only way to read or process these rows is the Supabase dashboard (Table Editor, which runs as `service_role` and bypasses RLS) — processing a request (actually deleting the account) is a manual step for now, same as this file's own top-of-migration note says, with `status`/`processed_at` there only so an operator can mark progress from the dashboard. No FK to `auth.users`: a request here doesn't presuppose the submitter has (or can prove) a working, loggable-into account at all.
  - `013_transport_items.sql`: adds `schedule_items.transport` (jsonb, nullable) — the storage for 기타 교통편(기차/버스/선박/기타), the same jsonb-column pattern `001`/`002` already use for `flight`/`lodging`/`airline`/`flight_no`. Shape: `{ category, depPlace, depTime, arrPlace, arrTime, seat }`. Unlike `flight`/`lodging` (present since `001`, so every `addItem` call already sends them), this column is new, so `storage.js#addItem` only sends the `transport` key when a value is actually given — a plain/flight/lodging item's insert never names this column, so it can't break on a server that hasn't run this migration yet. See **Transport (기타 교통편)** for the client side (`transportForm.js`).
  - `014_destinations.sql` (PRD v12 "여행지 확장·도시 검색"): adds `country_currency` (`country_code` PK, `currency_code`, `region` — the 11 region-tab keys, check-constrained; seeded with 201 countries/territories covering essentially every real country + HK/MO/TW/PS/XK/GU/MP, RLS read-only to `authenticated`) and `destinations` (`name_ko`/`name_en`, `country_code` references `country_currency`, `region`, `lat`/`lng`/`timezone` nullable, `currency`, `place_id` unique nullable, `source` `preset|user`, `sort_order`, `resolved_at` — null means "not yet geocoded", `unique(country_code, name_en)`, RLS read-only to `authenticated` — neither table gets an insert/update/delete policy, so only `service_role` — i.e. the `search-destination` Edge Function below — can write). Seeds 70 preset cities: the existing 일본/동남아/중국 (24, carried over from `destinations.js`'s `CITIES`, which never had coordinates — so all start with `lat/lng/timezone/resolved_at` null) + 7 new region tabs (대만/유럽/북미/오세아니아/중동/중미카리브/남미, 46 cities, PRD v12 2번) — `currency` for every seed row comes from joining `country_currency` by `country_code`. Also adds `trips.destination_id` (nullable, FK to `destinations`, `on delete set null`) — the existing `trips.destination`/`city_id` string/text columns are untouched, so nothing that reads them breaks; `destination_id` is the new system, populated only once a trip actually goes through `search-destination`'s select flow.
  - `015_destinations_unknown_country.sql`: drops the `destinations.country_code → country_currency` FK and makes `destinations.currency` nullable. Needed because `search-destination`'s select action must be able to save a city whose country isn't in `country_currency` at all (falls back to `region='other'`, `currency=null`) — `014`'s strict FK + `not null` would otherwise block that save outright. In practice this is rare (`country_currency` already covers 201 codes) but the save should degrade gracefully, not fail.
  - `016_destinations_preset_coords.sql`: backfills `lat`/`lng`/`timezone`/`resolved_at` for the 70 `source='preset'` rows `014` seeded, with hand-verified coordinates + IANA timezone names (one `update ... from (values ...)` matched on `(country_code, name_en)`, guarded to `source='preset'` only). Without this, every preset city would still need a live Google/Open-Meteo round-trip on first selection (via `search-destination`), defeating "프리셋만으로 모든 탭이 즉시 동작"— notable gotchas baked into the values: 발리 uses `Asia/Makassar` (WITA, not Jakarta's `Asia/Jakarta`/WIB), 코타키나발루 uses `Asia/Kuching` (East Malaysia's own zone, not Kuala Lumpur's), 베네수엘라/짐바브웨/시에라리온-style "currency code changed recently" issues don't apply here (this migration only touches coordinates/timezone, not currency).
  - `017_trips_timezone.sql`: adds `trips.timezone` (text, nullable) — the trip setup wizard (see **Main page / Trip setup wizard**) copies `destinations.timezone` here once `search-destination`'s select action confirms it, so later features (push notifications, briefing) can read the trip's IANA timezone directly without joining `destinations` — mirrors why `city_id`/`destination` stayed on `trips` instead of being pure joins. 국내 trips and anything created before this migration keep it `null`.
  - `018_trips_destination_fields.sql`: adds `trips.lat`/`trips.lng`/`trips.currency` (same copy-at-creation-time rationale as `017`). Added after an audit (see **My-trip page**'s 환율/날씨 bullets, **Budget page**'s 5-1 bullet) found that `hydrateExchangeCard`/`geocodeCity`/`expenseForm.js#currencyOptions` were still re-deriving currency/coordinates from the `destination` string (and a 13-country hardcoded table) even for trips that had already gone through `search-destination`'s select and knew the real ISO currency/coordinates — these three columns are what let that code branch on `trip.destinationId` instead. `currency` is `null` whenever `destinations.currency` was (country not in `country_currency`, see `015`) — code reading it must treat that as "don't guess, hide/omit" rather than defaulting to some currency.
  - `019_wallet_trip_required.sql` (user feedback: 여행지갑 items were showing mixed across every trip instead of staying with the trip they were uploaded under): makes `wallet_items.trip_id` `not null` for both `personal` and `shared` rows (006/007 only required it for `shared`; `personal` always saved `trip_id = null` — a "common storage across all trips" bucket that's exactly why every trip's 개인지갑 looked identical) and changes its FK from `on delete set null` to `on delete cascade` (a wallet item now always belongs to exactly one trip, so deleting that trip should delete its wallet items too, not orphan them into the no-longer-existing common bucket). Guarded by a `do $$ ... raise exception` block that refuses to run if any existing row still has `trip_id is null` (the migration can't know which trip an orphaned personal document belongs to — the file's own comment gives the manual fix-up SQL). RLS is untouched (007's policies never depended on `trip_id`'s nullability). The FK-rename step assumes the Postgres-default constraint name `wallet_items_trip_id_fkey` (same assumption `011_delete_account_cascades.sql` documents for its own FK renames) — the one way this migration could fail to apply cleanly. See **Wallet page** / **Wallet upload form** in `screen-wallet.md` for the client-side change (`walletForm.js` now always sends `tripId: storage.getTrip()?.id` instead of forcing `null` for personal uploads; `walletPage.js`/`storage.js` load and cache wallet items per-trip, mirroring `expenses`) and `storage.js#deleteTrip`'s new best-effort Storage cleanup of the caller's own wallet files for that trip (the DB rows cascade automatically, but Storage objects don't).
  - `020_admins.sql` (PRD v13 "메인 화면 개선 — 여행 소식·인기 여행지"의 공지사항 작성 등 운영자 권한; 이 저장소에 "관리자" 개념이 들어가는 첫 테이블): `admins` (`user_id` PK, `auth.users` FK `on delete cascade`, `created_at`). RLS는 "본인 행만 `select`" 한 정책뿐 — insert/update/delete 정책이 전혀 없어서 관리자 추가/해제는 Supabase 대시보드(Table Editor, `service_role`)에서 운영자가 직접 처리해야 한다(`012_account_deletion_requests.sql`의 "처리는 대시보드 수동 작업" 패턴과 동일). 전체 관리자 목록은 어떤 클라이언트에도 노출되지 않는다. 같이 추가한 `is_admin(uid uuid default auth.uid())`는 `001_invite_feature.sql`의 `is_trip_member`/`is_trip_owner`와 같은 이유로 `security definer`다 — 다른 테이블의 RLS 정책이 `admins`를 직접 참조하면 "본인 행만 조회" 정책 때문에 타인에 대해 확인할 길이 없어지는데, 이 함수는 RLS를 우회해 임의의 uid에 대해 관리자 여부를 판정한다. 클라이언트는 `supabase.rpc('is_admin')`으로 로그인한 사용자 본인의 관리자 여부를 확인할 수 있고(관리자 메뉴 노출 등), 향후 공지사항 테이블의 "관리자만 작성/수정/삭제" 정책은 `using (public.is_admin())`로 이 함수를 재사용하면 된다. 공지사항 테이블 자체는 아직 만들지 않았다 — 이 마이그레이션은 관리자 판별 기반만 놓은 것.
  - `021_travel_feed.sql` (PRD v13, `020_admins.sql` 이후): `travel_feed_items`(안전 소식/혜택 소식, `kind` `safety|benefit`, `scope` `domestic|overseas`, `country_code`는 `country_currency` FK지만 nullable, `airline_code`는 IATA 코드 nullable, `summary`는 길이를 DB에서 강제하지 않는 "200자 내외" 자유 텍스트, `valid_from`/`valid_to`는 `valid_to >= valid_from` 체크만, `status` `draft|published|archived`, `origin` `manual|auto`, `(origin, external_id)`는 `external_id is not null`일 때만 유니크한 부분 인덱스로 자동 수집 중복 방지)와 `popular_destinations`(월별 랭킹, `period`는 `'YYYY-MM'` 정규식 체크, `(scope, period, rank)` 유니크, `destination_id`는 있으면 `destinations` FK 연결 없으면 null) 두 테이블. RLS는 두 테이블 동일한 모양: `select`는 `status='published'`인 행만(로그인 사용자 전체), insert/update/delete는 전부 `020`의 `is_admin()`으로 게이트 — 일반 사용자는 어느 쪽도 직접 못 쓴다. **자동 수집 Edge Function은 아직 만들지 않았다**(이 마이그레이션엔 미포함) — 만들 때는 `service_role`로 `status='draft'`만 insert하면 되고, service_role은 RLS를 건너뛰므로 이 테이블에 별도 정책을 추가할 필요가 없다.
    - `get_travel_feed(p_kind, p_scope, p_limit)`: `security definer`(`set search_path = ''`), 로그인하지 않았으면(`auth.uid()` null) 빈 결과. 우선순위 1~5(낮을수록 먼저) — (1) 내 진행중·예정 여행 국가 일치 + `importance='high'`, (2) 내 여행 국가만 일치, (3) 내 여행 항공권 항공사 일치, (4) 그 외 `importance='high'`, (5) 나머지는 `published_at desc`. "내 여행"은 `trip_members`로 속해 있고 `end_date >= current_date`인 것만(지난 여행 제외) — `trips.destination_id → destinations.country_code`로 국가를 구하고, `schedule_items.flight_no`의 앞 2~3글자(정규식 `^[A-Za-z]{2,3}`)를 IATA 코드로 간주해 항공사를 구한다(스키마에 IATA 코드 전용 컬럼이 없어서 쓰는 best-effort 추출 — 틀린 코드를 뽑을 edge case가 있을 수 있음, 필요해지면 `schedule_items`에 전용 컬럼을 추가하는 편이 정확하다). `valid_to`가 지난 `benefit`, `importance`가 `high`가 아니면서 90일 넘은 `safety`는 결과에서 제외. 반환은 `travel_feed_items`의 `published` 행뿐이고 호출자의 여행/항공권 정보 자체는 결과에 섞이지 않는다. `p_limit`은 음수 방지 + 100개 상한(`least(greatest(p_limit,0),100)`).
    - `get_popular_destinations(p_scope)`: 같은 `security definer` 패턴, `published`인 행 중 해당 `scope`의 가장 최근 `period`(텍스트 `'YYYY-MM'`이라 문자열 `max()`가 그대로 최신월)의 `rank` 상위 10개만 반환.

    - **"성공"의 정의**: `net.http_post`는 비동기(요청을 큐에 넣고 바로 `request_id`만 돌려줌 — 실제 HTTP 응답은 기다리지 않음)라서, 진짜 "send-notification이 실제로 뭘 했는지" 동기로 확인하려면 pg_net의 `net.http_collect_response()`가 필요한데, 그 함수의 정확한 반환 타입/필드 이름을 이 환경에서 pg_net을 실제로 설치해 확인할 방법이 없었다(`airport-congestion`의 "확인 안 된 외부 API" 사례와 같은 이유로, 추측으로 그 API에 기대는 대신) — 그래서 `032`/`033`이 이미 쓰는 "fire-and-forget `net.http_post` + 예외 안 나면 성공" 검증된 패턴을 그대로 따랐다. `sent_at`은 "호출을 성공적으로 큐에 넣었다"는 뜻이지 "전원에게 실제로 전달됐다"는 보장은 아니다 — 다만 `send-notification` 자체도 best-effort(개별 기기 실패를 허용하고 항상 200에 집계만 돌려줌)라 이 해석이 기능 전체와 일관된다.
    - `title`/`body`는 `announcements` 행의 값을 그대로 실어 보낸다. 공지사항은 `notification_settings`에 끄는 설정이 없어서(031) `send-notification`의 대상 필터가 전원을 통과시킨다.
    - Vault의 `notify_secret`은 `032`가 등록해 둔 것을 그대로 재사용한다. 실패 격리(`exception when others`)는 `032`/`033`과 동일 — Vault 조회나 `net.http_post` 자체가 실패해도 `announcements` insert는 항상 성공하고, `sent_at`은 031의 애초 의도대로 "아직 발송 안 함"을 뜻하는 `null`로 남는다.
    - **`RETURNING`의 함정**: `insert ... returning sent_at`으로 바로 확인하면 `null`이 보인다 — `RETURNING`은 INSERT 문 자체가 끝난 시점의 행 이미지라서 그 다음에 도는 AFTER 트리거의 UPDATE(`sent_at` 채우기)를 못 본다(Postgres 표준 동작, 버그 아님). 실제로 채워졌는지는 insert를 끝낸 뒤 별도 SELECT로 봐야 한다 — PGlite 테스트에서 직접 재현해 확인했다(파일 자체 주석과 아래 insert 예시에도 남겨 뒀다).
    - **검증**: `032`/`033`과 같은 PGlite 기법 — `net.http_post`/Vault를 호출 기록만 하는 스텁으로 대체하고 실제 `insert into announcements`를 실행했다. 확인한 것: 발송 성공 시 `net.http_post`가 정확히 한 번, `send-notification` 엔드포인트로, `userIds:'all'`/`type:'announcement'`/입력한 `title`·`body` 그대로, Vault의 `x-notify-secret` 헤더와 함께 호출됨, 그 후 DB의 `sent_at`이 채워짐, `RETURNING`은 여전히 `null`(위 함정 재현), Vault에 시크릿이 없으면 `net.http_post` 호출 자체가 없고 `insert`는 에러 없이 성공하며 `sent_at`은 `null`로 남음 — 전부 통과.

- **Edge Function `delete-account`** (`supabase/functions/delete-account/index.ts` + README; deployed with `supabase functions deploy delete-account`; called from `accountDeletePage.js`'s final confirm dialog — see **Account deletion (회원 탈퇴)**): takes `POST` with no body — the only input is the caller's own `Authorization` JWT, decoded the same way `analyze-ticket#isSignedIn` does (`role`/`sub` claims, trusting the gateway already verified the signature) to get the id of the account to delete. **Deliberately ignores any user id a request body might contain** — a client can only ever delete itself, never be tricked or abused into deleting someone else. `service_role` is used only for the deletion work below, never for identifying the caller. Like `naver-login`, this one imports `@supabase/supabase-js` (same pinned version) because it needs the Auth Admin API (`admin.auth.admin.deleteUser`) and Storage admin calls, not just Postgres rows.
  - **Twelve explicit, ordered steps**, each wrapped so a failure names exactly which one broke (a shared `step(label, run)` helper turns any `{ error }` into `Error("<label> 실패: <message>")`): (1) `wallet_items` — reads each row's `file_url` (the path inside the private `'wallet'` bucket) first, removes those Storage objects, *then* deletes the rows, because Storage objects aren't Postgres rows and no FK `cascade` ever reaches them. (2) `expenses` where `created_by` = caller. (3) `schedule_items` where `created_by` = caller. (4) `trip_members` where `user_id` = caller — every membership, owned trips and shared ones alike ("본인이 속한"). (5) `trips` where `owner_id` = caller only — a shared trip the caller merely belongs to was already handled by step 4 (membership gone, trip itself untouched); deleting an *owned* trip here cascades via its own `trip_id` FKs to any remaining `schedule_items`/`expenses`/`trip_members`/`trip_invites` other members left in it — the same blast radius as `storage.js#deleteTrip`. (6) `trip_invites` where `created_by` = caller — RLS only lets owners create invites, so step 5's cascade has usually already cleared these; this is a (harmless, idempotent) mop-up. (7) `user_consents` where `user_id` = caller. (8) `device_tokens` where `user_id` = caller — every push token this account registered on any device/browser. (9) `notification_settings` where `user_id` = caller. (10) `notifications` where `user_id` = caller. (11) `notification_log` where `user_id` = caller. (12) `admin.auth.admin.deleteUser(caller)` — by now nothing should still reference this user, so this should always succeed cleanly.
  - **Steps 2, 3 and 6 deliberately aren't scoped to "only trips I own"** — they delete by `created_by` regardless of who owns the trip, on purpose: this is a genuine policy difference from "여행 나가기" (`storage.js#leaveTrip`, which only removes the `trip_members` row and leaves your contributions anonymized in place) — *deleting the account* is a stronger ask ("erase my data") than *leaving a trip* ("I'm done with this one"), so it reaches into other people's trips to remove what this user specifically contributed, not just what they owned.
  - **Steps 8–11 (added for PRD v11 push notifications) are purely personal data** — unlike 2/3/6, there's no "other user's trip" scoping question, `user_id = caller` is always the complete and correct scope.
  - **Not a single transaction.** Running twelve separate REST/Admin-API calls instead of one Postgres transaction means a mid-sequence failure can leave the earlier steps already applied. This is accepted, not accidental: every step's `WHERE` clause is scoped to the caller, so **re-running the whole function is always safe** — already-deleted rows just match zero and move on — making "retry" the actual recovery mechanism, which is also why the client's fixed failure message doesn't need to explain anything more specific than "try again / contact support." A single all-or-nothing version would need a dedicated Postgres function (RPC) wrapping all twelve steps in one transaction, which wasn't asked for and wasn't built.
  - `011_delete_account_cascades.sql` is a schema-level safety net for steps 1–7, not a dependency of them — see that migration's own CLAUDE.md entry above. `031_push_notifications.sql` is the equivalent safety net for steps 8–11 (it declared `on delete cascade` to `auth.users` from the start, not retrofitted later like 011). The function remains correct even on a database that hasn't run either — steps 1–11 already clear everything step 12 needs gone.
  - The client (`accountDeletePage.js`) never shows this function's specific error text to the end user — see **Account deletion (회원 탈퇴)** — only `console.warn`s it; the specific "`<단계> 실패: ...`" message exists for Edge Function logs, not for display.
  - Not yet deployed or run against a real account (deploying Edge Functions, and running `011_delete_account_cascades.sql`, are both the user's own steps, per this file's **Commands** section). Verified instead by exercising the client-side failure path for real: with the function undeployed, `accountDeletePage.js`'s confirm dialog genuinely received a failed `functions.invoke` call end to end (checkbox → button → confirm dialog → the fixed "고객센터로 문의해주세요" message shown inline, dialog left open, account/trips confirmed untouched afterward) — this is the actual current-state failure path, not a simulated one.

  - **구글 응답에 국가코드가 없는 문제**: Places Autocomplete (New)는 city/country 제안에 ISO 국가코드를 안 준다(Place Details까지 가야 나온다) — 그래서 검색 단계의 구글발 결과는 `secondaryText`(보통 "도시, 나라" 형식)의 마지막 구성요소를 하드코딩된 `COUNTRY_NAMES` 맵에서 역조회해 `country_code`를 best-effort로 채우고, 못 찾으면 `null`로 둔다(그래도 `place_id`가 있어서 선택 단계에서 Place Details로 확정된다). 같은 이유로 검색 단계의 구글발 결과는 `name_ko`/`name_en`에 같은 표시값이 들어간다 — 요청 언어 하나로만 Autocomplete를 부르기 때문에 두 언어를 동시에 정확히 채우려면 호출이 2배로 늘어 "검색당 외부 호출 2회" 한도를 검색 단계에서 다 써버린다; 정확한 영문 표기는 선택 단계에서 확정된다.
  - **남용 방지**: 사용자당 분당 20회(상수 `RATE_LIMIT_PER_MINUTE`, 검색+선택 합산) 초과 시 429. 함수 인스턴스 메모리의 `Map`으로만 세는 best-effort 제한이다 — 콜드 스타트/다중 인스턴스에서는 실제 상한이 설정값보다 높아질 수 있다; 엄격한 보장이 필요해지면 Postgres 테이블 기반 리미터로 바꿔야 한다.
  - 필요한 비밀값: `GOOGLE_PLACES_API_KEY`(서버용 — `googleMaps.js`의 브라우저용 키는 HTTP 리퍼러 제한이 있어 서버에서 쓸 수 없다). 없으면 Google 호출을 건너뛰고 Open-Meteo 전용으로 동작한다(로그에 경고만 남기고 500은 내지 않는다).
  - Node + `globalThis.Deno`-shim 기법(다른 함수들과 동일)으로 검증: 비로그인 401, 프리셋 적중 시 "10개 미만이면 항상 Google로 보충 시도"(명세대로의 의도된 동작), 프리셋에 없는 검색어의 Google 보완, 나라 이름 검색의 프리셋-먼저 채우기, 한글 1자/영문 1자 길이 검증, 이미 확정된 프리셋의 외부 호출 없는 select, 미확정 프리셋의 Text Search+Open-Meteo를 통한 확정 후 `PATCH`, place_id 경로의 신규 도시 Place Details+Open-Meteo를 통한 `INSERT`, select 입력 부족 400, 분당 상한 초과 429 — 전부 통과. 실제 Google/Open-Meteo API에는 호출하지 않았다(응답을 흉내낸 `fetch` 모킹) — 배포 후 실제 키로 curl 재확인은 README의 몫.

- **Edge Function `collect-travel-feed`** (`supabase/functions/collect-travel-feed/index.ts` + README; 자동 수집, `025_collect_travel_feed_cron.sql`이 pg_cron으로 매일 1회 부름; 단계 0 조사에서 "자동 수집 가능"으로 확인된 소스만 다룬다 — 인기 여행지는 공식 월간 순위가 API/파일로 없어서 이 함수에 없다, `/admin`에서 계속 수동 입력): Deno, no imports, 다른 Gemini 계열 함수들과 달리 **로그인한 사용자가 아니라 pg_cron(서버 대 서버)만 호출**하므로 `Authorization` JWT 대신 고정 공유 비밀값 헤더(`x-cron-secret`, `CRON_SECRET` 비밀값과 대조)로 막는다 — 틀리거나 없으면 401. `SUPABASE_URL`/`SUPABASE_SERVICE_ROLE_KEY`(자동 주입)로 PostgREST에 직접 쓴다(`travel-briefing`과 같은 "import 없이 REST" 방식).

- **Edge Function `send-notification`** (`supabase/functions/send-notification/index.ts` + README; PRD v11 "푸시 알림 시스템"; `031_push_notifications.sql`의 `device_tokens`/`notification_settings`/`notifications` 필요; 서버(DB 트리거, pg_cron 등)만 부르는 내부 발송 함수 — `collect-travel-feed`와 같은 이유로 `Authorization` JWT를 전혀 보지 않고 고정 공유 비밀값 헤더(`x-notify-secret`, `NOTIFY_SECRET` 비밀값과 대조)로만 막는다, 없거나 틀리면 401): **이 함수만 예외적으로 import를 쓴다** — Web Push(RFC 8291 aes128gcm 암호화 + VAPID JWT 서명)를 직접 구현하는 건 비합리적인 범위라 `https://esm.sh/web-push@3.6.7`을 쓴다(`naver-login`/`delete-account`가 Admin API 때문에 `@supabase/supabase-js`를 이미 같은 esm.sh 방식으로 예외 처리한 것과 같은 선례). FCM 쪽 Google OAuth2 JWT Bearer 플로우(RFC 7523)는 Web Crypto API(`crypto.subtle`, RSASSA-PKCS1-v1_5/SHA-256)만으로 직접 구현했다 — 짧고 의존성이 필요 없어서 import하지 않았다. 그 외에는 `travel-briefing`/`collect-travel-feed`와 같은 "`SUPABASE_URL`/`SUPABASE_SERVICE_ROLE_KEY`로 PostgREST에 직접 쓴다" 방식(supabase-js 미사용).
  - **입력**: `POST { userIds: string[] | "all", type: "departure"|"schedule"|"invite"|"announcement", title, body?, url?, tripId? }`. `userIds:"all"`은 GoTrue Admin API(`GET {SUPABASE_URL}/auth/v1/admin/users?page=&per_page=500`)로 전체 `user_id`를 모은다 — 응답이 배열 그대로인지 `{users:[...]}`인지 실제 호출로 확인 못 해 둘 다 받아들인다(`airport-congestion`과 같은 "정직한 불확실성 표기").
  - **대상 필터**: `departure`/`schedule`은 `notification_settings.schedule_enabled=true`, `invite`는 `share_enabled=true`, `announcement`는 필터 없음. `notification_settings`에 행이 없는 사용자는 "꺼짐(false)" 집합에서 `select`로 걸러낸 뒤 그 집합에 없으면 통과시키는 방식이라 자동으로 켜짐 기본값이 된다(설정 화면 `storage.getNotificationSettings()`의 기본값과 동일한 의미).
  - **발송**: 필터를 통과한 대상의 `device_tokens`를 `platform`별로 나눠 보낸다. android는 FCM HTTP v1(`https://fcm.googleapis.com/v1/projects/<project_id>/messages:send`, `android.notification.channel_id`를 `triplog/js/pushNotifications.js`가 만드는 채널 id `"routory-default"`와 맞춘다) — `FCM_SERVICE_ACCOUNT` 비밀값(서비스 계정 키 JSON)의 `private_key`로 RS256 JWT를 서명해 액세스 토큰을 받는다. web은 Web Push — `VAPID_PRIVATE_KEY`/`VAPID_PUBLIC_KEY`(`triplog/js/config.js`의 `vapidPublicKey`와 반드시 같은 쌍이어야 한다)로 `webpush.setVapidDetails`, `device_tokens.token`(`triplog/js/webPush.js`가 저장한 `PushSubscription` JSON)을 그대로 `JSON.parse`해서 전달. 만료·무효 토큰(FCM `error.status` `UNREGISTERED`/`NOT_FOUND` 또는 HTTP 404, Web Push `WebPushError.statusCode` 404/410)은 그 자리에서 `device_tokens`에서 삭제한다.
  - **notifications 기록**: 발송 성공 여부와 무관하게, 필터를 통과한 대상 전원에게 `notifications` 행을 하나씩 남긴다(기기 토큰이 없는 사용자도 인앱 알림센터 목록에는 보여야 해서).
  - **"all" 500명 배치**: 필터링→기기 토큰 조회→발송→`notifications` 기록 전체를 500명 단위 청크로 돈다(명시적으로 500명을 넘는 `userIds` 배열도 같은 루프를 타 안전하다). FCM 액세스 토큰/VAPID 설정은 실제 발송 대상이 생겼을 때만, 그리고 호출당 한 번만 준비해 재사용한다(매 청크 재조회하지 않음).
  - **시크릿 비노출**: `NOTIFY_SECRET`·`FCM_SERVICE_ACCOUNT`·`VAPID_PRIVATE_KEY` 값 자체는 어떤 로그에도 안 남는다(`collect-travel-feed`와 동일한 원칙) — 아래 검증에서 이 조건 자체를 자동으로 확인했다.
  - **검증**: 이 환경에 Deno/Docker가 없어 실제 Edge Runtime에서는 못 돌려봤다. 대신 (1) FCM RS256 서명을 Node `globalThis.crypto.subtle`로 자체 서명→검증 왕복까지 확인, (2) `web-push@3.6.7`을 로컬에 설치해 자체 서명 인증서 HTTPS 서버로 실제 VAPID 서명(`authorization: vapid ...`)과 `aes128gcm` 암호화 본문이 실려 오는 것까지 end-to-end로 확인, (3) `index.ts` 전체를 Node + `globalThis.Deno`-shim으로(import 한 줄만 esm.sh → 로컬 npm `web-push`로 바꾼 사본, 로직은 100% 동일) 401/405/400 가드·타입별 대상 필터(기본값 포함)·FCM/WebPush 성공·무효토큰삭제(가짜 Google OAuth 엔드포인트가 JWT 서명을 실제로 암호학적으로 검증한 뒤에만 토큰을 내주도록 만들어 서명 로직을 핸들러 전체 흐름 안에서도 확인)·`notifications` insert·`"all"`의 GoTrue 2페이지(500+150) 페이지네이션과 청크 분할·시크릿 무로그까지 전부 통과를 확인했다. **실제로 확인 못 한 것**: esm.sh의 `web-push`가 진짜 Supabase Edge Runtime(Deno) 위에서 그대로 동작하는지(ECDH/HKDF/AES-GCM을 esm.sh 번들 안에서 수행하므로 `@supabase/supabase-js` 선례보다 보장이 약하다), 실제 Firebase 프로젝트/기기로의 FCM 발송 — README의 배포 후 curl 테스트가 이 부분을 메운다.
  - `032_trip_member_notify.sql`의 `trip_members` AFTER INSERT 트리거가 이 함수를 처음으로 실제 호출한다(새 멤버 가입/초대 수락, `type:'invite'`) — 자세한 내용은 그 마이그레이션 항목 참고. 시간 기반 발송(출발 임박/일정 임박)은 아래 `notify-scheduler`가 호출한다.

- **Edge Function `notify-scheduler`** (`supabase/functions/notify-scheduler/index.ts` + README; PRD v11 4번 "시간 기반 이벤트"; `033_notify_scheduler.sql`의 pg_cron 작업이 5분마다 호출; `send-notification`과 같은 이유로 `x-notify-secret`/`NOTIFY_SECRET`로만 막는다 — Supabase secrets는 프로젝트 전역이라 `send-notification`에 이미 설정했다면 추가 설정이 필요 없다): Deno, no imports. 타임존 계산·중복 방지 예약은 전부 `033`의 두 SQL 함수(`rpc`로 호출)가 하고, 이 함수는 그 결과를 받아 `was_reserved=true`인 행만 트립/일정 단위로 묶어 `send-notification`을 부르는 "그룹핑 + 호출" 역할만 한다(요청 5번 — 대상 1명마다 부르지 않는다, `send-notification`이 `userIds` 배열 하나로 한 번에 처리하므로 같은 트립/같은 일정의 수신자는 항상 하나의 호출로 묶인다).
  - **문구**: 출발 임박은 `"내일 '<여행 제목><이/가>' 시작돼요. 항공권과 준비물을 확인하세요"`(요청 2번 예시 그대로, 다만 여행 제목이 받침 없이 끝나도(예: "하와이") 자연스럽도록 `josa()` 헬퍼로 조사만 코드로 고른다 — 한글 음절의 종성 유무 판정). 일정 임박은 `"'<일정 제목 또는 장소>' 일정이 곧 시작돼요 (HH:MM)"`(제목→장소→"다음 일정" 순으로 대체, "일정이"는 항상 받침 있는 "일정"에 붙어 조사 선택이 필요 없다).
  - **로그(요청 6번)**: 매 실행 끝에 `departure`/`schedule` 각각의 `processed`(조건 충족 전체)/`sent`(실제 신규 발송)/`skipped`(중복이라 건너뜀)/`calls`(`send-notification` 호출 횟수)/`events`(알림이 나간 트립·일정 개수)를 한 줄로 남긴다. `NOTIFY_SECRET` 값은 절대 로그에 안 남는다(`send-notification`과 같은 원칙).
  - 출발 임박/일정 임박 어느 한쪽 처리 중 오류가 나도(rpc 실패 등) 다른 한쪽은 그대로 처리되고 실패한 쪽만 0으로 기록된다 — 응답은 항상 200. 한 이벤트(트립/일정)의 `send-notification` 호출이 실패해도 다음 이벤트 처리를 막지 않는다.
  - Node + `globalThis.Deno`-shim(다른 함수들과 동일)으로 rpc 두 개와 `send-notification` 호출을 모킹해 검증: 401/405 가드, 후보 0건일 때 전부 0, 그룹핑이 유저 수가 아니라 이벤트(트립/일정) 수만큼만 `send-notification`을 부름, 받침 있는/없는 제목의 조사 선택, 시간 포맷(`HH:MM`)과 제목→장소→기본값 대체, 한쪽 호출 실패가 나머지를 막지 않음, `NOTIFY_SECRET` 무로그 — 전부 통과.
